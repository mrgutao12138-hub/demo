# 00 · 本章导读：企业数据接入

> 同学们好。  
> 前面你已经能让 Agent **调 Tool 查数**、用 **RAG 查口径**。  
> 从本章开始，我们要把假 `Map` 换成真世界：**ERP、WMS、EMS** 变成 Agent 的**只读决策数据源**——  
> 模型仍然不碰生产写账号，数字仍然只从你的 Java Tool 出来。

---

## 1. 本章要解决什么问题

管理层的问题从来不是「库里有没有表」，而是：

- 「华东仓 SKU-1001 **现在**能发多少？」——要 **可用库存**，不是理论库存。
- 「哪些采购单**已经超期**还没到货？」——要 **官方超期口径**，不是模型猜的「大概晚了」。
- 「今天哪条产线**停机超过半小时**？」——要 **EMS/MES 事件**，不是聊天记录。

这些数字来自三套异构系统：

| 系统 | 本讲义含义 | 你先暴露什么 |
|---|---|---|
| **ERP** | 采购、供应商、订单头行 | 超期采购、在途未到 |
| **WMS** | 仓库、库存快照 | 可用量、低库存清单 |
| **EMS** | 设备 / 能源 / 运维 | 长停机、产线状态 |

> **说明：** 若贵司把制造执行叫 **MES** 而不是 EMS，**接入套路完全相同**——同步事件宽表 + 只读 Tool，只是 `source_system` 字段写成 `MES`。

## 2. 四种接入模式（必须全懂，再选主路）

| 模式 | 一句话 | 何时用 |
|:---:|---|---|
| **1** | 调现成 HTTP/RPC 查询 API | 已有稳定查询服务、不想碰库 |
| **2** | 只读库账号 + 视图，参数化 SQL | 过渡期、表不多、能控权限 |
| **3** | **同步决策宽表到独立 Postgres** | **主推荐**，生产默认 |
| **4** | 受控 Text-to-SQL（关笼子） | 探索分析，**默认不作主路径** |

推荐演进：

```
有现成查询 API ──► 模式 1（短期最快）
        │
        ▼  API 不够灵活 / 要统一口径
只读账号 + 视图（模式 2）
        │
        ▼  要隔离生产、要压延迟、要审计
独立 Postgres 决策宽表（模式 3）  ← 主推荐落点
        │
        ▼  仅少数高阶分析场景
受控 Text-to-SQL（模式 4，笼子内）
```

## 3. 本章【红线】——不及格线，默写

1. **模型不直连生产写账号。** JDBC 连接决策库只读用户；`DataSource#setReadOnly(true)`。
2. **每个 Tool 一个业务能力。** 禁止暴露 `query(sql)` 这种通用 SQL 工具给模型。
3. **`warehouseId` / `tenantId` 强制。** SQL 的 `WHERE` 里必须有租户；仓要在用户白名单内。
4. **回答带 `dataAsOf`。** 来自宽表字段或 `sync_metadata`，让用户知道数字新鲜度。
5. **指标字典：中文名 → 官方查询。** 「可用库存」只能走 `INV_AVAILABLE_QTY` 对应 SQL，不能临场发明口径。
6. **JDBC 参数绑定。** 用 `NamedParameterJdbcTemplate` 或 MyBatis `#{}`；**禁止**字符串拼接 SQL。
