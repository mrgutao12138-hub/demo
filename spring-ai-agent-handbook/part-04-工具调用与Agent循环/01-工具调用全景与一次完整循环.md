# 01 · 工具调用全景与一次完整循环

> 这一节不讲业务，只讲机制。  
> 你把这张图吃透，后面写库存 Agent 不会慌。

---

## 1. 先纠正一个危险误解

很多同学以为：

> 模型连上了我的数据库，所以它能查库存。

**错。**

模型只能做两件事：

1. **生成文字**（包括「我想调用某个工具，参数是……」这种结构化意图）
2. **根据你喂回去的工具结果，再生成下一段文字**

真正查库、鉴权、限流、审计，全是你的 **Java 工具方法**。  
Spring AI 2.0 把「来回好几趟」编排进了 **`ToolCallingAdvisor`**，挂在 **`ChatClient` 的 Advisor 链**上——**不在 `ChatModel` 内部**。

---

## 2. 全景架构图

```
用户 HTTP 请求
      │
      ▼
┌─────────────────────────────────────────────────────────┐
│  ChatClient.prompt().user("...").tools(...).call()       │
└───────────────────────────┬─────────────────────────────┘
                            │
                            ▼
              ┌─────────────────────────────┐
              │  Advisor 链（按 order 排序）  │
              │  例：Memory(200) → Tool(300) │
              └─────────────┬───────────────┘
                            │
                            ▼
              ┌─────────────────────────────┐
              │  ToolCallingAdvisor          │  ← 工具循环的「心脏」
              │  （DefaultChatClient 自动注册 │
              │   恰好一个 ToolAdvisor）      │
              └─────────────┬───────────────┘
                            │
         ┌──────────────────┼──────────────────┐
         ▼                  ▼                  ▼
   组装 Prompt        调 ChatModel        ToolCallingManager
   （含 Tool Def）     （DeepSeek 等）      执行匹配的 ToolCallback
         │                  │                  │
         └──────────────────┴──────────────────┘
                            │
              有 tool calls？ ──是──► 结果写入 ToolResponseMessage
                            │              │
                            │              └──► 再进下一轮（重入链）
                            │
                           否
                            ▼
                    最终 Assistant 文本
                            │
                            ▼
              Memory Advisor 存最终轮（默认在循环外）
```

记住分工：

| 角色 | 负责什么 |
|---|---|
| 模型 | 选工具、填 JSON 参数、读结果、组织人话 |
| `ToolCallingAdvisor` | 循环、何时停、是否 returnDirect |
| `ToolCallingManager` | 按名找 `ToolCallback`、执行、转结果 |
| 你的 `@Tool` 方法 | 业务规则、只读、校验、返回给模型看的字符串 |

## 3. 一次完整循环（逐步跟）

假设用户问：「A 仓 SKU-1001 有多少可用库存？」  
你已注册 `getSku`、`queryInventory`、`compareWarehouses`。

### 第 0 步：你调用 ChatClient

```java
chatClient.prompt()
    .user("A 仓 SKU-1001 有多少可用库存？")
    .tools(inventoryTools)
    .call()
    .content();
```

`DefaultChatClient` 发现本次有 tools，会确保链上有**恰好一个** `ToolAdvisor`（默认自动挂上 `ToolCallingAdvisor`）。

### 第 1 步：Tool Definition 发给模型

`ToolCallingAdvisor` 从你传入的 `@Tool` 对象 / `ToolCallback` / `ToolCallbackProvider` 提取：

- 工具名（如 `queryInventory`）
- description（中文写清楚何时用）
- 参数的 JSON Schema（`@ToolParam` 会进 schema）

这些作为 **Tool Definition** 随本次 Prompt 发给 `DeepSeekChatModel`。

模型**看不到**你的 `Map`、**看不到**方法体。

### 第 2 步：模型返回（可能含 tool calls）

模型可能直接回答，也可能返回：

```json
{
  "tool_calls": [
    {
      "name": "queryInventory",
      "arguments": "{\"skuId\":\"SKU-1001\",\"warehouseId\":\"WH-A\"}"
    }
  ]
}
```

有没有 tool calls，由模型决定；你能不能执行，由你的 Java 决定。

### 第 3 步：ToolCallingManager 执行

`ToolCallingAdvisor` 把 tool calls 交给 `ToolCallingManager`：

1. 按名称匹配 `ToolCallback`
2. 反序列化参数，调你的 Java 方法
3. 把返回值（或你包装的错误信息）写成 **ToolResponseMessage**

### 第 4 步：结果回填，进入下一轮

Advisor **重入**下游链：把「用户原话 + 上一轮 assistant 的 tool call 请求 + tool response」合并后再打模型。

模型读到真实数字，生成人话：

> A 仓 SKU-1001 当前可用库存为 128 件，数据截至 2026-09-08 18:00。

### 第 5 步：停止条件

当模型响应**不再包含 tool calls**，循环结束，`call()` 把最终文本返回给你。

默认停止条件：`chatResponse.hasToolCalls() == false`。  
也可自定义 `ToolExecutionEligibilityChecker`（高级，本章先知道存在即可）。

## 4. 定义工具的三种方式（2.0 都汇到 ToolCallback）

| 方式 | 适用场景 | 典型代码 |
|---|---|---|
| **@Tool / @ToolParam** | 你写业务类，最省事 | 本章库存 Agent 主路径 |
| **MethodToolCallback** | 反射已有方法、动态注册 | 对接遗留 Service、运行时拼工具 |
| **FunctionToolCallback** | Lambda、`Function`、方法引用 | 薄封装、测试桩、配置化工具 |

三种产出都是 `ToolCallback`，走**同一条** `ToolCallingAdvisor` 循环。  
可以混用：` .tools(inventoryTools, myFunctionCallback, mcpProvider)`。

【易混】2.0 **删除**了 `SpringBeanToolCallbackResolver` 和 `.toolNames()`。  
不能扔一个裸 `Function` Bean 再按名字解析——必须显式 `.tools(...)` 或 `defaultTools`。

## 5. 怎么把工具传给 ChatClient

```java
// 单次请求
chatClient.prompt()
    .user("...")
    .tools(new InventoryTools(store))
    .call();

// 每个请求默认都有（慎用危险工具）
ChatClient client = ChatClient.builder(chatModel)
    .defaultTools(new InventoryTools(store))
    .build();
```

规则：

- `.tools(...)` 与 `defaultTools` **取并集**，不是覆盖
- 参数类型可混：`@Tool` POJO、`ToolCallback`、`ToolCallbackProvider`、数组
- 关自动执行：`spring.ai.chat.client.tool-calling.enabled=false` 或单次 `AdvisorParams.toolCallingAdvisorAutoRegister(false)`

## 6. DefaultChatClient 与「恰好一个 ToolAdvisor」

`ToolAdvisor` 是标记接口。`DefaultChatClient` 强制：

- 链上**有且仅有**一个实现 `ToolAdvisor` 的 Advisor
- 默认自动注册 `ToolCallingAdvisor`（order = `HIGHEST_PRECEDENCE + 300`）
- 你若注册自定义子类（如 `ToolSearchToolCallingAdvisor`），框架跳过默认注册，用你的那一个

为什么？两个 Tool Advisor 会导致**工具执行两次**——生产事故级 bug。

## 7. returnDirect 与 resultConverter（知道即可，第三章细讲）

- **returnDirect = true**：工具结果**不再回模型**，直接作为最终答案返回。适合「检索结果就是答案」的场景。多工具同轮时，**全部** returnDirect 才生效。
- **resultConverter**：自定义如何把 Java 返回值转成模型看到的字符串；默认 Jackson 序列化。
- **可选参数**：`@ToolParam(required = false)` 或参数上加 `@Nullable`（JSpecify），会进 JSON Schema 的 optional。

库存 Agent 默认 **不用** returnDirect——要让模型用数字组织管理层话术。

## 8. 和 1.x 的本质区别（口试必考）

| 维度 | Spring AI 1.x | Spring AI 2.0 |
|---|---|---|
| 循环位置 | 各 `ChatModel` 实现内部 | `ToolCallingAdvisor` |
| 组合记忆/审计 | 很难插进循环内部 | 调 order 即可 |
| 关自动执行 | `internalToolExecutionEnabled(false)` | 已删除；用配置或 `AdvisorParams` |
| 按名解析 Bean 工具 | `toolNames()` | 已删除 |
| 流式中间 tool 块 | `streamToolCallResponses`（且有设计缺陷） | 已删除；用 order>300 的观察 Advisor |

**DeepSeekChatModel** 在 2.0 支持 tool calling，走同一套 Advisor 循环。

## 9. 异常怎么处理（原则）

工具里**不要**把堆栈甩给 `ToolCallingManager`。

```java
try {
    return store.query(...);
} catch (Exception e) {
    log.warn("queryInventory failed sku={} wh={}", skuId, warehouseId, e);
    return "查询失败：仓位不存在或暂无权限，请勿编造数字。";
}
```

模型收到可读错误，可以转告用户；日志里保留完整异常供你排查。
