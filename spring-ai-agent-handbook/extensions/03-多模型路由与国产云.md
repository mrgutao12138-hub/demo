## 1. 为什么需要路由：不是一个模型干所有事

### 1.1 按任务类型

| 任务 | 特点 | 路由倾向 |
|---|---|---|
| -query 改写、关键词抽取 | 短、要快、要便宜 | 小模型 / flash 档 |
| 结构化抽取、分类 | 要稳、JSON 准 | 中等模型 + schema 校验 |
| 多步分析、归因、建议 | 要推理深度 | pro / reasoner 档 |
| 长文档摘要 | 上下文长 | 长窗口模型 |

同一套 `@Tool`，入口 ChatClient 不同，**后面的 Java 不动**。

### 1.2 按数据分级

- **公开制度 PDF**：可走任意合规云
- **含客户 PII 的工单**：仅本地或指定内网模型（见扩展 02）
- **跨境数据**：路由到区域合规 endpoint

分级标签应在 **进入 ChatClient 之前** 由 Java 判定，不要写进提示词让模型「自己决定敏不敏感」。

### 1.3 按成本

- 日均十万次轻量调用：flash + 缓存提示
- 管理层月报生成：少量 pro 调用
- 账单可观测（part-07）：每个路由打 `model.route=rewrite|analyze` 标签

### 1.4 按可用性 failover

云 API 会抖。路由层可做：

1. 主模型超时 → 备模型（需评测集证明备模型质量可接受）
2. 主区域不可用 → 读-only 降级（只返回检索片段 + 模板）
3. **绝不在 failover 时悄悄换模型而不记审计**——管理层追问「昨天答案怎么变了」时你要有据可查

## 2. Spring AI 2.0 多模型正确姿势

### 2.1 反模式：两个 starter 自动配置打架

```xml
<!-- 学习期不要这样干 -->
<dependency>spring-ai-starter-model-deepseek</dependency>
<dependency>spring-ai-starter-model-openai</dependency>
```

两个都引时，Spring Boot 可能注册两个 `ChatModel`，**默认注入哪一个变得不确定**。

**必须** 在 yml 指定：

```yaml
spring:
  ai:
    model:
      chat: deepseek
```

但这只解决「默认哪一个」——若你要 **同时** 用 DeepSeek 和 OpenAI 兼容网关，应走 **显式多 Bean**，而不是赌自动配置。

### 2.2 正模式：多个 ChatClient Bean + ChatClientBuilderConfigurer

Spring AI 2.0 提供 `ChatClientBuilderConfigurer`，把全局 customizer（观测、默认 Advisor 等）统一应用到多个 builder。

```java
@Configuration
public class ChatClientsConfig {

    @Bean
    @Primary
    ChatClient primaryChatClient(ChatClient.Builder builder) {
        return builder
                .defaultSystem("你是企业决策助手。")
                .build();
    }

    @Bean
    ChatClient rewriteChatClient(
            DeepSeekChatModel deepSeekChatModel,
            ChatClientBuilderConfigurer configurer) {
        ChatClient.Builder b = ChatClient.builder(deepSeekChatModel);
        configurer.configure(b);
        return b
                .defaultSystem("你只负责把用户问题改写成检索友好的短句，不回答问题。")
                .build();
    }

    @Bean
    ChatClient openAiCompatibleClient(
            OpenAiChatModel openAiChatModel,
            ChatClientBuilderConfigurer configurer) {
        ChatClient.Builder b = ChatClient.builder(openAiChatModel);
        configurer.configure(b);
        return b.build();
    }
}
```

要点：

- 每个 `ChatClient` **绑定明确的底层 `ChatModel` 实现**
- `@Primary` 标记默认注入的那一个（给不知道路由的 legacy 代码用）
- **Configurer 保证** 观测、Retry 等行为一致

### 2.3 路由服务（业务层）

```java
@Service
public class ModelRouter {

    private final ChatClient primary;
    private final ChatClient rewrite;
    private final ChatClient local; // 可选，Ollama

    public ModelRouter(
            @Qualifier("primaryChatClient") ChatClient primary,
            @Qualifier("rewriteChatClient") ChatClient rewrite,
            @Qualifier("localChatClient") ChatClient local) {
        this.primary = primary;
        this.rewrite = rewrite;
        this.local = local;
    }

    public ChatClient forRequest(ChatRequest req) {
        if (req.isSensitive()) {
            return local;
        }
        if (req.getTaskType() == TaskType.REWRITE) {
            return rewrite;
        }
        return primary;
    }
}
```

Controller 或 Agent 编排层 **只调 `forRequest`**，不散落 if-else。

### 2.4 ChatOptions 运行时覆盖

同一 `ChatClient` 也可 `.options(ChatOptions.builder().model("xxx").temperature(0.1).build())`，适合「同一厂商多档位」而非多厂商。

多厂商时，仍推荐 **多 ChatClient**，心智更清晰。

## 3. 国产云与 OpenAI 兼容端点

国内主流厂商（通义、智谱、文心、Moonshot、DeepSeek 自身、百川等）**多数提供 OpenAI 兼容的 HTTP 入口**。在 Spring AI 里，常见接入方式是：

- 引 `spring-ai-starter-model-openai`
- 改 `spring.ai.openai.base-url` 与 `chat.options.model`

### 3.1 示意配置（务必以厂商最新文档为准）

**通义（兼容模式示意）**

```yaml
spring:
  ai:
    openai:
      api-key: ${DASHSCOPE_API_KEY}
      base-url: https://dashscope.aliyuncs.com/compatible-mode/v1
      chat:
        options:
          model: qwen-max
```

**智谱（示意）**

```yaml
spring:
  ai:
    openai:
      api-key: ${ZHIPU_API_KEY}
      base-url: https://open.bigmodel.cn/api/paas/v4
      chat:
        options:
          model: glm-4
```

**Moonshot（示意）**

```yaml
spring:
  ai:
    openai:
      api-key: ${MOONSHOT_API_KEY}
      base-url: https://api.moonshot.cn/v1
      chat:
        options:
          model: moonshot-v1-8k
```

**文心、腾讯混元等** 同样模式：`base-url` + `model` 字符串 + 密钥。差异在鉴权头、路径是否严格 `/v1/chat/completions`，集成前用 curl 或 RestClient 先打一条最小请求。

### 3.2 DeepSeek 仍建议官方 starter

即使有 OpenAI 兼容 URL，**主线与生产默认**仍推荐 `spring-ai-starter-model-deepseek`，因 thinking、reasoning-effort 等配置与官方文档对齐。兼容模式适合「临时统一到 openai starter」的运维习惯，不是学习捷径。

### 3.3 多厂商 pom 策略

| 策略 | 做法 | 适用 |
|---|---|---|
| 单 openai starter + 换 base-url | 一个 `OpenAiChatModel` Bean，路由时换 options 或 properties | 厂商多、但同一 SDK 路径 |
| 多官方 starter | deepseek + openai + ollama 各一 Bean | 要原生配置项 |
| 抽象接口 + 工厂 | 自己封装 `LlmGateway` | 大型平台团队 |

讲义推荐中型团队：**2～3 个 ChatClient Bean**，不要超过五个，否则评测和维护爆炸。

## 4. spring.ai.model.chat：什么时候写、写什么

单 starter 工程通常 **不必写**。

以下情况 **必须写**：

- classpath 上有多个 chat model 自动配置
- 你想明确默认 `ChatClient.Builder` 绑定谁

```yaml
spring:
  ai:
    model:
      chat: deepseek
```

可选值取决于你引入了哪些 starter（如 `deepseek`、`openai`、`ollama`）。写错会导致启动失败或悄悄连错模型——**启动日志里确认注册的 ChatModel 实现类名**。

## 5. Embedding 与 RAG 在多模型下的分裂

路由不只 chat。RAG 常见三线：

```
文档入库：EmbeddingModel A  →  VectorStore
在线检索：同一 A（必须一致）
在线生成：ChatClient B / C（可按敏感级路由）
```

**换 embedding 模型必须重建索引。** 换 chat 模型不必重建索引，但要重新跑生成质量评测。

国产云有些同时提供 embedding 兼容接口，可用 openai starter 的 embedding 段；有些要单独 starter。part-05 原则不变：**向量与生成解耦配置，清晰文档化。**

## 6. 评测集决定能不能切

路由不是 `if (便宜) return 小模型` 这么随意。每一次「切模型」都是发布事件。

### 6.1 最小评测集结构

```text
eval/
  cases.jsonl        # 输入、期望工具、期望字段、数据分级标签
  rubric.md          # 人工打分标准
  baseline/          # DeepSeek pro 的基准结果
```

### 6.2 切换检查单

- [ ] 工具调用通过率 ≥ 基准 − 允许阈值（如 2%）
- [ ] 结构化输出 schema 失败率未上升
- [ ] RAG 答案 grounded 率未下降（抽检）
- [ ] P95 延迟在 SLA 内
- [ ] 单次成本下降是否符合预期
- [ ] 敏感路由 **从未** 误打到公有云（自动化测试 + 审计）

### 6.3 金丝雀

新模型先接 5% 流量或仅内部账号，对比日志与评测 diff，再全量。

**没有评测集就不要做多模型路由**——你会得到四个都不太行的模型而不是一个可靠的。

## 7. Failover 实现 sketch

```java
public String chatWithFailover(ChatClient primary, ChatClient secondary, String userText) {
    try {
        return primary.prompt().user(userText).call().content();
    } catch (Exception ex) {
        log.warn("Primary model failed, failover", ex);
        return secondary.prompt().user(userText).call().content();
    }
}
```

生产要加：

- 超时（Resilience4j / Spring Retry 与 `spring.ai.retry` 配合）
- 熔断（备模型也挂时快速失败）
- 审计字段：`primary_failed=true`

备模型 **质量必须事先评测**，failover 不是「随便找个能连上的」。

## 8. 合同、区域与密钥管理

- 每家国产云单独 **API Key**，分环境
- 合同里的 **QPS、日限额** 写进路由（超限排队或降级）
- 跨境路由注意 **数据 residency**；子公司用国际 endpoint 时单独 ChatClient
- 密钥轮换：支持双 key 窗口期，避免半夜改 yml

## 9. 与 Agent Advisor 链的关系

多个 `ChatClient` 可共享同一套 Advisor 定制：

```java
@Bean
ChatClient primaryChatClient(ChatClient.Builder builder,
        MessageChatMemoryAdvisor memoryAdvisor) {
    return builder
            .defaultAdvisors(memoryAdvisor)
            .build();
}
```

注意：**记忆是否共享**取决于你是否用同一 `CONVERSATION_ID` 和同一 repository。不同模型混用同一对话记忆时，模型脾气差异会导致体验怪异——可对「改写用 Client」禁用 memory。

`ToolCallingAdvisor` 通常随 `ChatClient.Builder` 自动配置；多 Client 时每个都能工具调用，但 **工具集可 deliberately 不同**（改写 Client 不挂业务 `@Tool`）。

## 11. 路由策略模式库：四种可落地的 Java 结构

### 11.1 静态路由（最简单）

```java
public ChatClient select(TaskType type) {
    return switch (type) {
        case REWRITE -> rewriteClient;
        case ANALYZE -> primaryClient;
        default -> primaryClient;
    };
}
```

适合：任务类型在 API 入参里 **显式声明**（如 `/api/rewrite` 与 `/api/analyze` 分开）。

### 11.2 基于内容分级标签

```java
public ChatClient select(DataClassification cls) {
    if (cls == DataClassification.SECRET) {
        return localClient;
    }
    if (cls == DataClassification.INTERNAL) {
        return domesticCloudClient;
    }
    return primaryClient;
}
```

`DataClassification` 由 **权限系统 + 数据字典** 在 Java 层判定，不交给 LLM。

### 11.3 成本感知路由

维护各模型「每千 token 单价」配置表，对 **非关键路径**（日志摘要、测试环境）强制走 flash 档：

```java
if (!request.isProduction() || request.isLowPriority()) {
    return flashClient;
}
```

### 11.4 链式 fallback

```java
for (ChatClient client : List.of(primary, secondary, tertiary)) {
    try {
        return client.prompt().user(text).call().content();
    } catch (Exception e) {
        log.warn("client failed: {}", client, e);
    }
}
throw new ServiceUnavailableException("all models down");
```

**禁止** 对管理层自动 fallback 到 **未评测** 的 tertiary，除非产品明确标注「降级模式」。

## 12. ChatClientBuilderConfigurer 深入：统一观测与默认 Advisor

```java
@Component
public class GlobalChatClientCustomizer implements ChatClientBuilderCustomizer {

    @Override
    public void customize(ChatClient.Builder builder) {
        builder
            .defaultAdvisors(new SimpleLoggerAdvisor())
            // 若有统一 memory，可在此谨慎添加；多 Client 共享 memory 时要评估
            ;
    }
}
```

`ChatClientBuilderConfigurer` 会把它应用到 **你手动 `ChatClient.builder(chatModel)` 的每个实例**，避免某个路由 Client 漏掉日志或 trace。

多模型时 Micrometer 标签建议：

```java
.tag("llm.vendor", "deepseek")
.tag("llm.route", "analyze")
```

账单分摊靠这两维就够财务问话。

## 13. 国产云接入踩坑实录（归纳）

| 坑 | 表现 | 规避 |
|---|---|---|
| base-url 双 `/v1` | 404 | 抄文档原串，用 curl 验证 |
| 模型名带日期后缀 | model not found | 控制台复制，不写记忆 |
| 工具调用非标准扩展字段 | 工具解析失败 | 升级到 Spring AI 2.0 最新补丁；向厂商提 ticket |
| 境内与境外 endpoint 混用 | 合规事故 | 配置中心分 profile |
| 免费额度与生产 key 混用 | 突然 429 | 分 key、分限额、告警 |

**通义、智谱、文心、Moonshot** 等文档都会变，讲义只教 **方法**：curl 最小请求 → 填入 openai starter → 上评测集。

## 15. 评测驱动路由：一个真实决策例子

假设评测结果：

- `qwen-max`：改写任务 BLEU 高、便宜，但工具调用 pass rate 比 DeepSeek 低 8%  
- `deepseek-v4-pro`：分析任务 pass rate 最高  
- `ollama qwen2.5:7b`：敏感摘要可读性够，工具 pass rate 仅 60%  

则路由策略：

- `REWRITE` → 通义（openai starter + base-url）  
- `ANALYZE` + 非敏感 → DeepSeek  
- `SUMMARIZE` + 敏感 → Ollama，**且禁用多工具链**  

若通义工具掉点不可接受，则 **改写也回 DeepSeek**，通义只用于非 Agent 的批量文案——**用数据说话，不用采购关系说话**。

## 16. 与 Spring Cloud Gateway、API 网关的关系

大厂有时在 **网关层** 做模型负载均衡，Java 应用只连 `https://llm-gw.corp/v1`。  
此时你仍用 `spring-ai-starter-model-openai`，`base-url` 指向内部网关；路由策略可能 **下沉到网关**（按 header 路由厂商）。

Agent 团队要分清：**网关路由** 与 **应用内 ModelRouter** 谁负责什么，避免双路由打架。

## 18. 课堂答疑

**问：两个 starter 必须写 `spring.ai.model.chat` 吗？**  
答：多个 chat 自动配置在 classpath 上时 **必须**；单 starter 通常可省略。

**问：能否运行时动态换 base-url？**  
答：可以自定义 `OpenAiChatModel` Bean，但生产更推荐 **配置中心刷新 + 重启金丝雀**，动态改 URL 易打错。

**问：路由要不要做成 AI 自己选模型？**  
答：默认 **不要**。让模型自选 = 不可审计 + 成本失控。小模型分类器可以，但要单独评测。

## 19. 端到端示例：DecisionFacade 统一入口

```java
@Service
public class DecisionFacade {

    private final ModelRouter router;
    private final InventoryQueryTools inventoryTools;

    public DecisionFacade(ModelRouter router, InventoryQueryTools inventoryTools) {
        this.router = router;
        this.inventoryTools = inventoryTools;
    }

    public String handle(DecisionRequest request) {
        ChatClient client = router.forRequest(request);

        return client.prompt()
                .advisors(a -> a.param(ChatMemory.CONVERSATION_ID, request.getConversationId()))
                .user(request.getQuestion())
                .tools(inventoryTools)  // 也可在 builder 上 defaultTools，按 Client 策略
                .call()
                .content();
    }
}
```

```java
public record DecisionRequest(
        String question,
        String conversationId,
        TaskType taskType,
        DataClassification classification,
        boolean production) {}
```

Controller 只构造 `DecisionRequest`，不散落 `if (通义)`。  
新厂商上线时，只改 `ModelRouter` 和配置，Controller **稳定**。

## 20. 通义 / 智谱 / 文心 / Moonshot：接入共性五步法

老师不替厂商维护文档，只教 **五步法**，换哪家都一样：

1. **开通** API Key，确认计费方式与限额。  
2. **curl** 最小 `chat/completions` 请求，确认 `base-url` 与 `model` 字符串。  
3. **pom** 引 `spring-ai-starter-model-openai`，yml 填 key、base-url、model。  
4. **十条** Hello World + **十条** 工具用例跑通。  
5. **评测集** 全量对比 DeepSeek 基线，开会决定是否切换或仅分流。

文心、腾讯混元等若路径非标准 `/v1/chat/completions`，仍可能通过 openai starter 的 `base-url` 拼完整路径解决；解决不了再考虑厂商专属 starter（查 Spring AI BOM 是否已收录）。

Moonshot 长文本场景常见，注意 **上下文窗口与单价** 同时评估——长上下文便宜模型有时更划算。

## 21. 成本路由的季度复盘模板

|---|---|---|---|---|---|---|
| deepseek-flash 改写 | 120万 | 180 | 90 | … | … | 98% |
| deepseek-pro 分析 | 8万 | 4200 | 800 | … | … | 96% |
| 通义 qwen-max | 5万 | … | … | … | … | 94% |
| ollama 本地敏感 | 2万 | … | … | 电费摊销 | … | 91% |

pass rate 低于基线 2% 的路由，**降权或下线**，不管采购合同是否还有余额。

## 22. spring.ai.model.chat 故障案例

**案例：** 同时引入 deepseek 与 openai starter，未写 `spring.ai.model.chat`，启动成功但工具调用偶发连错模型。

**现象：** 日志里 `ChatModel` 实现类名不确定；有时 `DeepSeekChatModel`，重启后变 `OpenAiChatModel`。

**修复：**

```yaml
spring:
  ai:
    model:
      chat: deepseek
```

并为多 Client 显式 `ChatClient.builder(具体ChatModel)`。

**教训：** 自动配置的「便利」在多 starter 时是 **坑**。

## 25. Bean 命名与 @Qualifier 约定（团队规范）

多 `ChatClient` 时命名混乱会导致注入灾难。推荐：

| Bean 方法名 | Qualifier | 用途 |
|---|---|---|
| `primaryChatClient` | `primaryChatClient` | 默认分析 |
| `rewriteChatClient` | `rewriteChatClient` | 检索 query 改写 |
| `domesticVendorChatClient` | `domesticVendorChatClient` | 集团采购国产云 |
| `localOllamaChatClient` | `localOllamaChatClient` | 敏感本地 |

**禁止** 用 `chatClient2` 这种名字。六个月后没人记得 2 是谁。

## 26. ChatClientBuilderConfigurer 源码级直觉（无需真读源码）

Configurer 在 Spring 容器启动时收集所有 `ChatClientBuilderCustomizer`，在创建每个 `ChatClient.Builder` 时依次 `customize(builder)`。  
因此你手动：

```java
ChatClient.builder(openAiChatModel)
```

之后调用 `configurer.configure(builder)`，等价于让 **手动 Bean 享受与自动配置 Bean 相同的观测、日志、默认 Advisor 策略**。

漏调 configure 的 Client 会在监控大盘上 **消失**——排障时先问「这个 Bean 有没有走 Configurer」。

## 27. 国产云「同一 openai starter、多 base-url」反模式

有人想动态换 `base-url` 实现「一个 Bean 走通义又走智谱」。  
**反模式原因：** 连接池、超时、审计标签、计费 key 都不同，挤在一个 `OpenAiChatModel` 里易错。

正模式：**一个厂商一个 ChatModel Bean**，路由在 `ModelRouter` 选择 Bean，而不是运行时改 URL。

## 30. 深度叙事：一家集团公司的模型矩阵（虚构合成）

集团信息中心三条政策同时落地：

1. **国资背景子公司**：核心经营文本不得出境，必须国产云或本地。  
2. **研发中心**：与海外协作，英文邮件允许走国际模型。  
3. **成本中心**：月度 LLM 账单不得超过预算，超标自动降级 flash 档。

技术团队落地：

- `ModelRouter` 读取请求里的 `subsidiaryId` 与 `DataClassification`。  
- 国资子公司 `SECRET` → Ollama；`INTERNAL` → 通义兼容 endpoint；`PUBLIC` → DeepSeek。  
- 研发中心 `ENGLISH` 标签 → OpenAI 兼容网关 `gpt-4o`。  
- 预算模块每日累加 token，接近阈值时 `CostAwareRouter` 把非关键任务切 flash。

Spring 配置上有 **四个 ChatClient Bean**，pom 上有 deepseek + openai + ollama 三个 starter，**必须** `spring.ai.model.chat=deepseek` 指定默认。  
评测集按子公司抽样，**任何路由不得低于基线 pass rate 2%**。

这个合成案例涵盖本篇 80% 知识点。你不必第一天实现它，但 part-09 架构评审时应能画出类似方块图。

## 31. Failover 与路由的区别（易混）

- **路由（Routing）**：正常路径下 **主动选择** 最合适模型。  
- **Failover（故障转移）**：主模型 **失败之后** 才用备模型。

不要把 failover 当日常省钱手段；备模型未评测就 failover，等于把生产当赌场。

## 34. 路由表配置外置化示例（YAML）

```yaml
app:
  llm:
    routes:
      - id: rewrite
        match:
          task-type: REWRITE
        client: rewriteChatClient
      - id: secret-local
        match:
          classification: SECRET
        client: localOllamaChatClient
      - id: default-analyze
        match: {}
        client: primaryChatClient
```

```java
@ConfigurationProperties(prefix = "app.llm")
public record LlmRouteProperties(List<RouteRule> routes) {}

public ChatClient resolve(DecisionRequest req, Map<String, ChatClient> clients) {
    for (RouteRule rule : properties.routes()) {
        if (rule.matches(req)) {
            return clients.get(rule.client());
        }
    }
    return clients.get("primaryChatClient");
}
```

规则外置后，产品改路由不必改 Java if-else，但仍需 **评测回归** 才能发布配置。

## 38. Moonshot 长文档与路由

Moonshot 常打「长上下文」卖点。若你的 Agent 需要 **单次塞入整本制度 PDF**（不推荐，应 RAG），路由可设 `LONG_CONTEXT` 任务类型走 Moonshot Client。

## 39. 文心一言等「非标准路径」时的策略

若某厂商兼容模式不成熟，Spring AI BOM 可能提供 **厂商专属 starter**（如 `spring-ai-starter-model-*`）。

## 42. 收束：多模型不是炫技，是合同与评测的乘积

讲义用整篇扩展 03 想纠正一个心态：**多模型路由不是「我会配五个 starter」**，而是：

1. 合同与合规画出 **允许集合**；  
2. 评测集在允许集合里挑 **最优**；  
3. `ChatClientBuilderConfigurer` 与 `ModelRouter` 让切换 **可维护**；  
4. 监控与 on-call 让切换 **可运营**。

四件事缺一，「多模型」只是 pom 里一坨依赖。part-09 答辩时，评委更想听第 1、2、4 点，而不是背厂商名字。你把这张逻辑图讲顺，扩展 03 就算读透。

## 49. 什么时候才应该用 · 和主线如何衔接

### 什么时候才应该用

- part-05 RAG 与 part-04 工具循环 **已过关**
- 存在 **≥2 个** 合规可用的模型来源（合同、区域、敏感级）
