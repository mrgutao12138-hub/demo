# 01 · 生成式 AI 核心概念全解

> 同学们，这一章是整个 part-01 的地基。  
> 我不教你背公式，我要你离开教室后，能跟架构师、跟业务总监、跟未来的自己解释：**大模型不是在「查答案」，而是在「接龙」**——而接龙这件事，处处是概率。

---

## 1. 生成式 AI 到底是什么（给 Java 工程师的版）

### 1.1 它不是数据库，也不是搜索引擎

你熟悉的系统里：

- **数据库**：存的是确定的事实；`SELECT` 返回的是行，同一 SQL 同一时刻结果一致（在事务隔离级别内）。  
- **搜索引擎**：倒排索引 + 排序；关键词匹配，有明确的召回逻辑。  
- **规则引擎**：if-else 或 DSL，路径可追溯。

**生成式大语言模型（LLM）** 做的是另一件事：  
给定一段已出现的文本（prompt + 历史），预测**下一个最可能出现的 token**（可以粗理解为「词片段」），然后把这个 token 接上去，再预测再一个……直到满足停止条件。

所以它的本质是：**条件概率下的文本续写**。

用你熟悉的类比：

```text
// 这不是真代码，是心智模型
String next = model.predict(上下文);  // 每次带随机性（受温度等影响）
回答 += next;
while (!应该停止(回答)) { ... }
```

【易混】学员常说：「我把库存表贴进 prompt，它不就是数据库了吗？」——不是。模型没有执行 `JOIN`，它只是在**模仿**「像库存汇报一样的文字」。数字对不对，要靠你后面的工具与护栏，不能靠「贴表」。

### 1.2 「生成」和「理解」

日常我们说模型「理解」了问题。工程上更准确的说法是：  
模型把输入编码成内部表示，再解码成输出 token 序列。对你有用的结论是：

- 它**没有**业务系统的 ground truth。  
- 它**擅长**语言模式、归纳、类比、按格式输出。  
- 它**不保证**事实正确，尤其涉及具体数字、日期、人名、条款编号。

决策 Agent 的设计原则由此而来：**让模型做它擅长的（选工具、写解释、套格式），让 Java 做它擅长的（查准数、验权限、记审计）。**

## 2. Token：钱的单位，也是长度的单位

### 2.1 什么是 token

模型不直接按「汉字个数」计费，而是按 **token**：

- 中文往往一个字或多个字对应一个 token，因分词器而异。  
- 英文一个单词可能拆成多个 token。  
- 标点、空格、JSON 花括号都占 token。

对你意味着三件事：

1. **账单**：输入 + 输出 token 数 × 单价。  
2. **上下文窗口**：模型一次能「看见」的 token 上限（输入+输出+工具消息合计）。  
3. **截断**：超了就要裁历史、裁 RAG、裁工具返回——裁错了就是**上下文污染**或**丢关键依据**。

【建议】学习期就在笔记本记一条：每次请求事后看 usage 里的 token 数，培养成本直觉。

### 2.2 上下文窗口（context window）

上下文窗口 = 模型单次能处理的最大 token 数。

里面通常包括：

- 系统提示  
- 历史对话  
- 当前用户消息  
- RAG 塞进去的文档片段  
- 工具调用的请求与返回  
- 模型自己的输出（含 thinking，若 API 返回且你选择保留）

窗口越大，能带的资料越多，但**也更贵、延迟更高、污染面更大**。  
企业决策场景不是「尽可能塞满」，而是「只塞决策必需的」。

## 3. 采样参数：温度、Top-P、Max-Tokens、Stop

这一节是本周重点，请逐字读懂。

### 3.1 温度（temperature）

**定义**：在选下一个 token 时，对概率分布做「锐化」或「抹平」。

- **温度 → 0**（如 0.1）：几乎总选概率最高的 token，输出**稳定、重复性高**。  
- **温度 → 1 或更高**：低概率 token 也有机会被选中，输出**多样、活泼、也更胡编**。

直觉类比：

- 温度低 = 老员工按 SOP 填表，字段几乎不变。  
- 温度高 = 实习生 brainstorm，同题每次说法不同。

**决策场景建议：0.1～0.3**

原因拆开说：

| 维度 | 低温（0.1～0.3） | 高温（0.7～1.0+） |
|------|------------------|-------------------|
| 数字表述 | 更倾向重复工具返回的精确值 | 更爱「约」「大概」，易改写数字 |
| 工具选择 | 更稳定，利于评测对比 | 同问不同次可能选不同工具 |
| 合规表述 | 更贴系统提示里的红线 | 更爱发挥，易越红线 |
| 创意文案 | 偏枯燥 | 适合写邮件、口号（非本期重点） |

技术选型说明书里 DeepSeek 决策默认 `temperature: 0.2`，就在这个区间。  
【红线】不要用「温度 1.0 试试能不能更聪明」——决策系统要的是**可复现**，不是文采。

Spring AI 配置示例（概念周先认识字段）：

```yaml
spring:
  ai:
    deepseek:
      chat:
        temperature: 0.2
```

### 3.2 Top-P（nucleus sampling）

**定义**：只从累计概率达到 P 的最小 token 集合里采样。

- **top-p = 0.1**：只在「最可能的那一小撮」里选，很保守。  
- **top-p = 0.95**：候选面大，多样性强。

温度和 top-p **通常只调一个**，都调容易行为难预测。  
企业决策 Agent：**固定温度 0.1～0.3，top-p 用默认或略保守**，把精力放在工具和提示词上。

【易混】「温度 0.2 + top-p 0.95」不等于「又稳又活」，往往是「稳不住」。

### 3.3 Max-Tokens（最大输出长度）

**定义**：限制模型**单次生成**最多输出多少 token（不含输入）。

解决什么问题：

1. **成本封顶**：避免模型长篇大论烧光预算。  
2. **延迟可控**：管理层要的是一页纸，不是论文。  
3. **格式约束**：配合「五段式输出」，max-tokens 设合理上限，逼它简洁。

设太小的问题：JSON 或表格被截断，解析失败。  
设太大的问题：模型爱加无关背景，增加幻觉面。

实践建议（决策报告类）：

- 纯结论 + 五段结构：**512～1024** 往往够（视是否含 thinking 而定）。  
- 带大段工具结果时，工具返回应在 Java 侧**摘要后再进上下文**，而不是靠 max-tokens 硬撑。

```yaml
spring:
  ai:
    deepseek:
      chat:
        max-tokens: 1024
```

### 3.4 Stop Sequences（停止序列）

**定义**：模型生成到**指定字符串**时立刻停止，不再继续 token。

用途：

- 防止模型在 JSON 后面继续「聊天」。  
- 多阶段生成时截断到某一节。  
- 与结构化输出配合（但要小心 stop 出现在正文里的误触）。

示例（概念）：

```yaml
spring:
  ai:
    deepseek:
      chat:
        stop:
          - "</report>"
          - "\n\n用户："
```

【易混】Stop 是**生成侧**截断，不是「告诉模型别说什么」。红线仍要靠系统提示和输出校验。

## 4. 幻觉（Hallucination）

### 4.1 定义

**幻觉**：模型用非常自信的语气，说出**不符合事实**的内容。

常见形态：

- 编造库存数量、订单号、法规条款。  
- 编造「刚才工具返回了 XXX」（其实没调工具）。  
- 把 RAG 里两段矛盾文档「揉」成一个看似合理的结论。  
- 编造引用来源：「根据 2023 年内部审计报告……」（报告不存在）。

### 4.2 为什么一定会发生（不是 bug，是机制）

因为它是概率续写，训练数据里大量文本都是「像真的一样写」。  
在缺少外部事实时，它仍会**补全一个看起来合理的句子**——这就是幻觉的温床。

【易混】「换成更强的模型就没有幻觉了」——错。只能**降低频率**，不能消灭。工程上靠工具、RAG、护栏、评测，不靠赌模型。

### 4.3 决策系统里怎么对付（预告，07 章展开）

1. **数字走工具**：凡可数、可聚合，必须 Java 查。  
2. **口径走 RAG**：制度条文检索带来，强制标注来源。  
3. **输出契约**：没数据就写「无数据」，不许估算。  
4. **评测集**：幻觉案例进回归测试。  
5. **低温 + 固定格式**：减少发挥空间。

---

## 5. 上下文污染（Context Pollution）

### 5.1 定义

**上下文污染**：无关、错误、过时或恶意的内容进入 prompt，**误导**模型后续推理与输出。

来源包括：

- 塞了太长的历史对话，早期错误结论被反复引用。  
- RAG 召回了相似但错误的段落（同名物料、不同仓库）。  
- 用户在前几轮诱导：「你就当库存是 10000」。  
- 把整份 Excel 贴进会话，关键信号被淹没。  
- 工具返回了未脱敏的脏数据，模型当成事实复述。

### 5.2 业务例子

场景：华东仓补货决策。

- 第 1 轮用户口误：「按华北仓算。」  
- 助手若没澄清，第 3 轮仍带着「华北」上下文。  
- RAG 同时召回华东与华北两份 SOP，模型「平均」成错误建议。

对策（概念）：

- **会话摘要**要由 Java 控制，不能无脑全历史塞回。  
- **元数据过滤**：RAG 带 `warehouse=华东`。  
- **工具参数**由用户意图解析 + 确认，不靠模型记错仓库。  
- **定期清空**或压缩无关轮次。

## 6. DeepSeek：Thinking、Reasoning-Effort 与多轮行为

### 6.1 思考过程 vs 最终答案

DeepSeek 部分型号支持 **thinking**（思考模式）和 **reasoning-effort**（推理力度）。

你可以把它理解成：

| 部分 | 是什么 | 给谁看 |
|------|--------|--------|
| **思考过程** | 模型内部链式推理、草稿、自我纠错 | 可选展示给「想看推理过程」的管理层；默认产品 UI 可折叠 |
| **最终答案** | 面向用户的结论性回复 | 必须进审计、进记忆摘要、进下一轮上下文 |

【易混】思考过程**不是**更可靠的依据。它也可能错，只是错在「草稿区」。**数字仍只信工具。**

配置概念（与选型说明书一致）：

```yaml
spring:
  ai:
    deepseek:
      chat:
        model: deepseek-v4-pro
        temperature: 0.2
        thinking:
          type: enabled
        reasoning-effort: high
```

- **reasoning-effort: low / medium / high**：越高，越愿意花 token 做推理，适合归因、多约束权衡；简单查数用 low 或关掉 thinking 更省。  
- 学习期：**同一问题用不同 effort 各测一次**，看质量与成本的 trade-off，记入笔记。

### 6.2 多轮对话时 CoT 通常不回灌

**重要行为（按 DeepSeek API 常见语义描述）**：

- 单轮请求里，thinking 内容可能在响应结构中单独字段返回。  
- **进入下一轮历史时，通常只保留「最终答案」角色消息 + 工具消息**，而不是把整段思考全文当作 assistant 历史再发回去。

对你设计 Agent 的含义：

1. **不要假设**「上一轮思考」会自动帮下一轮推理——往往不会。  
2. 若业务真要跨轮推理链，应由 **Java 侧会话摘要** 或 **结构化状态**（如「已确认仓库=华东」）显式传递。  
3. **省 token**：思考全文进历史又贵又容易污染。  
4. 审计日志可以**另存** thinking 全文到对象存储，与对话上下文分离。

伪代码（会话写入逻辑）：

```java
// 概念示意：写入 ChatMemory 的应是「干净答案」
void onAssistantTurn(DeepSeekResponse resp) {
    auditLog.saveThinking(resp.getThinking()); // 可选，审计用
    memory.add(new AssistantMessage(resp.getFinalContent())); // 不进 thinking 全文
}
```

## 7. 生成式 AI 能力边界（决策场景清单）

**适合做：**

- 意图理解、追问澄清  
- 工具选择与参数填充（需 schema 约束）  
- 把工具返回整理成五段式报告  
- 风险措辞、建议措辞（在依据真实的前提下）

**不适合单独做：**

- 库存、金额、交期的**权威数值**  
- 未经检索的法规原文引用  
- 写库、下单、改权限  
- 「全公司知识一问全答」

## 12. 章节小结

生成式 AI 是**概率续写器**。  
你作为 Java 工程师，手里有三把旋钮：**温度（稳不稳）、max-tokens（长不长）、stop（何时停）**；  
还有两道红线：**幻觉要靠工具与评测治，污染要靠记忆与 RAG 设计防**；  
用 DeepSeek 时，分清**思考草稿**和**最终答案**，多轮对话别指望 CoT 自动传承。

## 13. 深度专题：参数之间如何「打架」

### 13.1 温度与 top-p 同时调高

有些学员把「creative 写作」教程照搬：`temperature=0.9, top-p=0.95`。在决策场景会出现：

- 同一问题周一和周二工具选择不一致，评测无法对比；  
- 数字被「润色」：`1240` → `约一千二百`；  
- 风险节消失，模型过于自信。

**企业默认配方**：`temperature=0.2`，top-p 用提供商默认；除非评测证明需要动 top-p。

### 13.2 max-tokens 与工具返回长度的博弈

假设 max-tokens=512，但工具返回了 3000 token 的 JSON 在历史里，模型写五段式时可能被截断，出现：

```text
## 风险
- 库存快照延迟
- 在途订单未
```

Java 侧正确姿势：**工具结果进上下文前先摘要**（关键字段 + 行数 + asOf），而不是无限增大 max-tokens。

### 13.3 stop 与 JSON 结尾

若 stop 设为 `}`，可能把合法 JSON 拦腰截断。结构化输出优先用 schema 校验 + max-tokens，stop 用于明确分隔符如 `<!--END-->`。

## 14. Token 经济学（给会算账的工程师）

### 14.1 一次请求花在哪

```text
输入 token = 系统提示 + 历史 + RAG 块 + 工具定义 schema + 用户问题 + 工具结果
输出 token = thinking（若有）+ 最终答案
```

学习期养成习惯：记录典型问题的 input/output 分布。你会发现 **工具 schema 和历史** 往往比用户一句话贵得多。

### 14.2 省钱不等于删红线

有人为省 token 删系统提示红线——幻觉一升，管理层信任归零，省下的钱不够赔。

正确省钱：

- RAG topK 从 8 降到 4（用评测验证）；  
- 历史用摘要 + 结构化状态；  
- 简单意图用 flash 模型；  
- 工具 description 精炼但不删「何时必须调用」。

## 15. DeepSeek 型号与场景（概念对齐）

与技术选型说明书一致，学习期记住三档即可：

| 场景 | 型号倾向 | 温度 | thinking |
|------|----------|------|----------|
| 参数实验、Router 分类 | flash | 0.1～0.2 | 关 |
| 日常管理问答 | flash / chat | 0.2 | 视复杂度 |
| 归因、多约束权衡 | pro / reasoner | 0.1～0.3 | 开，effort medium～high |

**reasoning-effort** 不是「质量开关」的无限旋钮：effort 越高，延迟和 token 通常越高。用评测集找拐点，不要全局 high。

### 15.1 thinking 内容在产品里怎么展示

三种产品策略：

1. **默认隐藏**：管理层只看五段式；thinking 进审计。  
2. **可展开**：「查看分析过程」折叠面板，标注「非正式依据」。  
3. **禁止展示**：金融/强合规场景，防用户把草稿当审批依据。

无论哪种，**写入 ChatMemory 的仍是最终答案**（01 章已强调）。

## 16. 工作示例：同一问题的三次采样

## 17. 上下文窗口截断时发生什么

当输入超过窗口上限，框架或 API 可能：

- 从最旧的消息开始丢（危险：丢用户确认过的仓库）；  
- 截断 RAG 块（危险：丢关键条款）；  
- 直接报错（最安全，但体验差）。

工程策略：

1. **监控 token 预算**，快满时主动摘要历史；  
2. **RAG 动态减 K**；  
3. **工具 schema 用 ToolSearch 按需披露**（后期）；  
4. 永远不要让截断静默发生而无日志。

## 18. 与 Java 异常体系的类比

| LLM 现象 | Java 类比 |
|----------|-----------|
| 幻觉 | 未校验的外部 API 返回被当成 truth |
| 上下文污染 | ThreadLocal 没清，上次请求状态泄漏 |
| 温度 | Random 种子不固定，单测偶发失败 |
| max-tokens | `readLine()` 只读前 N 字节导致 JSON 残缺 |
| stop | 读到分隔符就 break，可能 break 太早 |

这样类比的目的：让你用**工程思维**而不是「AI 玄学」排障。

## 22. 从 Chat Completions 到「一个决策」的 token 账（虚构测算）

假设：

- 系统提示 800 token  
- 工具 schema 1200 token  
- 历史 1500 token  
- RAG 4 块共 2000 token  
- 用户问 50 token  
- 工具结果摘要 400 token  
- 输出 600 token  

合计输入约 5950，输出 600。若窗口 8k，已很紧。  
说明：**不是模型笨，是窗口被占满**，应减 RAG K 或摘要历史。

## 23. DeepSeek 多轮消息结构（概念）

```text
messages: [
  { role: system, content: "..." },
  { role: user, content: "华东 A123？" },
  { role: assistant, tool_calls: [...] },   // 无 thinking 在 content
  { role: tool, content: "{qty:1240}" },
  { role: assistant, content: "## 结论\n..." }  // 仅最终五段
]
```

下一轮用户再问时，**不应**出现上一轮的 `reasoning_content` 字段内容。若你自己拼接消息，检查 SDK 默认行为，避免双倍 thinking 账单。

## 25. 综合案例：没有工具时会发生什么（全程推演）

**用户**：「华东仓 A123 现在有多少库存？」

**场景 A · 纯大模型（错误示范）**  
模型可能回答：「根据一般情况，华东仓 A123 库存大约在千余件左右。」——**幻觉 + 不可审计**。

**场景 B · 低温 + 红线提示但仍无工具**  
模型可能回答：「我无法访问实时库存，请提供数据或联系 IT。」——**诚实但无用**。

**场景 C · 低温 + 工具 + 强制调用**  
模型调用 `queryInventory` → 得到 `1240` → 回答数字节写 `1240（来源：queryInventory）`——**唯一可上线路径**。

请把三场景写进你的笔记，答辩时必讲。
