# 04 · RAG 检索增强生成

> 同学们，RAG 解决一个问题：**模型没背下你们公司的制度，但回答又要符合口径。**  
> 它不是让模型「更聪明」，而是让模型「考前能翻小抄」——小抄还得是你控制的、带来源的、可过滤的。

---

## 1. 为什么需要 RAG

### 1.1 纯提示词的极限

把 200 页《库存管理制度》贴进系统提示：

- 超上下文、超预算；  
- 模型抓不住第 7.3.2 款；  
- 更新制度要改提示词、重新发版；  
- 多租户时每家制度不同，无法一份 prompt 打天下。

### 1.2 RAG 在做什么

**RAG（Retrieval-Augmented Generation）**：

1. **离线**：把文档切分、向量化、存入向量库。  
2. **在线**：用户提问 → 把问题向量化 → 检索最相关片段 → 塞进 prompt → 模型生成答案。

```text
用户问题 ──► Embedding ──► VectorStore 相似度搜索 ──► TopK 片段
                                                      │
                                                      ▼
                                            与问题一起发给 DeepSeek
                                                      │
                                                      ▼
                                            答案（须引用片段来源）
```

Spring AI 2.0 主推 **RetrievalAugmentationAdvisor**（`spring-ai-rag` 模块）。本周只讲原理，实现放 part-05。

### 1.3 RAG 不解决什么

- **不替代工具查实时数字**：制度里写「安全库存由系统计算」，具体数字仍要 `queryInventory`。  
- **不保证检索一定对**：召回了错段，模型仍会一本正经胡说。  
- **不是知识库万能入口**：脏文档、过期 PDF 会毒害答案。

---

## 2. Embedding（嵌入向量）

### 2.1 是什么

**Embedding**：把一段文本映射成一个高维向量（一串浮点数），使得**语义相近**的文本，向量距离**更近**。

```text
「华东仓补货流程」  →  [0.12, -0.05, ...]
「华南仓补货审批」  →  [0.11, -0.04, ...]   // 较近
「食堂菜单」        →  [-0.8, 0.3, ...]      // 较远
```

### 2.2 与 DeepSeek 的关系

【重要】DeepSeek 对话 API **不提供**与主线配套的官方 embedding 服务。  
你的 RAG 必须**另选 embedding 模型**，例如：

- 本地 `spring-ai-starter-model-transformers`  
- 其它云 embedding 服务  
- 内网部署的开源向量模型

这意味着架构上是**两个模型**：

| 用途 | 模型 |
|------|------|
| 生成回答、选工具 | DeepSeek Chat |
| 文档与问题的语义匹配 | Embedding 模型 |

【易混】不要用 Chat 模型「假装」做向量——成本高、效果差、不稳定。

### 2.3 维度与一致性

- 索引时用哪个 embedding 模型，查询时必须**同一个**。  
- 换 embedding 模型通常要**重建索引**。

## 3. 文档切分（Chunking）

### 3.1 为什么要切

向量库按「块」存，不是整本书一条。  
切太大：噪声多，相似度被稀释。  
切太小：语义残缺，「第 7 条」和「第 7 条的例外」分了家。

### 3.2 常见策略

| 策略 | 说明 | 适用 |
|------|------|------|
| 固定长度 | 每 500～1000 字一块，可重叠 50～100 字 | 通用制度 |
| 结构切分 | 按章/节/条款 | 规章、SOP |
| 表格单独 | 表格转 Markdown 或 JSON 再切 | 口径表 |
| 元数据挂载 | 每块带 `docId、version、warehouse` | 企业必做 |

重叠（overlap）的作用：避免一句话被拦腰切断后两边都搜不到。

### 3.3 决策类文档怎么切

- 《安全库存管理规定》：按「条款」切，元数据带 `effectiveDate`。  
- 《仓库命名与编码对照》：一表一块，别和 narrative 混切。  
- FAQ：一问一答一块。

## 4. TopK 与相似度

### 4.1 TopK

**TopK**：检索时取相似度最高的 **K** 条片段（如 K=3～8）。

- K 太小：漏关键条款。  
- K 太大：上下文污染，模型「平均」矛盾内容。

决策场景起步：**K=4～6**，用评测集调。

### 4.2 相似度（Similarity）

常见度量：

- **余弦相似度**（cosine）：看方向，不看长度，最常用。  
- **点积**、**欧氏距离**：依向量库实现而定。

返回结果通常带 `score`：

```text
chunk-华东-补货-003  score=0.82
chunk-华北-补货-001  score=0.79   // 仓库错了但词像，危险！
```

因此：**相似度只是候选，不是真理**——必须配合元数据过滤。

### 4.3 相似度阈值

低于阈值（如 0.65）的片段**不要塞进 prompt**，宁可回答「制度库未命中，请人工查阅」。  
否则模型会硬编「根据相关规定……」。

---

## 5. 元数据过滤（Metadata Filter）

### 5.1 为什么必须有

用户问华东仓，检索却命中华北仓同名流程——**纯向量救不了**，要靠过滤：

```text
filter: warehouse = "华东" AND docType = "SOP" AND status = "effective"
```

### 5.2 常见元数据字段

- `tenantId` / `orgId`  
- `warehouse` / `plant`  
- `docType`：制度 / 口径 / FAQ  
- `version` / `effectiveDate` / `expiredDate`  
- `classification`：内部 / 秘密（秘密文档慎入云 RAG）

### 5.3 与 Java 权限联动

检索前把**当前用户可看的 filter** 从鉴权服务取出，拼进 VectorStore 查询。  
不要指望模型自觉「不该看华北」。

## 6. RAG 在 Advisor 链中的位置

```text
请求进入
  → MessageChatMemoryAdvisor（历史）
  → RetrievalAugmentationAdvisor（检索片段注入）
  → ToolCallingAdvisor（可能要查数）
  → 模型生成
```

顺序可有微调，但原则：

- **先确定检索范围**（元数据）；  
- **再查实时数字**（工具）；  
- **最后生成**（低温 + 来源标注）。

注入 prompt 的 RAG 块建议格式：

```text
【检索文档 1】
来源：库存管理制度 v3.2 / 第 7.3 条 / chunkId=inv-7-3-华东
正文：......

【检索文档 2】
...
```

系统提示要求：依据节必须引用上述 `chunkId` 或文档标题。

## 7. 数字走工具，口径走 RAG（再讲透）

| 类型 | 例子 | 走哪 | 原因 |
|------|------|------|------|
| 实时库存 | 1240 件 | 工具 | 秒级变化，文档里是错的 |
| 安全库存公式 | 「按 7 日日均 × 系数」 | RAG | 解释规则 |
| 系数具体值 1.5 | 若在 ERP 配置 | 工具 | 配置是数据 |
| 系数含义 | 「旺季上调」 | RAG | 语义口径 |
| 审批权限 | 「总监以上」 | RAG | 制度条文 |
| 某人是否总监 | 组织架构 | 工具/组织 API | 人事数据 |

【口头验收高频题】「安全库存 500 件」——若来自昨晚测算结果，必须工具；若来自制度原文举例，须标注「制度示例非实时」。

## 8. RAG 失败模式与对策

| 失败 | 现象 | 对策 |
|------|------|------|
| 召回错仓 | 华北 SOP 混入 | 元数据 filter |
| 过期制度 | 旧版「15 日审批」 | version + effectiveDate |
| 片段断章 | 只要「除外情况」上半句 | 结构切分 + overlap |
| 相似但无关 | 食堂「补货」菜单 | docType 过滤 |
| 无命中硬答 | 胡编条款 | 阈值 + 拒答模板 |
| 注入攻击 | 文档里写「忽略以上规则」 | 07 章：文档注入防护 |

## 9. 索引更新与治理

- 制度变更 → 触发重新索引（或增量）。  
- 索引任务与线上查询分离。  
- 保留 `chunkId → 原文偏移` 便于审计。  
- 演示环境与生产索引分库。

## 10. 概念周伪代码：检索流程

```java
// 概念示意
List<Document> retrieve(String question, UserContext ctx) {
    float[] queryVec = embeddingModel.embed(question);
    Filter filter = Filter.and(
        Filter.eq("tenantId", ctx.tenantId()),
        Filter.in("warehouse", ctx.allowedWarehouses()),
        Filter.eq("status", "effective")
    );
    return vectorStore.similaritySearch(
        SearchRequest.query(queryVec)
            .topK(5)
            .similarityThreshold(0.68)
            .filter(filter)
    );
}
```

## 13. 【易混】

| 易混 | 正解 |
|------|------|
| RAG = 知识库全文搜索 | RAG 是语义向量检索 + 生成，不是关键词 grep |
| 检索分数高 = 答案对 | 只表示像，还要过滤、阈值、来源约束 |
| RAG 能查实时库存 | 实时数字必须工具 |
| 把对话历史当 RAG | 记忆是记忆，知识库是知识库（05 章） |
| 切得越碎越好 | 过碎丢语义，过大丢精度 |

## 14. 章节小结

RAG 给企业 Agent 一张**受控的「小抄」**：

- **Embedding** 做语义匹配；  
- **切分 + 元数据** 决定召回质量；  
- **TopK + 阈值 + 过滤** 防错召；  
- **口径走 RAG，数字走工具**，两者不可互换。

下一章：`05-记忆与会话.md`——对话记忆不是第二套知识库。

## 15. 索引流水线（Ingestion Pipeline）五步

```text
原始文档（PDF/Word/Markdown）
    → 1. 清洗（去页眉页脚、乱码）
    → 2. 结构化（标题层级、表格抽取）
    → 3. 切分（chunk + overlap）
    → 4. 元数据标注（tenant、warehouse、version、effectiveDate）
    → 5. Embedding + 写入 VectorStore
```

任何一步偷懒都会在在线阶段爆炸。最常见偷懒：PDF 不清洗，页码进向量，检索全是「第 12 页」。

---

## 16. 混合检索：向量 + 关键词

纯向量对「物料编码 A123」「单号 PO-2026-001」类**精确符号**有时不如关键词。

工程常见：

```text
候选 = 向量 TopK'（如 20）
     ∩ 或 ∪ BM25 关键词 TopK'
     → 重排序 → 取最终 TopK（如 5）
```

Spring AI 生态可用额外检索组件或自写；第一版若制度文档为主，**元数据过滤 + 向量** 往往够用，混合检索放优化项。

---

## 17. 重排序（Re-rank）

用交叉编码器或小型 rerank 模型对初筛 chunk 再打分，能显著降低「词像但义不对」。

成本：多一次模型调用。决策高影响场景（如合规认定）值得做；日常库存口径可先不做。

---

## 18. 切分实战：一条制度条款怎么切

原文（虚构）：

```text
第 7.3 条 华东仓 A 类物料安全库存不得低于 7 日日均消耗的 1.5 倍。
第 7.3.1 条 旺季（每年 6～8 月）系数上调至 2.0 倍，以系统参数为准。
```

推荐两块：

| chunkId | 内容 | 元数据 |
|---------|------|--------|
| inv-7-3 | 第 7.3 条全文 | warehouse=华东, class=A |
| inv-7-3-1 | 第 7.3.1 全文 | warehouse=华东, season=peak |

用户问「旺季系数」时应命中 7.3.1，而非只命中 7.3 的上半句。

## 19. RAG 评测用例设计

与 07 章联动，RAG 专项用例：

| ID | 问题 | 应命中 chunk | 不应命中 |
|----|------|--------------|----------|
| R-01 | 华东 A 类安全库存公式 | inv-7-3 | 华北同类 |
| R-02 | 旺季系数 | inv-7-3-1 | inv-7-3 单独 |
| R-03 | 食堂管理规定 | （无或拒答） | inv-7-3 |

每次改切块或 embedding 模型，跑 R-xx 系列。

## 20. 用户问题与检索 query 改写

口语「华东那边 A 类货还要备多少」向量检索可能偏。可在 Advisor 内增加**查询改写**（低温 LLM 或规则）：

```text
检索 query = 「华东仓 A 类物料 安全库存 规定」
```

改写错了会带偏召回，需评测。第一版可用简单规则：补全「仓」「物料等级」同义词。

---

## 21. 多租户 RAG 隔离

```text
VectorStore 物理隔离（每租户一库）  ← 最强
或
逻辑隔离（每条 metadata.tenantId + 强制 filter）  ← 常见
```

【红线】绝不做「全公司一个索引靠模型自觉不分租户」。

---

## 22. RAG 与工具冲突时的产品话术

系统提示写死：

```text
当检索制度与实时工具数据冲突时，以工具数据为准描述「当前系统状态」；
以制度描述「规则口径」；在风险节说明两者差异，不得自行调和为单一数字。
```

例：制度写系数 1.5，系统参数已是 2.0 → 数字节报 2.0（工具），依据节引制度并注「参数已按旺季上调」。

## 23. 成本：Embedding 与存储

- 索引阶段一次性 embedding 费用 + 向量库存储；  
- 查询阶段每问一次 query embedding；  
- 文档频繁变更要算重索引成本。

制度库相对稳定，比「把日志当 RAG」便宜得多。

```text
                ↑
用户问 → [query embed] → [filter+topK] → [注入 prompt] → [DeepSeek]
                              ↑
                        [工具实时数]
```

标注：哪些箭头只能走 Java，哪些可以走模型。

## 25. Embedding 质量对 RAG 的影响

同一 chunk，用不同 embedding 模型，召回率可差 20% 以上。  
选型看：

- 中文制度语料表现  
- 维度与向量库兼容  
- 本地 vs 云端（出网政策）  
- 推理延迟（QPS）

换模型 = 计划一次**全量重建索引**窗口。

---

## 26. 表格与 RAG

表格切进向量常丢结构。做法：

- 表格转 Markdown 或一行 JSON 一块；  
- 元数据 `contentType=table`；  
- 用户问数字仍以工具为准，表格块只解释「字段含义」。

---

## 27. 相似度分数要不要给用户看

产品可选「参考制度相似度 0.82」。  
管理层可能误读为「82% 正确」。  
更稳：只显示「命中制度 v3.2 第 7.3 条」，不显示 raw score。

---

## 28. RAG 冷启动：制度库最小集

第一版上线最少索引：

1. 安全库存管理办法  
2. 补货审批流程  
3. 仓库编码对照表  
4. 物料 ABC 分类说明  
5. 常见问题 FAQ 10 条  

五类文档覆盖 80%「口径类」问题，别等「全公司 PDF 扫完」才上线。

---

## 29. 反例：用 RAG 查「昨天销售额」

销售额是实时/准实时数据 → **工具**。  
RAG 里即使有「上月销售总结 PPT」，也不能当昨天数字。  
评测用例必须含「使模型 temptation 用 RAG 数字」的陷阱题。

## 33. 文档生命周期与 RAG

```text
草稿 → 审核 → 生效(effective) → 过期(expired) → 归档
```

仅 `effective` 进在线索引；过期文档保留审计但不参与检索。  
元数据 `status` 必过滤。

---

## 34. 多模态 PDF（图片扫描件）

扫描 PDF OCR 质量差会导致 RAG 全是乱码。  
制度类尽量要**可编辑文本源**；扫描件需人工校对 OCR 后再索引。

---

## 35. 引用格式统一

系统提示规定依据节格式：

```text
[制度] 库存管理办法 v3.2 §7.3 (chunkId=inv-7-3-华东)
```

统一格式便于正则抽取与存在性校验。

---

## 36. RAG 与多语言

若制度中英双语，chunk 带 `lang=zh|en`，检索 filter 与用户 locale 一致，避免英文问命中仅中文块无翻译。

---

## 37. 性能：预过滤 vs 后过滤

| 策略 | 做法 |
|------|------|
| 预过滤 | 查询向量库时带 metadata filter（推荐） |
| 后过滤 | 先 topK 再 Java 过滤（易漏真相关） |

永远优先预过滤。

## 39. 附录：RAG 问答全流程口述稿（3 分钟）

「用户问制度类问题 → 系统先把问题变成向量 → 带着仓库、租户等过滤条件去向量库找最像的几段制度 → 分数太低的丢掉 → 把剩下的片段编号写进 prompt → DeepSeek 只能根据这些片段解释口径，不能自己编条款 → 依据节必须写 chunkId → 如果问的是实时数字，还要再调 Java 工具，制度只解释规则不给出昨天销售额。」

背熟这段，04 章口头验收必过。

## 40. 附录：常见 RAG 切分错误集锦

1. **页眉页脚进 chunk**：每块都有「公司内部资料」五字，检索噪声。  
2. **目录进 chunk**：检索「第 7 章」命中目录而非正文。  
3. **多仓混切**：华东华北写在同一块，无法 filter。  
4. **无版本号**：旧版「15 日审批」与新版「7 日」同时命中。  
5. **表格拆行**：表头在一 chunk，数据在另一 chunk，模型只见表头。

对照检查你们即将索引的文档。

## 41. 附录：Embedding 与 Chat 双模型运维

运维需监控两套健康：

- DeepSeek Chat：延迟、429、token  
- Embedding：QPS、向量维度错误、索引滞后时间  

告警文案要区分，避免值班工程师对着 Chat API 查 embedding 故障。

## 42. 深度专题：向量相似度的直觉

余弦相似度 1.0 表示方向完全相同，0 表示无关。制度检索里：

- **0.75+**：常较相关，但仍需人工 spot check；  
- **0.65～0.75**：灰区，靠元数据 filter 决定去留；  
- **<0.65**：默认不注入 prompt。

阈值因 embedding 模型而异，必须用你们自己的评测集标定，不要抄讲义数字当真理。

## 43. 深度专题：制度更新如何不失效

```text
T0：新版制度 v3.3 发布
T1：索引管道索引 v3.3，metadata status=effective
T2：v3.2 改 status=expired（保留历史但不检索）
T3：评测集跑 R-01～R-10 回归
T4：上线
```

缺 T2 会导致旧版「15 日审批」与新版「7 日」同时被检索，模型在风险节胡搅成「11 日」。

## 44. 深度专题：用户上传文档与 RAG

第一期**不要做**「用户随便上传 PDF 进 RAG」——未经审核的文档是注入温床。  
若第二期要做：

- 上传先进隔离区；  
- 合规审核后入索引；  
- 元数据 `uploaderId`、`approvedBy`。

---

## 45. 深度专题：RAG 与缓存

同一问题 1 分钟内重复问，可缓存「检索结果 chunk 列表」而非缓存最终答案（数字仍要新工具）。  
缓存 key = `hash(question)+filter`。制度索引变更时清空缓存。

## 46. 课堂案例：错召分析

**问**：「华东仓 A 类物料安全库存怎么算？」  
**错召**：命中「华北仓 B 类物料促销管理办法」。  
**原因**：向量相近 + 缺 `warehouse` filter + 缺 `class=A` metadata。  
**修复**：切块时写元数据 + 检索强制 filter。

## 47. 收束：RAG 三不原则

1. **不**把 RAG 当实时数据库；  
2. **不**在未过滤的索引里检索多租户数据；  
3. **不**让依据节出现无 chunkId 的制度引用。

背下「三不」，04 章毕业。下一章记忆与会话，记得：**检索到的制度片段也不要写进永久 Memory 当唯一真相——制度更新后 Memory 里的旧引用会害你。**

## 48. 补充：RetrievalAugmentationAdvisor 在链中的输入输出（概念）

**输入**：用户问题、可选 filter（来自 SessionState 的 warehouse 等）。  
**过程**：query embedding → vector search → 拼接 context 块到 user 或独立 system 段。  
**输出**：增强后的 prompt 交给下一 Advisor 或模型。  
**不负责**：查实时库存、写 Memory、执行工具——别指望一个 Advisor 包打天下。

part-05 实现时对照此表检查职责是否越界。

## 50. 讲师结语

RAG 不是「把 PDF 扔进去就聪明了」，而是**可控的资料检索工程**。切块、元数据、阈值、filter，任何一步偷懒，都会在依据节露出马脚——要么胡编条款，要么张冠李戴。你和业务同事一起过一遍制度切分，比调三次温度更有用。第四章结束，去第五章把「记忆」和「知识库」彻底分开，后半周你会少踩一半坑。

**课后作业**：选公司一份制度 PDF（可脱敏），手工写 5 个 chunk 标题 + 元数据 JSON，拍照或打字存档。part-05 写索引代码时直接当测试数据规格。

**口头验收加一题**：闭眼说出 embedding、topK、元数据过滤、chunkId 各一句话。卡壳重读第 2～5 节。

**扩展思考**：若你们制度库全部在 SharePoint，索引管道还要处理权限同步——SharePoint 上谁能看的文档，向量库检索 filter 就要能表达同样范围。这是 part-05 的集成细节，概念周先记住「检索权限 = 业务权限」，不要「索引一次全员可见」。04 章全文完。下一文件：`05-记忆与会话.md`。
