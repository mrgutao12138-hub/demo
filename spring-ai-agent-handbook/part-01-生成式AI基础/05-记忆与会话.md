# 05 · 记忆与会话

> 同学们，记忆这一章很多人一开始就栽坑：  
> 把「对话记忆」当成「公司知识库」，把全厂数据塞进 session，结果**又贵又泄密又污染上下文**。  
> 今天我们把边界划清楚。

---

## 1. 对话记忆 ≠ 知识库

### 1.1 两个完全不同的东西

| 维度 | 对话记忆（Memory） | 知识库（RAG） |
|------|-------------------|---------------|
| 存什么 | 本会话里说过的话、确认过的参数 | 制度、SOP、口径文档 |
| 生命周期 | 随会话结束或过期清除 | 长期索引，版本管理 |
| 更新方式 | 每轮对话追加 | 文档变更后重新索引 |
| 检索方式 | 按时间顺序或摘要 | 向量相似度 + 元数据 |
| 典型容量 | 最近 N 轮或 N token | 全库分块 |
| 错误代价 | 污染后续轮次 | 错误片段被引用到多用户 |

【必背】**不要把全公司数据放记忆。**  
记忆是「这次开会白板上的字」，知识库是「档案柜里的制度」。

### 1.2 混淆后的灾难场景

某学员设计：「把 ERP 导出的 50 万行库存 CSV 放进 ChatMemory，下次就不用查工具了。」

后果：

1. **上下文爆掉**，请求失败或截断随机。  
2. **数据瞬间过时**，模型仍念旧数字 → 幻觉型决策事故。  
3. **多用户若共享记忆**（配置错误）→ 甲总监看见乙总监的查询。  
4. **成本**：每轮都把 50 万行往 API 送，账单爆炸。

正确做法：数字**每次用工具查**；记忆只留「用户已确认仓库=华东」这类**轻量状态**。

## 2. 会话（Session）与会话 ID

### 2.1 为什么需要 sessionId

HTTP 无状态，大模型 API 也无状态。  
「上一轮我说了华东仓」不会自动存在云端——要么你每次把历史拼进请求，要么你存库里下次取出。

**sessionId**：业务侧生成的唯一标识，绑定：

- 一段对话历史（Memory）  
- 审计日志关联  
- 限流与配额  
- 可选：用户身份、租户

```text
用户登录 ──► 创建或恢复 sessionId ──► ChatClient 带 memory advisor
                │
                ▼
         ChatMemoryRepository 按 sessionId 读写
```

### 2.2 sessionId 怎么生成

- 推荐：**UUID**，服务端生成，不信任客户端瞎传。  
- 绑定 `userId + tenantId`，防越权读别人会话。  
- 管理层 Web：一个浏览器标签一个 session，或「新话题」按钮换新 session。

### 2.3 会话何时结束

策略示例：

| 策略 | 说明 |
|------|------|
| 空闲超时 | 30 分钟无消息归档 |
| 显式结束 | 用户点「新对话」 |
| 长度上限 | 超过 N token 触发摘要压缩 |
| 敏感切换 | 用户角色变化强制新 session |

## 3. 短期记忆的几种形态

### 3.1 全量历史（最简单，最先爆）

每轮把 `user + assistant + tool` 全塞回。  
适合：演示、轮次 ≤ 5。  
不适合：生产决策对话。

### 3.2 滑动窗口

只保留最近 K 轮（如 10 轮）。  
优点：简单。  
缺点：早期确认的「仓库=华东」可能被滑掉。

### 3.3 摘要记忆（Summary）

旧轮次由模型或规则压成一段摘要：

```text
【会话摘要】
用户关注华东仓 A123 补货；已确认时间范围 7 天；
已调用 queryInventory 得 qty=1240；用户追问在途订单。
```

摘要由 **Java 触发**（如每 8 轮一次），低温生成，且要**审计存原文**。

### 3.4 结构化状态（推荐与摘要并用）

```json
{
  "confirmedWarehouse": "华东",
  "confirmedSku": "A123",
  "horizonDays": 7,
  "lastTools": ["queryInventory", "queryDemandForecast"]
}
```

比自然语言摘要**更不容易被模型改写成华北**。

Spring AI 2.0 概念对应：

- `ChatMemory` / `MessageChatMemoryAdvisor`  
- 生产可用 `JdbcChatMemoryRepository` 等持久化（part-07 再实现）

## 4. 记忆里应该存什么、不该存什么

### 4.1 应该存

- 用户原话（或脱敏版）  
- 助手**最终答案**（不含 thinking 全文，见 01 章 DeepSeek 行为）  
- 工具调用与**裁剪后**的工具结果摘要  
- 用户确认过的澄清（「对，就是华东」）  
- 结构化状态 JSON

### 4.2 不该存

- 全表库存、全量订单明细  
- 制度 PDF 全文（应 RAG 索引）  
- 其他用户的对话  
- 明文密钥、连接串  
- 未经同意的个人敏感信息  
- 模型 thinking 长文（除非审计专表，且不进入下一轮 prompt）

### 4.3 Tool 结果要不要原样进记忆

原则：

- 小结果（< 2KB 结构化 JSON）：可存。  
- 大结果：只存摘要 + 「详见审计 logId=xxx」。  
- 含 PII：脱敏后再存。

## 5. DeepSeek 多轮与 CoT 不回灌（复习强化）

单轮响应可能包含：

- `thinking`：推理草稿  
- `content`：最终答案

写入 **ChatMemory 参与下一轮拼接** 的，应是：

```text
assistant: （最终五段式报告正文）
tool: （工具返回）
user: （下一轮问题）
```

**通常不把 thinking 全文作为 assistant 历史回灌**（DeepSeek API 常见语义）。  
原因：省 token、减污染、防用户看到冗长草稿误以为「依据」。

审计需要 thinking 时：

```text
ChatMemory（给模型）     ≠     AuditStore（给人查）
```

## 6. 记忆与 RAG、工具的协作顺序

```text
1. 读 session 历史 / 摘要 / 结构化状态
2. RAG 检索（带租户、仓库 filter）
3. 模型决定工具调用
4. 工具执行
5. 生成答案
6. 写回 Memory（干净版）
```

【易混】先工具后 RAG 还是先 RAG 后工具？  
决策场景常见：**RAG 提供口径约束，工具提供数字**；两者都应在生成前就绪。Advisor 链顺序在 part-03 项目里微调，原则是不让「无数字的先结论」。

## 7. 多租户与权限

### 7.1 记忆隔离

```text
memoryKey = hash(tenantId, userId, sessionId)
```

严禁只用 `sessionId` 当全局键。

### 7.2 读记忆也要鉴权

恢复历史接口必须验证：当前用户是否该 session 的拥有者。

### 7.3 管理层代问

若秘书代总监问，session 应绑**实际数据权限主体**（总监账号），不是秘书的个人视图。

## 8. 记忆带来的上下文污染（复习）

记忆是污染主因之一：

- 第 2 轮助手口误「华北」，第 5 轮仍被引用。  
- 摘要模型把「未确认」写成「已确认」。  
- 用户恶意前几轮诱导，后续轮次「顺从」。

对策：

- 结构化状态以 **用户明确确认** 为准。  
- 关键参数每轮可用工具**再校验** existence。  
- 敏感决策可要求「请确认：仓库=华东」按钮，而不是纯文本「好的」。

---

## 9. 长期记忆要不要做

第一版：**不做**跨会话长期记忆。

原因：

- 「总监偏好简短」可从用户设置表读，不必向量记忆。  
- 跨会话「记住上次库存」必然过时。  
- 合规：用户要求删除历史时，向量记忆难删干净。

若第二期要做，也应是**显式用户配置**（「默认仓库=华东」），不是模型偷偷记。

## 10. 概念伪代码

```java
void handleTurn(String sessionId, String userText, UserContext ctx) {
    authz.assertSessionOwner(sessionId, ctx);

    List<Message> history = memory.get(sessionId, maxTokens(8000));
    SessionState state = stateRepo.get(sessionId);

    String augmentedUser = mergeStateIntoPrompt(userText, state);

    String answer = chatClient.prompt()
        .messages(history)
        .user(augmentedUser)
        .call()
        .content();

    memory.add(sessionId, new UserMessage(userText));
    memory.add(sessionId, new AssistantMessage(answer)); // 无 thinking

    stateRepo.update(sessionId, extractState(answer, userText));
}
```

## 13. 【易混】

| 易混 | 正解 |
|------|------|
| 记忆越大越智能 | 越大越贵、越易污染、越易泄密 |
| ChatGPT 能记住我所有事 | 那是产品功能；企业自建要显式设计且合规 |
| 工具查过一次就写进记忆不用再查 | 数字会过期；状态可记，数字应再查 |
| RAG 可以替代记忆 | RAG 是制度；记忆是对话上下文 |
| 摘要 = 可靠事实 | 摘要也会错，关键参数用结构化状态 |

## 14. 章节小结

记忆是**会话内的短期上下文**，不是公司知识库：

- **sessionId** 绑定用户与审计；  
- 存**最终答案 + 轻量状态**，不存全量业务表；  
- **thinking 不回灌**；  
- 与 RAG、工具分工清晰，防止上下文污染。

下一章：`06-Agent架构模式.md`——这些零件怎么排成一条流水线。

## 15. 会话状态机（概念）

```text
CREATED → ACTIVE → IDLE → ARCHIVED
              │        │
              └─ RESET（用户点「新对话」）→ CREATED（新 sessionId）
```

| 状态 | 行为 |
|------|------|
| CREATED | 空记忆，仅系统提示 |
| ACTIVE | 正常读写 Memory |
| IDLE | 超时未发言，可只读打开或归档 |
| ARCHIVED | 不参与在线推理，仅审计查阅 |

实现可简化，但产品要有「新对话」与「继续上次」的明确区分。

---

## 16. 摘要记忆怎么写才不容易错

摘要 prompt（给摘要专用低温调用）示例：

```text
请将以下对话压缩为 200 字以内事实摘要：
- 只保留已确认参数与用户明确同意的结论
- 禁止引入对话中未出现的数字
- 用 bullet 列表
```

摘要结果进 Memory 前，可选规则校验：若摘要比对工具日志发现新数字，丢弃摘要改全量保留最近 2 轮。

## 17. 结构化 SessionState 完整范例

```json
{
  "tenantId": "T001",
  "userId": "U888",
  "confirmedWarehouse": "华东",
  "confirmedSku": "A123",
  "horizonDays": 7,
  "pendingClarification": null,
  "lastToolCalls": ["queryInventory", "queryDemandForecast"],
  "lastAsOf": "2026-09-08T08:00:00+08:00"
}
```

每轮结束后由 Java 更新，**不交给模型自由改写 JSON 存盘**（防注入改仓库）。

## 18. 合规：用户要求删除会话

企业场景常见「右键删除对话」：

- Memory 表按 sessionId 物理删除或软删除；  
- 审计日志是否保留，按公司合规（有的要求删用户可见但留审计）；  
- 向量库**不**按 session 存，无需删 chunk；  
- 若曾把对话导出进 RAG（错误做法），删除极难——再次强调对话不进知识库。

## 19. 多端同步：Web 与企业微信

同一 `userId` 在不同端是否共享 session？

| 策略 | 优点 | 缺点 |
|------|------|------|
| 每端独立 session | 简单 | 体验割裂 |
| 云端统一 session | 体验好 | 并发写记忆要锁 |
| 仅 Web 完整，IM 只推送结论 | 安全 | 功能差 |

第一版：**每端独立 sessionId**，避免 IM 与 Web 历史打架。

## 20. 记忆容量估算（心算公式）

```text
每轮约 = 用户 50～200 字 + 助手 300～800 字 + 工具 JSON 200～2000 字
10 轮可能 = 数千～两万 token
```

超过预算前主动摘要，不要等 API 报错。

## 21. 与 Spring AI MessageChatMemoryAdvisor 的对应关系（概念）

```text
请求前：advisor 从 repository 按 conversationId 取历史，插入 messages
请求后：advisor 把本轮 user/assistant 写回 repository
```

`conversationId` 即你的 sessionId（或映射）。  
配置 `maxMessages` 或 token 上限在 advisor 或 repository 层。

## 25. 对话记忆的数据结构演进

```text
v0：全量 messages 列表
v1：滑动窗口 maxMessages=20
v2：v1 + 每 10 轮摘要
v3：v2 + SessionState JSON
v4：v3 + 关键工具结果哈希（防摘要改数字）
```

企业上线路径按 v0→v3 逐步演进，不要第一天就 v4 过度设计，但**设计表结构时留扩展字段**。

## 26. sessionId 与 traceId 分工

| ID | 生命周期 | 用途 |
|----|----------|------|
| sessionId | 用户一次「话题」 | Memory 键 |
| traceId | 单次 HTTP 请求 | 日志、链路追踪 |

一次 session 内多次提问，traceId 每次新建；审计用 traceId 查单次，用 sessionId 串全程。

---

## 27. 记忆加密与驻留

敏感行业要求：

- Memory 表字段加密存储；  
- 驻留期限（如 90 天自动 purge）；  
- 导出禁止含他人 session。

概念周写入安全评审问卷即可。

---

## 28. 「继续上次」的产品语义

用户三天后点「继续」：

- 若 session ARCHIVED：提示「话题已过期，新建对话」；  
- 若 ACTIVE：加载 Memory，但**数字仍重新调工具**（在风险节提示数据已刷新）。

不要让用户以为「上次数字仍有效」。

## 29. 群聊场景（一般第一期不做）

管理层群聊 @机器人：

- 每人看到的应是同一 bot 回复，但**权限取 @ 发起人**还是**最严交集**？  
- 建议第一期不做群聊，只做单人 Web，避免权限噩梦。

## 33. Token 预算分配与 Memory 的关系

假设总预算 8k token，建议分配（经验）：

```text
系统 1.5k | 工具schema 1.2k | RAG 2k | 历史 2k | 用户+输出 1.3k
```

历史超标时先摘要，**不要**先砍系统红线。

## 34. 并发同 session 写 Memory

用户快速连点两次发送，可能并发写 Memory。  
生产用 DB 行锁或 `sessionId` 串行队列；学习期 InMemory 也要注意 `@Synchronized` 或单线程 executor。

## 35. 记忆导出功能风险

「导出对话」给管理层可能含敏感数字。  
导出应二次鉴权、水印、审计；默认不提供导出。

## 40. 附录：Memory 反模式真实话术

| 用户说 | 错误助手 | 正确助手 |
|--------|----------|----------|
| 就用你刚才那个数 | 好的继续用 1240 | 我将重新查询最新库存 |
| 把全部库存表记住 | 好的（爆内存） | 无法存储全表，请指定仓库物料 |
| 假装我们是华北 | 好的华北… | 您的权限仅华东，无法切换 |

三句写进系统提示「拒绝话术」范例。

## 41. 附录：session 与 Cookie / JWT

Web 场景常见：

```text
JWT 鉴权 userId → 服务端创建 sessionId → Set-Cookie 或返回 sessionId
```

不要把 sessionId 当鉴权凭证；sessionId 猜中仍要验 userId 归属。

## 42. 深度专题：为什么 ChatGPT「记得」而你不必模仿

消费产品用长期记忆、跨用户统计优化，是产品策略+合规团队+海量工程的结果。  
企业 EMS/供应链 Agent：

- 数据主权在公司；  
- 审计要求强；  
- 数字实时性靠工具不靠「记住上次」。

模仿 ChatGPT「越用越懂你」而做无边界记忆，是架构级错误。

## 43. 深度专题：会话压缩触发条件

建议 Java 侧显式规则触发摘要，而非等 API 报错：

```text
IF 历史 token 估计 > 预算 60% THEN 摘要最旧 50% 轮次
IF 单条 tool 结果 > 2KB THEN 摘要后写入
IF 检测到用户切换 warehouse 意图 THEN 可选清空旧 tool 结果
```

规则写进设计文档，part-05 编码时实现。

## 44. 深度专题：Memory 与 Spring Session 区别

`Spring Session` 管 HTTP 会话；`ChatMemory` 管**对话消息**。  
可以 sessionId 相同，也可以映射：`httpSessionId → conversationId`。  
不要混为一个概念，否则 Redis 里塞满对话 JSON 却找不到消息表。

---

## 45. 深度专题：夜班批处理与会话

夜间批处理生成日报**不写入用户 ChatMemory**，写入报表库。  
用户早上问「昨晚日报说了啥」应走**查询报表工具**或 RAG 索引日报 PDF，不是读 Memory。

## 47. 收束：记忆五不原则

1. **不**存全公司业务表；  
2. **不**把 RAG 全文塞进 Memory；  
3. **不**把 thinking 当下一轮历史；  
4. **不**跨用户共享 session；  
5. **不**用 Memory 替代再次 tool 查数。

配合 04 章「数字走工具」，五不原则构成会话侧红线。06 章见。

## 48. 补充：MessageChatMemoryAdvisor 默认行为（Spring AI 2.0 概念）

- 在调用模型**前**读取 `conversationId` 对应历史消息；  
- 在模型与工具循环**结束后**把本轮 user/assistant 写回（具体是否包含 tool 消息以实现为准，学习期要求：**tool 结果要进历史或进审计，至少其一**）；  
- 与 `InMemoryChatMemoryRepository` 配合用于本地学习，生产换 JDBC。

【易混】Memory Advisor 放在链的**外侧**，不要放在 ToolCalling 循环**内部**重复叠加同一条历史，否则 token 指数涨。官方推荐顺序见 06 章与选型说明书架构图。

## 50. 讲师结语

记忆问题在生产环境往往比 RAG 更早引爆——因为产品同学天然想要「它应该记得我刚才说的」。你的标准回答是：**记得参数，不记得全表；记得话题，不记得权威数字。** sessionId、摘要、SessionState 三件套，是从 demo 到可审计系统的最低配置。第五章完成后，你已经具备画完整架构图的所有零件，第六章把它们排成一条不会散的流水线。

**课后作业**：写 `chat_session` / `chat_message` 两表字段说明（不少于 8 个字段），注明哪些字段加密、哪些字段禁止存 thinking 全文。

**口头验收加一题**：用户说「继续用刚才的库存数」你怎么办？标准答案：重新调 `queryInventory`，并在风险节说明已刷新快照。

**扩展思考**：移动端会话更短、更易中断，Memory 摘要触发阈值可比 Web 更激进；但**鉴权与 session 归属**不能更松。同一套 `ChatMemoryRepository` 接口，不同端可配不同 `maxMessages`，这是产品策略，不是技术妥协。05 章全文完。下一文件：`06-Agent架构模式.md`。

## 51. 与全书金句的衔接

若产品说「想让助手记住公司所有客户名单」，你的回答是：客户主数据在 CRM/ERP，应通过工具按权限查询；会话里只保留「当前讨论的客户编码」等轻量状态。能把边界讲清，05 章才算毕业。

**【必做回顾】**：完成 SessionState 设计、超时策略、禁止清单、对比图四项必做后，向同事解释「为什么 ChatGPT 能记住很多事，我们第一期却不做长期记忆」——答案要点：合规、实时数字、成本、污染。05 章全部正文结束。【易混】最后强调：`conversationId` 与 HTTP Session 不是同一个东西，可以一一映射，但不要混在一个 Redis key 里塞两种语义。
