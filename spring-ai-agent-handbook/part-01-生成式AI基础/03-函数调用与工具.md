# 03 · 函数调用与工具

> 同学们，这一章是决策 Agent 的「分水岭」。  
> 没工具，你做的是**聊天**；有工具且工具背后是真数据，你做的才是**辅助决策**。  
> 记住铁律：**模型永远不能直连数据库。**

---

## 1. 函数调用（Function Calling）是什么

### 1.1 一句话定义

**函数调用**：模型在生成文本的过程中，可以按约定格式输出「我要调用某个函数，参数是这些」；**真正执行函数的是你的 Java 程序**，执行结果再塞回对话，模型据此继续生成最终回答。

类比餐厅：

| 角色 | 对应 |
|------|------|
| 顾客 | 管理层用户 |
| 服务员（模型） | 听懂需求、填点菜单、上菜时念菜名 |
| 厨房（Java @Tool） | 真炒菜、真查库存 |
| 菜单（Tool schema） | 菜名、配料说明、辣度选项 |

模型**不会**冲进厨房自己拿盐。它只会递一张点菜单 JSON。

### 1.2 与「让模型写 SQL」的本质区别

有人提议：「让模型生成 SQL，我们在 Java 里执行不就行了？」

学习期和企业第一版，**强烈不推荐**：

- SQL 注入与越权表风险极高。  
- 模型爱「猜表名」「猜字段」，幻觉直接变成数据泄露。  
- 审计困难：你不知道它下次会 `SELECT` 什么。

正确做法：**每个业务问题对应少数、语义清晰的只读工具**，内部写死仓储查询或调用既有内部 API。

```text
❌ tool: executeSql(sql: string)
✅ tool: queryInventory(warehouse: string, sku: string, asOfDate: date)
```

## 2. 调用链路（心里要有一张图）

```text
用户问题
   │
   ▼
ChatClient + 系统提示 + 工具 schema 列表
   │
   ▼
模型输出（两种可能之一）
   ├─ A. 普通文本 → 直接返回（应少见，决策场景应鼓励先查数）
   └─ B. tool_calls JSON → 「我要调 queryInventory，参数 {...}」
           │
           ▼
      Java ToolCallingAdvisor 拦截
           │
           ▼
      校验参数 + 鉴权 + 调用 @Tool 方法
           │
           ▼
      工具结果（JSON/文本）作为 tool 角色消息追加
           │
           ▼
      再次请求模型 → 生成五段式报告
           │
           ▼
      （可能循环：还要调第二个工具）
```

Spring AI 2.0 里，**ToolCallingAdvisor** 负责这个循环；你用 `@Tool` 标注 Service 方法，框架生成 schema 并注册。

本周概念重点：**循环存在、执行在 Java、模型只见结果摘要**。

## 3. 模型只能发 JSON，Java 才执行

### 3.1 模型侧长什么样

模型发出的不是 Java 代码，而是结构化请求，概念上类似：

```json
{
  "tool": "queryInventory",
  "arguments": {
    "warehouse": "华东",
    "sku": "A123"
  }
}
```

具体字段名以 DeepSeek + Spring AI 适配为准，但语义不变：**name + arguments**。

### 3.2 Java 侧必须做什么

在 `@Tool` 方法真正跑查询之前，你的代码层（或统一拦截器）要做：

1. **参数校验**：类型、范围、必填；`warehouse` 是否在用户权限内。  
2. **鉴权**：当前 session 的租户、角色、数据域。  
3. **超时与限流**：防止模型连环调用拖死连接池。  
4. **结果裁剪**：不要把 10 万行 raw 结果全塞回上下文；摘要 + 分页。  
5. **审计日志**：谁、何时、调了啥工具、参数哈希、返回行数。

伪代码：

```java
@Tool(description = "查询指定仓库、物料的可用库存快照")
public InventorySnapshot queryInventory(
    @ToolParam(description = "仓库编码，如 华东、华北") String warehouse,
    @ToolParam(description = "物料编码，如 A123") String sku) {

    authz.assertCanReadWarehouse(currentUser(), warehouse);
    return inventoryReadService.snapshot(warehouse, sku);
}
```

【红线】`@Tool` 方法里出现 `INSERT` / `UPDATE` / `DELETE` —— 学习期一律禁止。

### 3.3 模型永不直连数据库

三层隔离：

```text
模型 ──(仅 JSON 意图)──► Java Tool 层 ──(参数化查询)──► 只读数据源
         ✗ 无 JDBC
         ✗ 无连接串
         ✗ 无 SQL 字符串由模型生成
```

即使将来用 MCP 暴露工具，也是 **Java 进程持连接**，不是模型持连接。

## 4. Tool Description 怎么写

`description` 是**写给模型看的**，不是写给产品经理看的 Javadoc。

### 4.1 好 description 的结构

1. **一句话用途**：解决什么问题。  
2. **何时必须调用**：出现哪些关键词、哪些数字需求。  
3. **何时不要调用**：和相似工具的区别。  
4. **参数语义**：枚举值、格式、时区。  
5. **返回语义**：字段含义、可能为空。

### 4.2 对比示例

**差：**

```java
@Tool(description = "查库存")
```

**好：**

```java
@Tool(description = """
    查询某一仓库、某一物料编码的当前可用库存数量（不含在途）。
    当用户问「还有多少」「能不能撑几天」「要不要补货」且涉及具体物料时必须调用。
    不要用于查询采购订单状态（应使用 queryOpenPO）。
    参数 warehouse 使用公司标准仓库名：华东、华北、华南。
    返回 qty 为整数，asOf 为快照时间，若物料不存在 qty 为 null。
    """)
```

### 4.3 工具命名

- 动词开头：`query` / `list` / `summarize` / `compare`  
- 语义单一：一个工具一件事  
- 避免 `getData`、`handleRequest` 这种模型无法选的命名

### 4.4 工具数量

第一版：**5～15 个**高频只读工具足够。  
工具爆炸时，Spring AI 2.0 可用 **ToolSearchToolCallingAdvisor** 按需披露——那是 part-04 的事，本周知道「不是一次塞 200 个」即可。

## 5. 只读原则（Read-only First）

### 5.1 为什么默认只读

- 模型会**误触发**写操作。  
- 管理层要的是**建议**，不是不可回滚的自动执行。  
- 合规与审计：读比写容易辩护。

### 5.2 只读的技术含义

| 层级 | 要求 |
|------|------|
| 数据库账号 | 只读用户或只读视图 |
| Service | 无 `@Transactional` 写方法暴露为 Tool |
| API | GET / 查询类内部接口 |
| 命名 | 避免 `create` `update` `delete` 出现在 Tool 名 |

### 5.3 「建议单」怎么处理

可以有一个工具：

```java
@Tool(description = "生成补货建议单草稿文本，不写入任何业务系统")
public String draftReplenishmentAdvice(ReplenishmentDraftRequest req) {
    // 仅组装文本或写审计表，不调 ERP 写接口
}
```

注意：这是**生成文本**，不是**执行补货**。

## 6. 工具返回什么给模型

### 6.1 结构化优先

```json
{
  "warehouse": "华东",
  "sku": "A123",
  "qty": 1240,
  "uom": "件",
  "asOf": "2026-09-08T08:00:00+08:00"
}
```

比大段自然语言更不容易被模型改数字。

### 6.2 摘要与大结果

若返回 5000 行：

- Java 侧先 `LIMIT` + 聚合；  
- 或返回「共 5000 行，已截断，请缩小范围」；  
- **绝不全量进上下文**。

### 6.3 错误怎么返回

```json
{
  "error": "WAREHOUSE_FORBIDDEN",
  "message": "当前用户无权查看华北仓"
}
```

让模型在「风险」节如实写，而不是编造数字。

## 7. 多工具协作（单 Agent 内）

典型决策问：「要不要补货？」

模型应依次或并行：

1. `queryInventory`  
2. `queryDemandForecast`  
3. `queryOpenPO`（在途）  
4. 可选 `querySafetyStockPolicy`（若政策走工具而非 RAG）

这是 **单 ChatClient + 工具循环**，不是多 Agent。06 章再讲架构。

【易混】「模型选了错工具」通常是 **description 不清** 或 **少样本不够**，不是先上第二个 Agent。

---

## 8. 安全：工具层是最后防线

即使系统提示写满红线，仍要假设模型会：

- 胡乱填参数；  
- 尝试调用未授权仓库；  
- 在高温度下跳过工具直接答。

因此：

- **鉴权在 Java**，不在提示词。  
- **敏感字段脱敏**在 Java 返回前。  
- **幂等与限流**防刷。

## 12. 【易混】

| 易混 | 正解 |
|------|------|
| 模型执行了工具 | 是 **Java** 根据模型 JSON 请求执行 |
| Tool = Controller | Tool 是模型可调用的**窄接口**，Controller 对人 |
| 让模型写 SQL 更灵活 | 灵活 = 失控；用语义化只读工具 |
| 工具越多越好 | 先少而清，description 质量 > 数量 |
| 返回 raw 表更准 | raw 太大易污染且模型仍会改数字 |

## 13. 章节小结

工具是决策 Agent 的**手和眼**：

- 模型只递 **JSON 点菜单**；  
- **Java 执行、鉴权、裁剪、审计**；  
- **永不直连库**；  
- **description 决定模型会不会点对菜**；  
- **只读是第一版铁律**。

## 14. Tool Schema 长什么样（概念）

Spring AI 根据 `@Tool` 和 `@ToolParam` 生成 JSON Schema 发给模型，概念形态如下：

```json
{
  "name": "queryInventory",
  "description": "查询指定仓库、物料的可用库存……",
  "parameters": {
    "type": "object",
    "properties": {
      "warehouse": { "type": "string", "description": "仓库编码：华东、华北、华南" },
      "sku": { "type": "string", "description": "物料编码，如 A123" }
    },
    "required": ["warehouse", "sku"]
  }
}
```

模型只能在这个 schema 范围内「填参」。Java 侧仍要校验，因为模型可能填「华东仓」而你的枚举是「华东」。

**参数 description 和工具 description 同样重要**：写清格式、枚举、时区。

---

## 15. 并行工具调用与顺序依赖

部分模型支持一次返回多个 `tool_calls`。例如同时查库存和需求预测。

Java 侧：

- 无依赖的可 `parallelStream` 或虚拟线程并行，注意连接池大小；  
- 有依赖的（先查 sku 是否存在再查预测）应靠 description 写明顺序，或拆成模型两轮。

【易混】并行不是「模型能并行就无脑并行」，数据库压力要自己算。

---

## 16. 工具错误处理标准矩阵

| 错误类型 | 返回给模型 | 用户五段式 |
|----------|------------|------------|
| 参数非法 | `error=INVALID_PARAM` | 风险节说明，建议澄清 |
| 无权限 | `error=FORBIDDEN` | 结论「无法提供」，不编造 |
| 超时 | `error=TIMEOUT` | 建议缩小范围或稍后重试 |
| 空结果 | `qty=null` 明确字段 | 数字节「无数据」 |
| 下游 ERP 500 | `error=UPSTREAM` | 不暴露栈，记 traceId |

模型看到结构化 error，比看到 Java 栈更不容易幻觉。

## 19. 为什么不让模型「选 SQL」——展开三个事故剧本

**剧本 A**：模型 `SELECT * FROM inventory`，一次拉回百万行，OOM。  
**剧本 B**：模型 `JOIN` 了人事薪资表，管理层问答泄敏。  
**剧本 C**：模型生成 `UPDATE` 被误执行（若账号权限配置错误）。

语义化工具把爆炸半径锁死在单个 Service 方法内。

## 20. MCP 与 @Tool 的关系（预习）

将来若用 MCP 把别的系统能力接进来，原则不变：

- MCP Server 持连接与鉴权；  
- 模型仍只发 tool call JSON；  
- 你的决策 Agent 仍是**一个编排入口**。

本周只需记住：**无论 MCP 还是 @Tool，执行体都在 Java 进程（或你控制的 Sidecar），不在模型里。**

## 22. 工具粒度：太粗 vs 太细

| 粒度 | 例子 | 问题 |
|------|------|------|
| 太粗 | `querySupplyChain(任意问题)` | 模型难填参，Java 难实现 |
| 太细 | `getInventoryRowById` 每表一个 | schema 爆炸，选错率升 |
| 适中 | `queryInventory(warehouse,sku)` | 语义清晰，易鉴权 |

原则：**一个工具对应管理层能听懂的一个业务动作**。

---

## 23. 工具与缓存

只读工具也可缓存：

```text
queryInventory(华东,A123) 缓存 60s
```

减轻 ERP 压力，但必须在工具结果里带 `asOf`，并在风险节提示缓存延迟。  
不要让模型「以为实时」而你不说明。

---

## 24. 工具链与 Saga（别和 Agent 循环混）

五个工具顺序调用是 **Agent 循环**，不是分布式 Saga。  
若某步失败，由 Java 决定：中止、部分报告、或重试。  
不要在提示词里写「自动重试三次」而不实现。

## 26. 参数枚举与 @ToolParam

```java
@ToolParam(description = "仓库，允许值：华东|华北|华南，不含「仓」后缀")
```

枚举写进 description；Java 侧 `Set.of("华东","华北","华南")` 校验。  
模型填「华东仓」时返回明确错误，促使其下一轮改参。

## 28. 与提示词的工具使用条款

系统提示应镜像工具 description：

```text
涉及库存数量必须调用 queryInventory，不得凭记忆或推测回答。
```

三处一致：**系统提示、tool description、少样本**，减少「说了不调用」。

---

## 29. DeepSeek 工具调用与 Spring AI 2.0 概念映射

| 概念 | 含义 |
|------|------|
| `tool_calls` | 模型返回的调用列表 |
| `tool` 角色消息 | Java 执行后塞回的结果 |
| `ToolCallingAdvisor` | 自动循环直到无 tool_calls |
| `@Tool` | 你写的 Java 方法 |

模型提供商差异由 Spring AI 屏蔽；你只需保证 **description 和鉴权** 写对。

---

## 30. 工具幂等性

同一 `queryInventory(华东,A123)` 在 5 分钟内多次调用应安全（只读）。  
若工具触发「发送邮件」类副作用，即使只读语义也不应重复调用——第一期不做此类工具。

---

## 31. 超时与熔断

```text
单工具超时：5s
整 Agent 请求超时：30s
ERP 连续失败：熔断 1min，返回降级文案
```

写在运维手册，不是写在 prompt 里。

---

## 32. 工具返回字段命名

与管理层报表字段一致：`qty` vs `quantity` 统一一种。  
模型和前端都少犯错。在 description 写清别名映射若不可避免。

---

## 33. 跨系统工具编排

`queryInventory` 调 WMS，`queryOpenPO` 调 ERP，对模型仍是两个工具。  
Java 内部分别走不同 `RestClient`，模型不感知系统边界。

## 34. 工具权限模型 RBAC 范例

```text
角色「华东总监」→ warehouses=[华东]
角色「集团供应链」→ warehouses=[华东,华北,华南]
```

工具内 `assertAllowed(warehouse)`，模型填「华北」而用户无权限 → 结构化 FORBIDDEN。

## 39. 深度专题：从 REST 到 @Tool 的封装思维

你们平时写 `InventoryController` 暴露 HTTP，管理层 Agent 不应让模型直接调 HTTP URL——仍是无约束调用。正确封装路径：

```text
ERP 只读视图 / 内部 REST
        ↓
InventoryReadService（已有 Java 服务）
        ↓
@Tool queryInventory（窄接口 + 鉴权 + 审计）
        ↓
ToolCallingAdvisor / 模型
```

模型只见 `queryInventory` 的三个参数，不见 SQL、不见 URL、不见连接池配置。  
若已有 OpenAPI，可从 DTO **派生** Tool 参数，但暴露给模型的必须是**子集**，不是整个 OpenAPI 树。

## 40. 深度专题：工具结果摘要算法（概念）

当 ERP 返回 2000 行时，Java 侧摘要策略：

1. **聚合优先**：按仓库 sum、topN 滞销；  
2. **字段白名单**：只留 `sku,qty,asOf`；  
3. **截断声明**：`truncated=true, totalRows=2000, returnedRows=50`；  
4. **禁止**把 2000 行塞给模型再让它「自己总结」——它仍会改数字。

摘要后的 JSON 进上下文，完整结果进审计对象存储，供人工追溯。

## 42. 深度专题：工具与事务

只读工具应在只读事务或无需事务中执行：

```java
@Transactional(readOnly = true)
public InventorySnapshot snapshot(...) { ... }
```

即使只读，长事务仍占连接。工具方法要短、要快，复杂报表走异步批处理，不要塞进交互 Agent。

## 45. 补充：Spring AI 2.0 @Tool 与 Advisor 关系（预习表）

| 组件 | 职责 |
|------|------|
| `@Tool` 方法 | 业务只读查询实现 |
| `ToolCallback` / 自动注册 | 生成 schema 供模型选择 |
| `ToolCallingAdvisor` | 解析 tool_calls、执行、回灌、循环 |
| `ChatClient` | 统一入口，挂 Advisor 链 |
| 你的 `AuthzService` | 每个 Tool 内调用，模型不可见 |

part-04 第一周目标：一个 `@Tool` + 默认 `ToolCallingAdvisor` 跑通单轮查询。本周只需记住：**注解标在 Service 方法上，执行权永远在 Spring 容器内的 Java 线程，不在云端模型进程。**
