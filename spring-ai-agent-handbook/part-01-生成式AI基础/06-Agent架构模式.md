# 06 · Agent 架构模式

> 同学们，学到这一章，零件都齐了：提示词、工具、RAG、记忆、护栏。  
> 今天要回答：**这些零件按什么顺序转？**  
> 先讲清几种模式，再讲企业第一版该选哪条——答案可能会让你失望：**别一上来多 Agent 自治。**

---

## 1. 什么叫 Agent（在本讲义里的定义）

**Agent** 不是「会聊天的模型」，而是：

> 在**受控循环**里，根据目标决定**下一步动作**（调工具、检索、追问、结束），直到满足停止条件，由 **Java 掌控权限与数据** 的系统。

三个关键词：

1. **循环**（可能多轮 tool call）  
2. **受控**（工具白名单、只读、鉴权）  
3. **停止条件**（任务完成、超步数、超时、用户取消）

ChatGPT 网页版你也可以当聊天；加上 ToolCallingAdvisor 循环，才是本课程意义上的 Agent。

## 2. 单工具循环：ReAct 思想（不背英文也行）

### 2.1 ReAct 是什么

**ReAct**（Reasoning + Acting）思想：交替进行

```text
思考（该干什么）→ 行动（调工具）→ 观察（工具结果）→ 再思考 → …
```

在 Spring AI 2.0 里，你不需要手写 ReAct 字符串格式；**ToolCallingAdvisor** 驱动类似循环：

```text
Round 1: 模型 → tool_call queryInventory
Round 2: 模型看到结果 → tool_call queryDemandForecast
Round 3: 模型 → 最终五段式报告（无 tool_call）
```

### 2.2 停止条件（Java 必须配置）

| 条件 | 说明 |
|------|------|
| 模型不再发起 tool_call | 正常结束 |
| 最大步数 | 如 5 步，防死循环 |
| 总超时 | 如 30s |
| 重复调用检测 | 同一工具同参数连续 3 次 → 中止 |
| 用户中断 | SSE 断开 |

【红线】无步数上限的 Agent 循环 = 给自己埋雷。

### 2.3 伪代码

```java
// 概念：框架内由 ToolCallingAdvisor 实现类似逻辑
int step = 0;
while (step++ < MAX_STEPS) {
    Response r = model.chat(messages);
    if (r.hasToolCalls()) {
        for (ToolCall tc : r.getToolCalls()) {
            Object result = toolExecutor.execute(tc); // 鉴权在内
            messages.add(toolResult(tc, result));
        }
    } else {
        return r.getFinalContent();
    }
}
throw new AgentException("超过最大步数");
```

## 3. 路由模式（Router）

### 3.1 什么时候需要

问题类型差异大：

- 「查库存」走供应链工具集  
- 「查设备停机」走 EMS 工具集  
- 「制度怎么规定」可能只 RAG、少工具

一个模型一次看 30 个工具，**选错率上升**。

### 3.2 怎么做（概念）

**Router**：先用一次**低成本分类**（小模型、规则、或关键词）决定 `intent`，再进入对应子链：

```text
用户问题
   │
   ▼
Router（intent = REPLENISHMENT | DOWNTIME | POLICY_QA）
   │
   ├─► REPLENISHMENT → ChatClient + 供应链工具 + 供应链 RAG filter
   ├─► DOWNTIME      → ChatClient + EMS 工具
   └─► POLICY_QA     → ChatClient + RAG only（严格拒编数字）
```

Router 可以是：

- `if` 规则（学习期够用）  
- 一次低温 LLM 分类（`输出枚举 JSON`）  
- 未来：独立小分类模型

### 3.3 与多 Agent 的区别

Router 是**一个编排层**，子链仍是**同一套受控 ChatClient**，不是多个「自治大脑」互相踢皮球。

## 4. 计划-执行模式（Planner–Executor）

### 4.1 思想

复杂任务拆步骤：

```text
计划：
1. 查华东 A123 库存
2. 查 7 日需求
3. 查在途 PO
4. 对照安全库存制度
5. 输出建议

执行：逐步调工具，Planner 可根据上步结果调整 4、5。
```

### 4.2 两阶段实现

| 阶段 | 谁做 | 输出 |
|------|------|------|
| Planner | 模型（reasoning-effort 偏高） | 步骤列表 JSON |
| Executor | Java 循环或第二个 prompt | 逐步执行工具 |

### 4.3 适用与风险

**适用**：多约束归因、「为什么交期延误」类问题。  
**风险**：

- Planner 编造不存在的工具名 → Java 校验计划合法性  
- 计划过长 → 超 token  
- 计划泄露到用户 → UI 可折叠「分析过程」

第一版建议：**隐式 ReAct 够用就不显式 Planner**；显式 Planner 放第二期。

## 5. 多 Agent 自治（本期明确不做）

### 5.1 网上时髦方案

「采购 Agent」「库存 Agent」「财务 Agent」互相发消息，自主谈判。

### 5.2 为什么企业第一版别碰

| 问题 | 说明 |
|------|------|
| 责任不清 | 出错了算哪个 Agent |
| 成本失控 | Agent 互聊烧 token |
| 权限穿透 | 子 Agent 可能组合出越权查询 |
| 评测地狱 | 组合爆炸，无法回归 |
| 延迟 | 管理层等不起 |

### 5.3 正确替代

> **一个 ChatClient + 一组受控工具 + Advisor 链**

必要时加 **Router** 分流，仍是**单编排、单审计主体**。

## 9. 观测与调试（概念）

Agent 循环必须可观测：

- 每步：tool 名、参数、耗时、行数  
- token usage 累计  
- 最终 stop 原因（完成 / 超步 / 超时）

否则业务说「慢、错」，你无法定位是 Router 错了还是工具慢了。

## 10. 反模式清单

1. 每个 ERP 表一个 Agent。  
2. Agent 之间用自然语言传数字（应传结构化 tool 结果）。  
3. 无步数限制的 while true。  
4. 把写操作 Tool 藏给「高级 Agent」。  
5. 多 Agent 做权限分割但**没有统一审计 ID**。

## 14. 章节小结

架构模式是**组织零件的方式**：

- **ReAct 式单循环**是第一版主力；  
- **Router** 在工具变多时分流；  
- **计划-执行**用于复杂归因，谨慎引入；  
- **多 Agent 自治**不在第一期范围；  
- **一个 ChatClient + 一组只读工具 + Advisor 链**足够做出可演示的决策系统。

## 15. 完整走查：一个补货问题在架构里怎么转

**用户**：「华东 A123 要不要补货？」

```text
1. API 鉴权 → 取 userId、allowedWarehouses
2. 加载 sessionId 对应 Memory + SessionState
3. 若 state 无 warehouse → 模型追问（可能无 tool call）
4. 用户确认华东 → 更新 state
5. RAG 检索「安全库存制度」filter warehouse=华东
6. ToolCallingAdvisor 循环：
     queryInventory → queryDemandForecast → queryOpenPO
7. 模型生成五段式（temperature 0.2）
8. 输出校验 Advisor（来源、schema）
9. 写 Memory（仅最终答案 + 更新 state）
10. 审计落盘（含 tool 明细、rag chunkIds、token）
```

此链路 **只有一个 ChatClient**，没有「采购子 Agent」。

## 16. Router 实现三种成熟度

| 级别 | 实现 | 适用 |
|------|------|------|
| L0 | 无 Router，工具 <15 | 第一版默认 |
| L1 | 关键词规则 `if (q contains "停机")` | EMS/供应链分拆 |
| L2 | 低温 LLM 输出 `intent` 枚举 JSON | 问法多样 |
| L3 | 独立分类模型 | 大规模产品 |

不要从 L0 跳到 L3。

## 17. 计划-执行 vs 隐式 ReAct 选型

| 维度 | 隐式 ReAct | 显式 Planner |
|------|------------|--------------|
| 用户可见步骤 | 少 | 可多展示计划 |
| 实现成本 | 低（Advisor 默认） | 高（校验计划） |
| 可控性 | 中 | 计划可先审 |
| 第一版 | ✅ | 通常 ❌ |

显式 Planner 适合「计划本身要给人批」的强合规流程，第一期少见。

---

## 18. 「多 Agent」与微服务混淆辨析

微服务：**接口契约清晰、独立部署、单职责**。  
多 Agent 自治：**多个 LLM 实例互相对话、目标可能冲突**。

你可以有很多微服务，仍然只需要 **一个 Agent 编排层** 调它们的只读 API。  
不要把「每个微服务一个 LLM」当成架构目标。

---

## 19. 成本与延迟模型（心算）

```text
单次决策 ≈ 1～3 次 LLM 调用（含 Router）+ N 次工具 + 1 次 RAG embed
延迟 ≈ LLM RTT × 次数 + max(工具耗时) + 向量检索
```

每增加一个「自治 Agent」对话轮，近似多乘一次 LLM 账单。  
管理层问十个连续问题，十个独立 session 比一个大杂烩 session 更省污染、有时更省 token。

---

## 20. Supervisor 模式（了解即可，第一期不用）

网上常见 Supervisor 让主 Agent 派子 Agent。问题：

- 子 Agent 权限边界难审计；  
- 子 Agent 返回自然语言，数字易变形；  
- 调试要追多条 trace。

若将来要用，子 Agent 应返回 **结构化 tool 结果**，且仍经统一鉴权层。

---

## 21. 人机协同断点

企业决策系统常见「人在回路」：

```text
Agent 生成建议单 → 状态 PENDING → 人工在 ERP 点击确认
```

Agent 循环在「生成建议」处停止，不要循环到「执行写操作」。  
这是架构模式，不是模型能力问题。

## 23. 架构决策记录（ADR）模板

当你选型「单 Agent + Router」时，写 ADR：

```text

决策：加 L1 关键词 Router，分供应链/EMS
后果：多一次 if 维护；评测集加路由用例
替代方案：多 Agent —— 拒绝，审计与成本不可控
```

概念周写 ADR 能强迫你想清楚，不必等代码。

## 25. 单 Agent 循环的步数与业务复杂度

| 问题类型 | 典型 tool 步数 |
|----------|----------------|
| 单点查库存 | 1 |
| 补货评估 | 2～4 |
| 跨系统归因 | 4～5（触顶） |

超过 5 步往往说明工具粒度不对或应拆 Router，而不是提高 `MAX_STEPS`。

## 26. 流式输出（SSE）与 Agent 循环

管理层 Web 常用 SSE 逐字显示。注意：

- 工具调用阶段可能长时间无 token；  
- UI 应显示「正在查询库存…」而非空白；  
- **不要在 tool 未完成时流式输出数字**。

Spring AI `ChatClient` 流式 API 在 part-03 实现；本周知道 UX 要求即可。

---

## 27. 同步 vs 异步 Agent

| 模式 | 场景 |
|------|------|
| 同步 HTTP | 管理问答 <30s |
| 异步任务 + 轮询 | 超大报表、多工具慢查询 |

第一期同步够用；异步要任务表、取消、进度，复杂度高。

---

## 28. Agent 与批处理

「每晚生成事业部库存日报」是 **批处理 + 模板**，不是交互 Agent。  
别用 Agent 循环做 cron 能做的事。  
Agent 价值在**交互式、参数不确定**的决策问。

---

## 29. 工具搜索 Advisor（ToolSearch）何时上

工具注册 >20 且 description 仍易混淆时，用 `ToolSearchToolCallingAdvisor` 先检索相关工具子集再循环。  
小于 15 个工具不必提前优化。

---

## 30. 失败重试：模型 vs 工具

| 层 | 重试策略 |
|----|----------|
| 工具 | 指数退避 2 次，仍失败返回 error 结构 |
| LLM | 429/5xx 退避；**同一 prompt 不要盲目重试 5 次** |
| 整请求 | 用户可见「请重试」，带 traceId |

Agent 循环内「模型选错工具」靠 description 和评测改，不靠重试碰运气。

---

## 31. 架构评审常见质疑与回应

**质疑**：「一个 Agent 够不够？」  
**回应**：第一期证明价值用单 Agent；工具数 >15 加 Router，仍单编排。

**质疑**：「要不要上 LangGraph？」  
**回应**：团队 Java，Spring AI Advisor 链等价满足；不引入第二运行时。

**质疑**：「reasoning 模型太慢。」**  
**回应**：简单问 flash；复杂问 pro；评测驱动选型。

## 34. Advisor 链顺序争论与推荐默认

常见争论：Memory 在 RAG 前还是后？  
**推荐**：Memory → RAG → ToolCalling → 校验。  
理由：先知道用户上下文再检索，检索 query 可含 confirmedWarehouse；工具循环最后，避免未检索口径就乱调工具。

若业务特殊，用评测集验证顺序，不要凭感觉。

---

## 35. 单 Agent 与「工作流引擎」边界

若每一步固定（先 A 后 B 后 C），用 **工作流/Camunda** 更合适。  
Agent 适合**下一步依赖上一步结果、分支不确定**的流程。  
补货评估通常需要 Agent；「每月 1 号发固定报表」不需要。

---

## 36. 工具循环与人工审批接点

```text
Agent 循环结束 → 生成建议单 PDF → 人工审批 → ERP 录入（人）
```

Agent 架构在「生成建议单」停止；后面不是 LLM 的事。

## 37. 多模型在同一 Agent 内（高级）

Router 用 flash，报告用 pro——仍是**一个编排服务**，两个 `ChatClient` bean，共享 session。  
不要两个自治 Agent 互聊。

## 40. 附录：三种架构模式选型问卷

答完自动选型：

1. 工具数量 <15？是 → 单循环；否 → 考虑 Router。  
2. 是否需要展示给人审批的「计划步骤」？是 → 考虑 Planner；否 → 隐式 ReAct。  
3. 是否存在多个 LLM 互相对话需求？是 → **停**，回第一期范围砍需求。  
4. 延迟要求 <30s？是 → 控制 tool 步数 ≤5。  
5. 是否有评测集？否 → **先别上线**。

## 46. 课堂辩论：「一个 Agent 是不是太简陋？」

## 51. 讲师结语

架构章最容易犯的错是「堆概念」：Router、Planner、Supervisor、多 Agent 全上要。你把第一期收成**单循环、单编排、单审计主体**，不是落后，是成熟。等评测集稳定、工具稳定、幻觉率数字能拿给总监看，再加 Router 或 Planner 都有据可依。第六章结束，最后一章评估与护栏，给这套架构装上刹车和年检。

**课后作业**：用一页 PPT 或纸画「企业第一版架构」，必须含 Advisor 顺序、只读边界、sessionId 触点。下周 part-02 开项目前给同事讲 3 分钟，讲不顺不准写代码。

**口头验收加一题**：用 30 秒解释 ReAct 与 `ToolCallingAdvisor` 的对应关系，禁止背诵英文缩写，用中文「思考—行动—观察」说清。

**扩展思考**：将来若接企业微信机器人，架构仍是「一个编排服务 + sessionId」，只是入口从 MVC 换成回调 Controller；**不要**为 IM 再克隆一套 Agent 逻辑，否则评测集要维护两份，幻觉率翻倍。入口可多，编排应一。06 章全文完。下一文件：`07-评估护栏与幻觉.md`——part-01 最后一章，把评测与红线写进你的工程 DNA。
