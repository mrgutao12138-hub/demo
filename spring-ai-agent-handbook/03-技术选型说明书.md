# 03 · 技术选型说明书

> 选型不是信仰。是约束条件下的工程决策。  
> 这一章把「为什么是 Spring AI 2.0 + Boot 4 + DeepSeek」讲透，避免你第三周又想换成别的栈。

---

## 1. 你的真实约束

把约束写在桌上：

1. 团队语言是 Java，存量系统是 Spring。
2. 没有时间再养一套 Python 服务、两套发布、两套监控。
3. 数据在企业内部库，出网受限，权限复杂。
4. 用户是管理层，要的是**可信的数 + 可解释的判断**，不是文采。
5. 第一版必须几个月内能演示，不能先研究两年算法。

在这些约束下，正确策略是：

> 用 Java 生态里最官方、最能跟 Spring 生命周期走在一起的 AI 框架，  
> 模型则买云端 API，把算力问题外包。

这就是 Spring AI + DeepSeek。

---

## 2. 为什么不是 Python

Python 生态（LangChain、LlamaIndex、各种 Agent 框架）文档多、示例多、研究快。对算法同学很香。

对你不香的原因：

- 你要对接的 SSO、权限、数据源、事务、审计，全在 Spring 里已经有了。
- Agent 的核心价值在**工具背后的业务方法**，那些方法本来就是 Java Service。
- 多一门运行时，故障域直接翻倍：虚拟环境、包冲突、GIL、独立网关。
- 你要学的是 Agent 工程，不是生态观光。概念（Tool、RAG、Memory）是通用的，学 Spring AI 一样能建立。

以后若公司有算法组用 Python 做离线分析，让它们通过 HTTP / MCP 把能力暴露出来，你在 Java 里当编排方。不必把主应用改成 Python。

## 3. 为什么是 Spring AI 2.0，而不是 1.x 或自己拼 HTTP

### 3.1 自己拼 HTTP 的结局

你当然能用 RestClient 调 `https://api.deepseek.com/chat/completions`。第一天很快。第 30 天你会手写：

- 消息拼接
- 工具循环
- JSON schema
- 流式解析
- 重试与退避
- token 统计
- 多模型差异

这些正是框架的工作。企业 Agent 的复杂度在业务工具和护栏，不在 HTTP 客户端。

### 3.2 为什么必须 2.0

Spring AI 2.0.0 于 2026 年 6 月 GA，基线是 **Spring Boot 4.0 / 4.1 + Spring Framework 7**。

相对 1.x，和你最相关的变化：

| 主题 | 1.x | 2.0（你要学的） |
|---|---|---|
| 日常 API | ChatModel 和 ChatClient 混用 | **ChatClient 为一等公民**，ChatModel 是底层 |
| 工具循环 | 埋在各个 ChatModel 实现内部 | **ToolCallingAdvisor** 在 Advisor 链里循环 |
| 组合能力 | 很难在工具循环「里面」插记忆、观测 | Advisor 可排序、可重入，记忆/校验/评估都能组合 |
| 大量工具 | 一次把全部 schema 塞给模型 | **ToolSearchToolCallingAdvisor** 按需披露 |
| 结构化输出 | 主要靠提示词约束 | 可 `validateSchema()` 失败重试；可选提供商原生结构化 |
| RAG | 大量教程教 `QuestionAnswerAdvisor` | 主推模块化 **RetrievalAugmentationAdvisor**（`spring-ai-rag`） |
| MCP | 分散 | 官方 MCP Java SDK 2.0，注解 `@McpTool` 等 |
| JSON | Jackson 2 | **Jackson 3** |
| 空安全 | 不统一 | JSpecify |
| 配置 | 不少 `.options` 段 | 选项与配置解耦，默认值在 options 上 |

【易混】网上 90% 中文 Spring AI 教程仍是 1.x。看到旧 starter 名、`toolNames`、`internalToolExecutionEnabled`，直接关掉。

### 3.3 版本冻结（学习期）

```
Java            21（推荐） / 17（最低） / 25（可用）
Spring Boot     4.1.x
Spring AI BOM   2.0.0
Maven           3.9+
```

学习期不要用 `2.0.0-SNAPSHOT`。快照天天变，排障会把你打崩。

## 4. 为什么大模型选 DeepSeek 云端

### 4.1 对你友好的点

- 有官方 `spring-ai-starter-model-deepseek`，不是「用 OpenAI 兼容凑合」的唯一路径（兼容路径也成立，但官方 starter 更省事）。
- API 形态就是 Chat Completions，概念与行业主流一致。
- 价格通常明显低于同档国际模型，适合你这种要大量试错的学习期。
- 中文业务文档、ERP 术语表现好。
- 提供闪速档与专业档：`deepseek-v4-flash` / `deepseek-v4-pro`，还有 `deepseek-chat`、`deepseek-reasoner` 等别名型型号，讲义会教怎么选。
- 支持思考模式（thinking）与推理力度（reasoning-effort），适合「对比、归因、建议」类决策问题。

### 4.2 你必须接受的限制

- **没有官方 embedding 接口配这套对话 API。** RAG 必须另接向量模型（本地 Transformers 或其它 embedding 服务）。这不是小事，part-05 会专门处理。
- 云端意味着文本出域。制度里有绝密、名单里有完整手机号，要脱敏或改走内网模型（扩展篇）。
- 有配额、有限流、有偶尔波动。工具超时和降级不是可选功能。
- 模型会变。你的系统必须靠工具和评测集稳住质量，而不是赌某一版模型「变聪明」。

### 4.3 主线默认怎么配

学习 Hello World：

```yaml
spring:
  ai:
    deepseek:
      api-key: ${DEEPSEEK_API_KEY}
      chat:
        model: deepseek-v4-flash
        temperature: 0.3
```

决策 Agent 默认：

```yaml
spring:
  ai:
    deepseek:
      api-key: ${DEEPSEEK_API_KEY}
      chat:
        model: deepseek-v4-pro
        temperature: 0.2
        thinking:
          type: enabled
        reasoning-effort: high
```

数字查询、工具选择：温度偏低。写邮件、写纪要：可以略高。不要全局 1.0。

## 6. 模块依赖怎么切（避免一个 pom 堆满）

按阶段加，不要第一天全加。

**阶段 A · 只会说话**

- `spring-boot-starter-web`
- `spring-ai-starter-model-deepseek`

**阶段 B · 成为 Agent**

- 仍是上面那些。`@Tool` 与 `ToolCallingAdvisor` 已在 ChatClient 体系内。
- 需要大量工具时再加 `spring-ai-starter-tool-search-advisor`

**阶段 C · RAG**

- `spring-ai-rag`
- `spring-ai-vector-store`（以及具体存储 starter，如 pgvector）
- `spring-ai-starter-model-transformers` 或其它 embedding starter

**阶段 D · 生产记忆**

- 开发：内存 `InMemoryChatMemoryRepository`
- 生产候选：Redis / JDBC（注意：不是所有仓库都能存 tool 消息；默认把记忆放循环外更安全）

**阶段 E · MCP（可选）**

- `spring-ai-starter-mcp-client` 或 server 端 starter
- 当你要把「别人已经做好的工具进程」接进来，或要把自己的工具暴露给 IDE / 其它 Agent 时才需要

完整可复制 pom 见 `appendix/pom完整模板.md`。

## 7. 数据层选型原则

管理层决策系统最常见的失败，不是模型不够聪明，而是**查到的数口径乱、权限乱、延迟乱**。

推荐演进：

1. **演示期：** 独立 Postgres，表结构按讲义脚本，数据是假的但像真的。
2. **试用期：** 从 ERP/WMS/EMS 同步「决策宽表」到只读库，每天或每小时。Agent 只打宽表。
3. **稳定期：** 宽表 + 指标字典（「库存周转」官方 SQL）。需要实时的少数指标走现成 API。
4. **不要作为默认：** 模型现场生成 SQL 打核心库。这叫把生产当玩具。

part-06 会把四种接入模式展开。这里先定调：宽表 + 工具，是你的主路。

## 8. 前端怎么选（别在 UI 上牺牲）

第一版前端只需要：

- 一个对话页（输入框、流式输出、来源卡片）
- 一个审计页（管理员看日志）

实现建议：

- 后端 SSE；前端随便：原生 HTML、Vue、React 都行。
- 不要一上来做「自动生成 PPT」「语音会议纪要」。那是下一季度的糖。

讲义综合项目给最小 HTML + fetch，保证零前端框架也能演示。你有前端同事就让他们换皮。

## 9. 以后换模型会不会推倒重来

只要你坚持：

- 业务代码对着 `ChatClient` / `ChatOptions` 编程
- 工具是你自己的 Java 方法
- 提示词不写死某一家模型的私有字段（DeepSeek 的 thinking 用配置隔离）

那么换成 GPT、Ollama、国产云，主要是：

1. 换 starter
2. 换 base-url、api-key、model 名
3. 回归评测集
4. 处理该模型对工具/JSON 的癖好

这正是 Spring AI 存在的意义。扩展篇会给对照表，主线不要提前换。

## 10. 「越先进越好」怎么理解才不会翻车

先进 ≠ 每天追新模型名。

对 Java 企业 Agent 而言，2026 年仍然先进的能力是：

1. **Advisor 化的工具循环**（Spring AI 2.0 的核心）
2. **按需披露工具**（Tool Search）
3. **模块化 RAG** 而不是「检索拼一段字」
4. **MCP 作为工具互操作协议**（先会用，再决定是否上）
5. **结构化输出校验闭环**
6. **可观测性与评测集**（这比换一个更新的模型更先进）

第一年把这六件做扎实，你不会落后。落后的人是：无工具的聊天框 + 无来源的数字 + 无审计的权限。

## 11. 明确不选的东西（以及为什么）

| 不选 | 原因 |
|---|---|
| 把 Python Agent 当主服务 | 与存量 Java 分裂 |
| 学习期上 Kubernetes GPU 池 | 你还不会走工具循环 |
| 微调一个「公司专属模型」当第一件事 | 贵、慢、不解决查数 |
| 让 Agent 直接拥有写权限 | 事故概率不可接受 |
| 一个 Tool 打全部数据库 | 无法鉴权、无法缓存、无法测试 |
| 用聊天记录当唯一知识库 | 口径会漂 |
