# 01 · 会话记忆怎么设计

> 老师先泼冷水：记忆不是把公司知识塞进 ChatClient。  
> 记忆只解决一件事——**同一段对话里，后一句能看懂前一句的指代。**

---

## 1. 三种完全不同的「记得」

| 名字 | 存什么 | 生命周期 | 例子 |
|---|---|---|---|
| 对话记忆 | 最近若干轮 user/assistant | 一个会话 | 「那上周呢」里的「那」 |
| 业务知识 | 制度、口径、SOP | 月/年 | 「可用库存不含残次」 |
| 业务事实 | 库存数字、停机记录 | 分钟～天 | 「A 仓 SKU-1001 = 42」 |

【易混】把 ERP 同步进 ChatMemory，是最常见的架构错误。数字会过期，权限会穿仓，token 会爆炸。

业务知识走 RAG，业务事实走 Tool，对话记忆只走 Memory。

---

## 2. Spring AI 2.0 你必须记住的 API

注册顾问：

```java
@Bean
ChatClient chatClient(ChatClient.Builder builder, ChatMemory chatMemory) {
    return builder
            .defaultAdvisors(MessageChatMemoryAdvisor.builder(chatMemory).build())
            .build();
}
```

**每一次**调用都要带会话 ID，2.0 不再允许省略：

```java
String reply = chatClient.prompt()
        .user(question)
        .advisors(a -> a.param(ChatMemory.CONVERSATION_ID, conversationId))
        .call()
        .content();
```

缺了或为 null：直接 `IllegalArgumentException`。这是特性，不是 bug——防止所有人掉进同一个记忆桶。

【易混】

- 不要写 `PromptChatMemoryAdvisor`（已删除）。
- 不要在 builder 上 `.conversationId("固定值")`（已删除）。
- 不要幻想「不传就用默认会话」。

---

## 3. conversationId 怎么设计

推荐格式：

```text
{userId}:{clientSessionId}
```

例如 `u10086:web-20260909-a91`。

规则：

1. **必须包含用户。** 否则同一浏览器被别人接着聊，会看到上一个人的仓。
2. 客户端可以生成 UUID，存在 localStorage；退出登录必须换。
3. 管理端「新话题」按钮 = 新 UUID。不要无限往同一个 ID 里堆。
4. 不要用公司名当 ID，不要用「default」。

服务端校验：从网关解析出的 `userId` 必须是 ID 的前缀。客户端乱传别人的 ID 一律 403。

---

## 4. 默认：记忆放在工具循环外面

Advisor 默认顺序（2.0）：

- 记忆：`HIGHEST_PRECEDENCE + 200`
- 工具循环：`HIGHEST_PRECEDENCE + 300`

数字更小的更靠外。所以默认是：

```
记忆加载一次
  → 工具循环（内部自己带着 tool 消息多轮）
→ 记忆只写入最终 user + assistant
```

这对你是好事：

- 大多数 `ChatMemoryRepository` 本来就不会存 tool 消息。
- 审计另有表，不必靠记忆还原工具轨迹。
- token 更省：下次请求不会把「调了 queryInventory 返回 42」整段再送进去。

模型下一轮仍然看得到用户的问题和最终回答，足够处理「那上周呢」。上周的数字如果还要准，**再调一次工具**，不要信记忆里的旧数。

在系统提示里写死：

> 涉及库存、订单、停机等数字，即使对话里出现过，也必须重新调用工具。记忆只用于理解指代，不用于当数据源。

---

## 5. 什么时候才把记忆放进循环内

只有当你确实需要模型在**同一轮多步工具**里「记得自己试过什么」并且要把 tool 消息持久化时。

做法：

```java
var toolAdvisor = ToolCallingAdvisor.builder()
        .disableInternalConversationHistory()
        .build();

var memoryAdvisor = MessageChatMemoryAdvisor.builder(chatMemory)
        .advisorOrder(Ordered.HIGHEST_PRECEDENCE + 400)
        .build();
```

仓库必须能序列化 tool 请求/响应。2.0 内置里相对安全的是：

- `InMemoryChatMemoryRepository`（进程内，重启丢，开发可以）
- Redis
- Neo4j

【红线】别把循环内记忆 + 普通 JDBC 记忆仓库想当然组合。写进去可能丢字段，读出来会把对话搞坏。

社区项目 `spring-ai-session` 做事件溯源和压缩，计划更贴近 2.1。主线不依赖它。你先用默认循环外。

---

## 6. 窗口满了怎么办

对话变长，记忆全塞会把工具 schema、RAG 片段挤掉。策略从简单到复杂：

1. **硬切：** 只保留最近 N 轮（例如 8 轮）。简单，够用。
2. **新话题：** 产品上引导「这个问题建议开新会话」。
3. **摘要：** 用 flash 模型把旧轮次收成一段「到目前为止的结论」，替换旧消息。这是进阶，综合项目可以不做。

不要用「无限记忆」当卖点。管理层会话通常很短：问三句、看数、关掉。

---

## 7. 最小可用配置

```java
@Configuration
class MemoryConfig {

    @Bean
    ChatMemory chatMemory() {
        return MessageWindowChatMemory.builder()
                .maxMessages(16)
                .build();
    }
}
```

开发用内存即可。上试用再换 Redis：以「按 conversationId 隔离」为验收，而不是先追求集群。

---

## 8. 【必做】

1. 给 ChatClient 挂上 `MessageChatMemoryAdvisor`。
2. 前端每次带 `conversationId`，后端校验属于当前用户。
3. 同一 ID 连续问：「A 仓 SKU-1001 库存？」→「那 B 仓呢？」第二句必须能理解「同一 SKU」。
4. 换一个 ID，不应再知道上一句的 SKU。
5. 故意不传 ID，确认是 400/明确错误，而不是静默共用。
