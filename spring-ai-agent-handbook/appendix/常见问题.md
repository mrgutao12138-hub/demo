# 常见问题（FAQ）

> 老师答疑口吻，随手查。至少 25 问；按主题分组。  
> 主线版本：Spring Boot 4.1 · Spring AI 2.0.0 · DeepSeek 云端。

---

## 一、定位与价值

### Q1. 这个 Agent 会不会替代我们公司现有的 BI 看板？

**不会替代，是互补。**

BI 看板适合**固定指标、每天看同几张图**——周转率、销售额、产能利用率，刷新节奏明确，权限在报表层已经固化。  
Decision Copilot 适合**临时的、跨系统的、需要解释的问题**——「对比 A/B 仓同一 SKU 结合超期 PO 谁该先补」「昨天停机 30 分钟和产出缺口对得上吗」。这类问题要调多个 Tool、拼口径、给建议，看板往往没有现成页。

**正确姿势：** 看板继续服务日报；Agent 服务「开会前五分钟才想到的追问」。第一期不要承诺替代 BI。

---

### Q2. 领导问：和 ChatGPT 网页版有什么区别？

三点就够：

1. **数字来自你们库**，不是模型记忆；  
2. **制度口径来自 RAG**，可指到文档条款；  
3. **写操作默认没有**，有审计、权限、租户。

网页版是通用聊天；你做的是**带护栏的企业决策接口**。

---

### Q3. 第一期到底要解决管理层哪三类问题？

讲义默认三域，你可换成自己公司的：

| 域 | 示例问题 |
|---|---|
| 库存 WMS | 某仓某 SKU 可用量、缺货风险 |
| 采购 ERP | 超期 PO、供应商 Top N、在途影响 |
| 设备 EMS | 停机时长、产线缺口对齐 |

每域 2～3 个 Tool 即可毕业演示，不要一口吃 200 张表。

---

## 二、模型与训练

### Q4. 要不要先微调一个「公司专属大模型」？

**第一期不要。** 微调贵、慢，且不解决「库存数是多少」——数仍要从数据库来。  
先把 **Tool + RAG + 评测集** 做扎实。微调适合：有大量标注、模型总在固定术语上翻车、且你有算法团队维护时——那是第二年的事。

---

### Q5. Flash 还是 Pro？能不能全用 Flash 省钱？

| 场景 | 建议 |
|---|---|
| 闲聊、意图粗分、简单 FAQ | `deepseek-v4-flash` |
| 对比、归因、风险建议、多工具推理 | `deepseek-v4-pro` |

全用 Flash 会省一点钱，但复杂问题工具选错、推理浅，**返工成本更高**。讲义推荐双 `ChatClient` Bean 路由。

---

### Q6. 思考模式（thinking）什么时候开、什么时候关？

**开：** 多步对比、因果归因、「该不该补货」类需要推理链的问题。  
**关：** 简单查数、路由、结构化字段填充。

思考模式增加 **Token 与延迟**；管理层 UI 默认只展示最终结论，不展示思考过程。配置写在 `spring.ai.deepseek.chat.thinking`，与业务代码隔离，方便按环境开关。

---

### Q7. 上下文窗口满了怎么办？

按优先级砍：

1. 缩短 system（细则进 RAG）；  
2. 限制会话记忆轮数（`MessageWindowChatMemory`）；  
3. 减少工具数量或上 Tool Search；  
4. 降低 RAG `topK`；  
5. 对历史做摘要再注入。

**不要**指望换更大窗口就不做 RAG——制度全文照样塞不下。

---

### Q8. 模型升级了我们要跟着升吗？

学习期 **钉死 2.0.0 + Boot 4.1**。生产升级时：

1. 换 model 名或 starter 小版本；  
2. **全量跑评测集**；  
3. 看 Release Notes 里 Advisor、配置前缀变更。

质量靠评测集稳住，不靠赌「新模型更聪明」。

---

## 三、技术栈选择

### Q9. 我们是否必须学 Python？团队只会 Java。

**主服务不必 Python。** Agent 的价值在业务 Tool，你的 Service、权限、事务已在 Spring 里。  
Python 生态示例多，但多一门运行时 = 多一套部署、监控、故障域。算法组若用 Python，可通过 HTTP 或 MCP 暴露能力，你在 Java 里编排。  
你要学的是 **Agent 工程概念**，语言是通用的。

---

### Q10. 为什么选 Spring AI 2.0 而不是自己拼 HTTP？

第 30 天你会手写：消息拼接、工具循环、流式解析、重试、token 统计、多模型差异——这些正是框架工作。企业复杂度应在**业务工具与护栏**，不在 RestClient。

---

### Q11. ChatClient 和 ChatModel 我到底用哪个？

**日常只用 ChatClient。** ChatModel 是底层，仅在你手写工具循环或调试时碰。2.0 的设计就是把循环放到 `ToolCallingAdvisor`。

---

### Q12. 1.x 教程还能看吗？

能看**概念**（Token、RAG、幻觉），**代码别抄**。见到 `toolNames`、`QuestionAnswerAdvisor` 一条龙、`internalToolExecutionEnabled` 直接关掉。

---

## 四、RAG 与数据

### Q13. 接了 ERP 还要 RAG 干什么？

**数字走 Tool，口径走 RAG。**  
「可用量多少」是 SQL；「可用量是否含质检待放行」是制度定义。没有 RAG，模型会「像那么回事」地编口径——比数字编错更隐蔽。

---

### Q14. DeepSeek 配置了为什么还不能做向量检索？

DeepSeek **对话 API 不提供 embedding**。向量必须用另一套 `EmbeddingModel`（讲义学习期用 `spring-ai-starter-model-transformers`）。架构图永远画两个模型框。

---

### Q15. 制度 PDF 很多，要全部塞进 Prompt 吗？

**不要。** 走切分 → 向量 → 按需检索。全文塞 prompt 会 Token 爆炸、贵、慢，且中间段落模型「看不见」。

---

### Q16. 检索不到制度时能不能让模型自由发挥？

**决策系统默认不能。** 必须答「未检索到相关制度」，关闭 `allowEmptyContext(true)`。宁可少说，不可编条款。

---

### Q17. EMS 和 MES 有什么区别？我们该接哪个？

简单说：

| 系统 | 侧重 |
|---|---|
| **EMS** | 设备台账、停机、维保、OEE |
| **MES** | 工单、工序、产线执行、报工 |

管理层问「昨天哪条线停了 30 分钟」多来自 EMS；问「某工单进度」来自 MES。讲义 part-06 用 EMS 停机作示例；你若 MES 更痛，换一个等价 Tool 即可，原则仍是只读 + 宽表。

---

### Q18. 能不能让 Agent 自动生成 SQL 查库？

**不作为默认方案。** 模型生成的 SQL 难审计、难鉴权、易被注入，一次全表扫描能把从库打爆。  
默认：**固定 Tool + 指标字典 + 白名单参数**。若领导坚持 Text-to-SQL，必须关在笼子里：只读库、表白名单、行数上限、人工审核——见 part-06 反例章。

---

### Q19. 宽表是什么？为什么要同步宽表？

宽表是为**决策查询**预聚合的只读大表，字段面向业务问题（仓+SKU+可用量+在途+更新时间），不是 ERP 第三范式原样。  
Agent 只打宽表，ERP 压力可控，SQL 可评审、可缓存。同步频率按业务接受（小时/天），回答里必须写**数据截止时间**。

---

## 五、工具、Agent 与安全

### Q20. 领导要求「能自动下单」怎么办？

**第一期明确不做自动写操作。** 正确回应：

1. 演示「建议补货单」JSON 或页面草稿，**人工确认**后才进 ERP；  
2. 解释写错库存比答错一句话严重两个数量级；  
3. 路线图：第三季度可做「工单流 + 双人复核」——不是模型直接 `UPDATE`。

讲义红线：不提供 `updateInventory` 类工具。

---

### Q21. 数据能否出域？怎么向安全部门解释？

DeepSeek 云端意味着：**问题文本、检索片段、工具返回摘要**会发到模型服务商。  
向安全说明：

| 项 | 措施 |
|---|---|
| 出域内容 | 脱敏后的制度片段 + 聚合业务数字，非完整客户名单 |
| 密钥 | 环境变量，不进 Git |
| 权限 | 工具层二次校验，模型看不到无权仓 |
| 替代 | 绝密场景走扩展篇本地 Ollama / 内网模型 |
| 审计 | 谁问了什么、调了什么工具，可追 |

准备一份《数据分级与出域字段表》，比口头承诺管用。

---

### Q22. 怎么防 Prompt 注入？

多层：

1. system 红线写死，但不迷信；  
2. 工具权限不依赖模型「自觉」；  
3. RAG 文档当不可信输入；  
4. 敏感操作无工具即无能力；  
5. 定期用评测集跑注入用例。

用户说「忽略以上规则」——应仍拒绝列手机号。

---

### Q23. 多租户怎么做？一个公司多个事业部算吗？

算。每一层都要带 `tenantId` / `org`：

- API 鉴权写入 `TenantContext`；  
- 每个 Tool SQL 强制 `AND tenant_id = ?`；  
- RAG `FILTER_EXPRESSION` 过滤 `org`；  
- `CONVERSATION_ID` 含用户与租户，防记忆串台。

多租户不是多建几个 ChatClient 就完事。

---

### Q24. 并发大了怎么办？模型 API 和数据库会不会被打爆？

1. **限流**：按用户/IP 令牌桶；  
2. **连接池**：Hikari 上限与只读库容量匹配；  
3. **缓存**：热点 SKU 查询短 TTL 缓存（注意新鲜度标注）；  
4. **异步**：管理层场景多数可接受 3～10 秒，不必盲目并发调模型；  
5. **熔断**：模型 5xx 时降级文案「请稍后再试」，别无限重试烧 Key。

---

### Q25. 两个 ChatModel Bean 启动报错怎么办？

定义 `flash` 和 `pro` 两个模型时，要 `@Primary` 一个默认，或全部显式 `ChatClient.builder(specificModel)`。见 `踩坑手册.md` 第 11 节。

---

## 六、记忆、成本与工程

### Q26. 会话记忆存在哪？Redis 还是数据库？

| 阶段 | 建议 |
|---|---|
| 学习 / 演示 | `InMemoryChatMemoryRepository` |
| 试用 | Redis |
| 生产 | Redis 或 JDBC（注意 tool 消息支持） |

**默认记忆放工具循环外**；JDBC 对 tool 消息支持有限，别盲目「循环内记忆」。

---

### Q27. 每次都要传 CONVERSATION_ID 吗？太麻烦了。

必须传。否则所有人共用一个会话，或永远没有多轮上下文。  
API 层用 `userId + clientSessionId` 生成即可，前端只存一个 UUID。

---

### Q28. 100 个管理层每人每天 20 问，一个月大概多少钱？

粗算公式（需按实际 usage 调整）：

```
月费 ≈ 人数 × 日均问数 × 30 × (平均输入 Token + 平均输出 Token) × 单价
```

学习期用 flash 试错、pro 做演示；开 thinking 会明显上浮。  
part-08 要求你能给出**区间估算**，不是精确到分——领导要的是量级与可控开关（限额、路由 flash）。

---

### Q29. 流式输出一定要加 webflux 吗？

**要。** Spring AI 2.0 流式走 Reactive 栈，仅有 `spring-boot-starter-web` 会踩坑。见 `踩坑手册.md`。

---

### Q30. MCP 要不要第一期就上？

**不要。** MCP 是「远程工具插座」，适合接已有工具进程或 IDE 生态。你的 ERP/WMS 主路径仍是 Java `@Tool` + 只读库。part-04 建立概念即可，扩展篇再深水。

---

### Q31. 工具多了 Token 爆炸怎么办？

1. 合并相关工具；  
2. 精炼 `@Tool` description，去掉废话；  
3. 上 `spring-ai-starter-tool-search-advisor` 按需披露 schema；  
4. 意图路由：先分类再挂子集工具。

小于 15 个工具通常不必 Tool Search。

---

### Q32. 结构化输出就能保证数字正确吗？

**不能。** 结构化只保证**格式**——字段齐、类型对。数字必须来自 Tool 返回值，由 Java 填进 DTO，或让模型只组织 Tool 已返回的数。`validateSchema()` 解决不了幻觉数值。

---

### Q33. Maven 下不下来 spring-ai-bom 2.0.0？

镜像或公司私服未同步 Boot 4 / AI 2.0。见 `踩坑手册.md` 第 15 节：调整 `settings.xml` 或请运维同步 central。

---

### Q34. 评测集要多少条？怎么建？

part-08 要求 **≥20 条**，覆盖：

- 命中查数 / 命中 RAG  
- 未命中制度  
- 拒写  
- 越权仓  
- Prompt 注入  
- 混合问题  

改 prompt 或工具前后各跑一遍，记录通过率。没有评测集就没有迭代，只有「感觉好像好了」。

---

### Q35. 答错了谁负责？怎么追？

产品层面：

1. 回答带来源卡片（哪张表、哪条制度、截止时间）；  
2. 审计日志可追溯谁何时问了什么；  
3. 明确免责声明：**辅助决策，不替代人工审批**；  
4. 评测集与工单闭环：错例入库，改 Tool/RAG/提示，而非怪模型「今天心情不好」。

## 七、团队与组织

### Q36. 我们需要专职算法工程师吗？

**第一期不需要。** 需要会 Java、会 SQL、会写提示与评测的业务架构型工程师。算法在微调、训练 embedding、复杂排序时出现——那是增强项。

---

### Q37. 前端不会写怎么办？

讲义 part-08 给**最小 HTML + fetch SSE**，零框架能演示。有前端同事再换 Vue/React 皮。不要在 UI 上卡毕业。

---

### Q38. 运维/DevOps 要准备什么？

模板 B 已含 Actuator：`/actuator/health`、`metrics`。上线清单见 part-09：密钥管理、多环境配置、限流、日志采集、模型不可用降级。

---

### Q39. 和现有 SSO 怎么接？

在 Spring Security（或公司统一网关）鉴权后，把 `userId`、角色、可访问仓列表放进 `UserContext`，Tool 内强制使用——**不要**让模型自己传 `userId` 参数就算鉴权。

---

### Q40. 学完了还是跟不上 Spring AI 更新怎么办？

1. 关注 **2.0.x** Release Notes，别追每个 SNAPSHOT；  
2. 扩展篇 `04-SpringAI1到2迁移.md` 看懂旧文；  
3. 维护评测集，升级后一键回归；  
4. 业务代码只依赖 `ChatClient` 与自有 Tool，换 starter 成本可控。
