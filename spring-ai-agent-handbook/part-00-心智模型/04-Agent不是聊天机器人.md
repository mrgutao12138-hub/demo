# 04 · Agent 不是聊天机器人

> 同学，这一讲可能有点「扫兴」。  
> 你会看到很多团队 proudly 演示「我们也有 AI 了」——一个聊天框接 DeepSeek。我要告诉你：**那很可能还不是 Agent，甚至不是合格的企业 ChatBot。**

---

## 你现在在哪

你已经：

- 会把 Spring AI 分层和 JDBC 类比（第 01 讲）；
- 知道模型不是数据库（第 02 讲）；
- 知道 Prompt 有 Token 和窗口限制（第 03 讲）。

产品或领导可能还会说：

「ChatGPT 网页版都能聊业务了，你们 Spring 接一下 API 不就一样吗？」

**你现在需要一把尺子：什么算「聊天玩具」，什么算「管理层辅助决策 Agent」。**  
没有这把尺子，Part 08 综合项目会被砍成「做个聊天窗口」，安全与 DBA 也会拒绝配合。

## 1. 聊天机器人在做什么

### 1.1 消费级产品（ChatGPT / DeepSeek 网页）的典型路径

```
用户打字
   │
   ▼
浏览器 ──HTTPS──► 厂商云端大模型
   │
   ▼
流式文本回到界面（Markdown、表格看起来很美）
```

特点：

- **极低的接入成本**：注册账号就能用；
- **极高的通用性**：写诗、写代码、聊战略；
- **事实来源不透明**：数字、引用、政策条款可能是 **生成的**；
- **无企业身份**：不知道你是谁、你能看哪个仓；
- **无稳定 Tool**：不能官方地「替你去查 WMS 第 17 号只读库」；
- **无审计**：谁问了什么、答用了什么数，不在你们 SIEM 里。

这对 **个人效率** 很好；对 **ERP 管理层决策** 不够。

### 1.2 企业内部「伪 Agent」：ChatController 套壳

很多 Java 团队的 v0.1：

```java
@PostMapping("/chat")
public String chat(@RequestBody String msg) {
    return chatClient.prompt().user(msg).call().content();
}
```

演示时 **好像** 能聊。但：

- 没有 `@Tool` → 库存数字 **来自模型幻觉**；
- 没有 SSO → 任何人问任意 SKU；
- 没有 audit log → 合规不过；
- 没有 Advisor 护栏 → Prompt 注入轻易骗过；
- system prompt 写「你是助手」→ **没有「不得编造、必须 Tool」的宪法**。

这是 **聊天机器人**，不是 **Agent**。  
连「只读决策辅助」都算不上，只能叫 **未受控的生成接口**——安全部门应直接叫停。

## 2. Agent 在做什么：多出来的「手、眼、规矩」

### 2.1 定义（本讲义采用）

**企业 Agent** = 在受控入口后，由 **ChatClient + Advisor 链** 编排 **ChatModel**，并通过 **Tool / RAG / Memory** 连接企业事实与文档，在 **权限与审计** 下完成 **多步任务**，服务于 **明确业务目标**（此处：管理层辅助决策）。

关键词：**受控、Tool、Advisor 循环、权限、审计、业务目标**。

### 2.2 和 Java 组件的再对照

| 能力 | 聊天套壳 | 企业 Agent |
|------|----------|------------|
| 入口 | 匿名或弱鉴权 | SSO / RBAC，绑定组织范围 |
| 事实 | 模型生成 | **Tool → 只读 Service → SQL/视图** |
| 文档口径 | 模型编造 | **RAG → VectorStore → 可追溯片段** |
| 多步 | 单轮文本 | **ToolCallingAdvisor 循环** |
| 会话 | 可选 | **Memory（会话级缓存）**，不替代 ERP |
| 观测 | 无 | traceId、tool 日志、token usage、耗时 |
| 边界 | 模糊 | **第一版只读；写操作清单明确禁止** |

### 2.3 Agent 循环：不是 Filter 只走一次

Spring AI 2.0 里，**ToolCallingAdvisor** 让一次用户提问可能经历：

```
用户：ABC 华东库存够吗，上周 PO 到了没？
   │
   ▼
模型：我要调 queryStock(sku=ABC, wh=HD)
   │
   ▼
Advisor 执行 @Tool → 返回 JSON → 写回 Message 列表
   │
   ▼
模型：我要调 queryPoReceipt(poHint=上周, sku=ABC)
   │
   ▼
Advisor 再执行 @Tool → 返回 JSON
   │
   ▼
模型：生成中文结论（引用两次 Tool 字段）
```

这才是 **Agent 味道**：**模型负责规划和表达，Java 负责执行与边界。**  
聊天机器人通常 **没有中间两次 Tool**，一次生成结束——快，但 **不可信**。

类比：**Filter 链里有一个会「自己决定要不要重定向、重定向几次」的智能 Filter**——你要在代码里限制最大循环次数，防止死循环与 Token 爆炸。

## 3. ChatGPT 网页 ≠ 企业 Agent：至少七条差异

请背熟，评审时用：

1. **数据主权**：网页对话进厂商云；企业 Agent 应最小化出网字段、合同约束、可选私有化（本讲义主线是 DeepSeek API + 脱敏）。
2. **事实来源**：网页无你们 WMS；Agent 必须 Tool 查只读库。
3. **身份与权限**：网页不知道用户是哪个工厂厂长；Agent 每个 Tool 带 `@PreAuthorize` 或等价校验。
4. **审计**：网页无法导出「张总在 9:03 问了 SKU X，用了库存视图 Y」；Agent 必须全链路日志。
5. **产品目标**：网页是通用聊天；Agent 是 **决策辅助**，输出格式要 **结论 + 依据 + 建议（只读）**。
6. **稳定性**：网页功能随厂商迭代；Agent 的 Tool 契约、Prompt 版本 **由你 Git 管理**。
7. **责任边界**：网页错了用户「自己辨别」；企业里错了可能 **错误停产、错误补货**——所以第一版 **禁止自动写库**。

【红线】**不要让管理层把 Agent 回答截图当「系统官方数据」而不看 Tool 依据。** UI 上应展示「数据来源：库存只读视图 v2，查询时间 2026-09-09 10:03」。

## 4. 第一版「只读 Agent」：能做什么、不做什么

### 4.1 第一版要做（辅助决策）

- 自然语言问 **只读** 指标：库存、PO 状态、停机统计、OEE 摘要；
- 跨 Tool 归纳：**风险清单 + 解释 + 建议下一步人工动作**；
- RAG 查 **制度/SOP**：「超期 PO 升级流程是什么」；
- 生成 **建议单草稿**（PDF/工单 URL），**不写入 ERP**；
- 完整 **审计与 trace**。

### 4.2 第一版明确不做（即使用户撒娇）

| 禁止行为 | 原因 |
|----------|------|
| 自动改库存、冻结、调拨 | 幻觉 + 非确定 + 无审批 = 生产事故 |
| 自动创建/修改采购订单 | 财务与供应商合规 |
| 自动下发 EMS 控制指令（启停设备） | 人身与产线安全 |
| 绕过权限查其他事业部数据 | 违法与内控 |
| 无 Tool 确认直接报数字 | 违反本讲义【红线】 |

话术模板（对业务）：

> 「第一版是 **班长 + 望远镜**，帮你看清数据和制度，不是 **遥控机械臂**。  
> 建议可以自动生成，**按钮必须在人手里**。」

### 4.3 「建议补货」怎么做得安全

可以：

- Tool 查库存与安全库存；
- 模型输出：「建议创建补货申请，数量建议 200，理由：……」；
- 系统生成 **待办链接** 到现有 ERP 审批流，**人工点确认**。

不可以：

- Tool 里调 `updateInventory()` 或发消息给 WMS 直接加库存。

## 5. 三个管理层问题：聊天 vs Agent 对照

### 5.1 库存：「ABC 华东还能撑几天？」

| 聊天套壳 | 企业 Agent |
|----------|------------|
| 模型编「约 7 天」 | Tool 查可用量、日均消耗，Java 算天数 |
| 无法引用 SKU 定义 | 返回里带 sku、warehouse、asOfTime |
| 无权限 | 只能查用户所属组织仓 |

### 5.2 超期采购：「哪些 PO 超期影响 3 号产线？」

| 聊天套壳 | 企业 Agent |
|----------|------------|
| 列举「看起来像真的」PO 号 | Tool 查 PO 宽表视图，产线映射来自主数据 |
| 制度口径可能错 | 超期定义 RAG 引制度 + Tool 算天数 |
| 无法追责 | 日志记录 SQL 参数与返回条数 |

### 5.3 设备停机：「空压站昨天非计划停机多久？」

| 聊天套壳 | 企业 Agent |
|----------|------------|
| 「大约 2 小时」 | Tool 查 EMS 停机事件视图，分钟级精确 |
| 混淆计划维护与非计划 | Tool 带 `downtimeType=UNPLANNED`  filter |
| 不能下钻 | 第二个 Tool 分页查明细（仍只读） |

## 6. 企业 Agent 最小合格清单（MVP Checklist）

上线前自检，少一项都不要叫 Agent MVP：

- [ ] 每个涉及数字的回答，日志里能对应 **至少一次 Tool 调用** 或明确「无数据」；
- [ ] 所有 Tool **只读**，且走现有权限体系；
- [ ] system prompt 含 **禁止编造数字** 与 **只读边界**；
- [ ] SSO 或等价鉴权，session 与 audit user 绑定；
- [ ] traceId 贯穿 Controller → Advisor → Tool → SQL；
- [ ] Token usage 与 P95 延迟可见；
- [ ] 用户界面展示 **数据时间戳与来源视图名**；
- [ ] 安全评审过 Prompt 注入与越权用例；
- [ ] 产品签字 **不做清单**（不改库存、不下单、不遥控设备）。

## 7. 和「Copilot for 研发」的区别（避免目标漂移）

管理层 Agent **不是**：

- IDE 里补全 Java 代码；
- 帮程序员写 SQL 草稿（那是研发 Copilot，权限模型不同）；
- 给全员的一般问答知识库。

管理层 Agent **是**：

- 服务厂长、采购经理、设备经理；
- 回答 **决策问题**；
- 数字 **来自 ERP/WMS/EMS**；
- 语气 **短、稳、可追责**，不是论文体。

若项目范围被改成「公司通用聊天」，请拉回第 05 讲全景图重新对齐。

## 8. 课堂角色扮演：三次方案评审

### 8.1 评审一：「先上线聊天，Tool 下个迭代」

**产品：** 领导下周要看 Demo，先接 DeepSeek 聊天，Tool 以后再说。  
**你应该答：** Demo 若无 Tool，**库存数字不可展示为事实**；可 Demo「制度 RAG + 假数据环境」，但 **必须标注演示数据**；生产 MVP 与聊天 Demo 要分环境。引用本章 MVP Checklist 第 1、8 条。

### 8.2 评审二：「Agent 自动锁库存防止超卖」

**业务：** 模型发现 available<0 就调 WMS 锁库。  
**你应该答：** 违反第一版只读；幻觉与非确定会导致 **错误锁库**；锁库是 **写操作**，走现有审批与 WMS API，不能由 ToolCallingAdvisor 默认循环执行。引用第 02 讲幻觉与第 05 讲不做清单。

### 8.3 评审三：「跟 ChatGPT 一样，加个 iframe 就行」

**信息部：** 内网嵌 OpenAI 网页。  
**你应该答：** 无 SSO 映射、无 Tool、无审计、数据出网不可控；**ChatGPT 网页 ≠ 企业 Agent**。应做 Spring Agent API + 只读 Tool + 内网 UI。引用本章七条差异。

三次评审能答顺，你就有资格参加自家项目架构会了。

### 8.4 UI 上「像聊天」没关系，「本质是聊天」才有问题

界面可以是气泡对话框——**交互形态不等于系统定性**。定性看 **后台有没有 Tool 审计链**。

建议在 UI 固定展示：

- **结论区**
- **依据区**（Tool 返回字段摘要）
- **来源区**（视图名、asOfTime、制度 docId）
- **免责声明**：「建议需人工确认，不自动执行写操作」

这样厂长 **看起来在聊天**，实际上在用 **决策辅助系统**。

### 8.5 Agent 循环上限

ToolCallingAdvisor 可能多轮。工程上要设 **maxToolCallsPerUserMessage**（具体配置 Part 04），防止：

- 模型死循环同一个 Tool；
- Token 爆；
- SQL 库被打爆。

类比：**Filter 链不能无限 forward**；Agent 循环也要有 **熔断**。

### 8.6 「辅助决策」四个字怎么落地

「辅助」= 人做最后决定；「决策」= 输出要有 **结论、依据、可选行动建议**，不是闲聊。

合格答复结构（第一版可在 system 里强制）：

```
【结论】一句话
【依据】Tool 字段 / 制度 docId
【建议】仅只读动作：联系谁、查哪张单、走哪条审批——不含自动执行
【数据时间】asOfTime
```

若只有一段 Markdown 小作文、没有依据区—— **仍是聊天机器人**，不是辅助决策 Agent。

### 8.7 和 Copilot、知识库问答的边界（再划一次）

| 系统 | 用户 | 典型问题 | 数字从哪来 |
|------|------|----------|------------|
| 研发 Copilot | 程序员 | 生成代码/SQL 草稿 | 编辑器上下文，人负责执行 |
| 企业知识库问答 | 全员 | 制度/general FAQ | RAG 文档 |
| **管理层 Agent（本讲义）** | 厂长/经理 | 库存/PO/停机 | **Tool+SQL** |

三套系统 **可以共存**，不要混成一个「公司 AI」大杂烩。**权限模型不同**，硬合并会出事故。

### 8.8 第一版 Agent 的「Definition of Done」

跟产品对齐 DoD，避免无限 scope：

1. 三个场景（库存/超期 PO/停机）各 **至少 1 个 Tool** 跑通；
2. 每个数字答复 **可关联 Tool 日志**；
3. SSO 用户 **不能越权仓/产线**；
4. **不做清单** 写进 PRD 且 UI 有免责声明；
5. 内测 **10 人 × 20 问**，抽检无幻觉数字。

达不到 5 条，不叫 Agent MVP，叫 **技术验证 Demo**，只能在内网实验室展示。

### 8.9 审计日志最小字段（与聊天套壳对比）

| 字段 | 聊天套壳 | 企业 Agent |
|------|----------|------------|
| userId | 可选 | 必填 |
| userMessage | 有 | 有 |
| assistantText | 有 | 有 |
| toolName + args | 无 | 必填 |
| sqlView / rowCount | 无 | 建议有 |
| promptTokens | 无 | 必填 |
| traceId | 无 | 必填 |

评审时把这张表给安全看，比讲「我们用了 Spring AI」有说服力。

### 8.10 从聊天升级成 Agent 的最小改造清单

已有 ChatController 套壳时，按顺序改， **不要一次全上**：

1. 加 system 只读宪法；  
2. 加 1 个只读 `@Tool` + ToolCallingAdvisor；  
3. 加 userId/traceId/tool 日志；  
4. UI 加依据区与 asOfTime；  
5. 加 SSO 与 Tool 内权限；  
6. 写不做清单进 PRD；  
7. 再扩 Tool 到三场景。

跳过 1～4 直接扩功能，等于 **给聊天机器人贴 Agent 标签**。

### 8.11 为什么「流式输出」不改变 Agent 本质

Spring AI 支持 `stream()`，UI 可以打字机效果。**流式只改变体验，不改变事实链**：该走的 Tool 仍要走，该写的 audit 仍要写。不要因为有流式，就跳过 Tool 先喷字——那是 **更流畅的聊天套壳**，不是 Agent。

### 8.12 本讲小结

聊天 = 单轮文本；Agent = Tool 循环 + 权限 + 审计 + 只读。  
ChatGPT 网页缺 Tool、缺 SSO、缺审计。  
第一版不做：改库存、下单、遥控设备。  
辅助决策 = 结论 + 依据 + 人工确认。  
04 讲毕业。

**验收前自测：** 能否列举 MVP Checklist 9 项中的任意 5 项？能否说明 ToolCallingAdvisor 循环与单轮 chat 的差异？能，04 讲过关。

**关键词：** 聊天套壳、企业 Agent、Tool 循环、审计、SSO、只读、不做清单、ChatGPT 网页、辅助决策、MVP Checklist。

**本节复盘：** 界面像聊天没关系，后台必须有 Tool 循环、权限、审计与只读宪法。ChatGPT 网页缺企业连接与追责能力，不能当内网 Agent 替身。第一版明确拒绝自动改库存与自动下单。辅助决策的输出要有结论、依据与人工确认门——这才是厂长需要的系统，不是三天套壳 Demo。请把 MVP Checklist 打印贴在工位，评审时用。与产品对齐 DoD 后再开发，避免 Agent 项目变成 endless 聊天需求池。下一讲用 ASCII 全景图把 Tool、RAG、DeepSeek 与 ERP 视图串成一条可落地的只读决策链。请完成角色扮演作业，练熟对产品的「不做自动写库」话术。记住：**没有 Tool 审计日志的功能，不配叫企业 Agent MVP。** 流式 UI、Markdown 排版、企业微信入口都可以后加；**Tool + 权限 + 只读 + 审计** 这四样才是 MVP 的脊梁。产品若要求跳过，请用本章 checklist 与审计字段表沟通，不要默默妥协。

### 8.14 三场景「聊天 vs Agent」一句话对照（背诵用）

- **库存：** 聊天编数量，Agent 调 `queryAvailableStock` 后归纳。  
- **超期 PO：** 聊天编单号，Agent 查 `v_erp_po_overdue` 并可 RAG 制度。  
- **停机：** 聊天估小时，Agent 查 `v_ems_downtime_event` 聚合分钟。  

三句背顺，你就不会在产品会上被「先做聊天」带偏。辅助决策系统的尊严，在于 **每一句带数字的话都能追溯到 Tool 或明确标注无数据**。完成角色扮演作业后进入 Part 00 收官全景讲。企业里最常见的失败，就是把 **ChatGPT 的交互** 当成 **Agent 的架构**；你现在已经具备反驳这种失败的能力。请把 **不做清单** 与 **MVP Checklist** 合并成一页纸，下一讲画架构图时放在手边。04 讲全部正文结束，去做【必做】作业吧。过关后再打开 05 全景讲。记住：ChatGPT 网页永远不是本项目的架构模板。04 讲正文完结。去做作业。加油，同学。阅读愉快。

## 常见误解

| 误解 | 正解 |
|------|------|
| 「有聊天界面就是 Agent」 | 界面只是壳；无 Tool、无审计、无权限不是 Agent。 |
| 「模型升级成 reasoning 就是 Agent 了」 | 推理只改善规划；事实仍要 Tool，边界仍要只读。 |
| 「领导要用，所以可以先上线再补审计」 | 管理层问答涉及经营数据，**先审计再内测**，不是反过来。 |
| 「Tool 太慢，先让模型答，以后再查库」 | 先查库是原则；慢则优化 SQL/缓存，不是先幻觉上线。 |
| 「Agent 会自动越来越懂我们公司」 | 不会 magically；懂公司靠 Tool/RAG/Prompt 版本迭代与人工运营。 |
