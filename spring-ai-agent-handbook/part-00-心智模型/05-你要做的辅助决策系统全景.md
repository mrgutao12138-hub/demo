## 1. 系统目标：一句话 + 边界

### 1.1 一句话

> **给 ERP/WMS/EMS 管理层用的、只读的自然语言决策辅助入口：数字来自企业库与制度文档，结论可解释、可审计，不自动改业务数据。**

### 1.2 用户是谁

- 工厂厂长、仓储经理、采购经理、设备/能源经理；
- 事业部管理层（看汇总与风险，不是仓库文员录单）。

### 1.3 成功长什么样

用户问：

「ABC 在华东仓可用库存多少，离安全库存差多少，上周下的 PO 到了多少？」

系统在 **10～30 秒级**（视 Tool 与 SQL 性能）返回：

- **结论**：三句话以内；
- **依据**：库存视图字段、PO 到货字段、查询时间；
- **建议（只读）**：「建议跟进 PO-xxxx，联系采购员张三」—— **不创建 PO、不改库存**。

后台留下：谁问、问了什么、调了哪些 Tool、SQL 参数摘要、token usage、traceId。

### 1.4 技术栈（本讲义冻结）

```
Java 21（推荐） / Spring Boot 4.1.x
Spring AI BOM 2.0.0
DeepSeek（spring-ai-starter-model-deepseek）
Embedding + VectorStore（Part 05 展开，如 PGVector / Redis Stack 等）
只读 JDBC / MyBatis 访问 ERP/WMS/EMS 宽表或视图
```

不走 Python 主线；不把 ChatGPT 网页当组件。

## 4. 三个管理层场景端到端走读

### 4.1 场景 A：库存与安全库存（WMS + ERP）

**用户问题：**

「SKU ABC 在华东仓（HD）可用库存多少？够不够安全库存？若不够，建议在途 PO 有哪些？」

**走读：**

1. **入口** 校验用户是否有 HD 仓读权限。
2. **ChatClient** 加载 system：「数字必须来自 Tool；只读；不得改库存。」
3. **Memory** 若上一轮问过 ABC，带上 `lastSku` 减少重复澄清。
4. **模型** 规划调用：
   - `queryAvailableStock(sku="ABC", warehouse="HD")`
   - `querySafetyStock(sku="ABC", warehouse="HD")`
   - 若 available < safety → `queryOpenPoInTransit(sku="ABC", warehouse="HD")`
5. **@Tool** 内部：
   - `InventoryReadService` → 视图 `v_wms_available_stock`（只读账号）；
   - 返回精简 JSON：`qtyAvailable`, `uom`, `asOfTime`。
6. **Java 可选** 在 Tool 或后置 Advisor 做 `available - safety` 算术，**不让模型心算**。
7. **模型** 生成中文：结论 + 引用 Tool 字段 + 建议「跟进 PO-xxx」（**不创建 PO**）。
8. **日志** traceId + 3 次 Tool 名 + token usage。

**RAG 是否参与？**  
一般 **不参与** 数字；若用户问「安全库存定义按哪份制度」，再 RAG 制度 PDF。

**明确不做：** 自动创建补货单、自动调拨、自动改 `available_qty`。

---

### 4.2 场景 B：超期采购与产线影响（ERP）

**用户问题：**

「哪些采购订单超期未到货，会影响 3 号产线下周排产？按公司制度谁该升级处理？」

**走读：**

1. **Tool** `queryOverduePo( lineCode="L3", daysOverdue>=? )`  
   → 只读视图 `v_erp_po_overdue` + 物料与产线 BOM 映射表。
2. **返回** TopN PO：poNo、supplier、dueDate、daysOverdue、material、estimatedLineImpact。
3. **RAG** 检索《采购管理制度》里 **超期升级** 章节，注入 Prompt（Top3 段，带 docId）。
4. **模型** 综合：**事实表 + 制度片段** → 清单 + 「按制度应升级至 XX 角色」。
5. **Memory** 可选：用户接着问「那 PO-7788 呢？」—— 带上轮实体。

**明确不做：** 自动给供应商发催货邮件、自动改 PO 日期、自动取消 PO。

**和聊天的差别：** 超期天数、PO 号 **必须** 来自 SQL；制度 **必须** 标注 RAG 来源；不能模型「编造升级流程」。

---

### 4.3 场景 C：设备非计划停机（EMS）

**用户问题：**

「空压站（asset=AC-01）昨天非计划停机多久？近 30 天同类非计划停机几次？最长一次原因是什么？」

**走读：**

1. **Tool** `queryUnplannedDowntime(assetId="AC-01", from, to, granularity=SUMMARY)`  
   → 视图 `v_ems_downtime_event`（`type=UNPLANNED`）。
2. **返回聚合 JSON**：`yesterdayMinutes`, `last30DaysCount`, `maxEventReasonCode`, `maxEventMinutes`。
3. 若用户追问「最长那次几点开始的？」→ 第二次 Tool **分页/明细** `queryDowntimeDetail(eventId=...)`，仍只读。
4. **模型** 用中文解释；对原因码可映射字典表（另一 Tool 或 SQL join）。
5. **RAG** 若问「按 SOP 非计划停机超过 2 小时报告谁」→ 查设备 SOP，而非瞎编。

**明确不做：** 自动下发 PLC 复位、自动停线、自动改 EMS 告警阈值。

## 5. 数据层设计原则（跟 DBA 对齐用）

### 5.1 为什么要宽表/视图

- Agent Tool **不宜** 每次临时 join 十几张 ERP 表（性能 + 权限 + 稳定性）；
- 视图 **封装** 复杂 join，Application 只读稳定列；
- 视图名进审计日志，方便复盘「当时查的是哪套口径」。

示例命名（示意）：

```
v_wms_available_stock      -- SKU + 仓 + 可用量 + 快照时间
v_erp_po_overdue           -- PO + 超期天数 + 供应商 + 物料
v_ems_downtime_event       -- 设备 + 起止 + 类型 + 原因码
```

### 5.2 只读账号

- 专用 DB 用户 `agent_ro`，仅 `SELECT` 授权到上述视图；
- **禁止** INSERT/UPDATE/DELETE/EXEC；
- 连接池独立，避免与 OLTP 抢连接（只读副本更佳）。

### 5.3 快照时间

每个视图尽量带 `as_of_time` 或 `etl_loaded_at` 字段，答复里 **必须展示**，避免「以为实时其实 T+1」。

## 8. 非功能需求（现在就要写进方案）

- **延迟**：P95 < 30s（视 Tool 次数与 SQL）；
- **可用性**：DeepSeek 不可用时降级提示，不返回假数；
- **安全**：Prompt 注入测试用例库；Tool 参数校验；字段脱敏；
- **合规**：出网数据最小化；保留审计 180 天（按公司政策改）；
- **成本**：每用户每日 token 配额（防刷）。

## 10. 课堂白板：三场景在同一张架构图上的「着色」

重看第 2 节 ASCII 图，用三种颜色（ mentally ）标路径：

**库存问数（蓝）：** 入口 → ChatClient → ToolCallingAdvisor → `queryAvailableStock` → `v_wms_available_stock` → 回 Model → 响应。**不经过 VectorStore。**

**超期 PO（蓝 + 绿）：** 蓝线到 `queryOverduePo` → ERP 视图；绿线到 RAG → 《采购制度》向量库 → 片段进 Prompt → Model 综合。

**设备停机（蓝）：** `queryUnplannedDowntime` → EMS 视图；若问 SOP 报告流程再加绿线 RAG。

**Memory（黄）：** 三场景多轮追问时都走 Memory Advisor，但不替代 SQL。

你在白板上能 **30 秒指对颜色**，Part 00 毕业。

### 10.1 部署拓扑（概念）

```
┌─────────────────┐     ┌──────────────────┐     ┌─────────────────┐
│  Spring Boot    │     │  DeepSeek API    │     │  ERP/WMS/EMS    │
│  Agent 应用     │────►│  （出网 HTTPS）   │     │  只读从库/视图  │
│  ChatClient     │     └──────────────────┘     └────────▲────────┘
│  @Tool          │                                      │
└────────┬────────┘                                      │
         │                                                │
         │         ┌──────────────────┐                  │
         └────────►│ VectorStore      │                  │
                   │ （内网 PG/Redis）│                  │
                   └──────────────────┘                  │
         └──────────────────────────────────────────────┘
                        内网 JDBC 只读
```

**DeepSeek** 和 **VectorStore** 和 **ERP 库** 是三个不同数据源：推理、文档语义、业务事实——**不要在架构上混成一个「AI 库」**。

### 10.2 典型一次请求的耗时构成（心里要有数）

| 阶段 | 典型耗时 | 优化方向 |
|------|----------|----------|
| SSO / Controller | 10～50ms | 常规 |
| 第 1 次 DeepSeek | 1～5s | 模型选型、Prompt 瘦身 |
| Tool SQL | 50～500ms | 视图、索引、只读副本 |
| 第 2 次 DeepSeek | 1～5s | 减少 Tool 轮次 |
| RAG 检索 | 50～200ms | TopK、metadata 过滤 |

厂长耐心有限。**Agent 不是毫秒级 API**；产品文案要写「分析中」，并设超时降级。

### 10.3 与安全部门的「最小出网」话术

「我们出网只有 DeepSeek Chat API；业务库存不出库，只在公司内网 JDBC 查只读视图；Prompt 里不带客户 PII；密钥 KMS/环境变量；全量 audit 留 180 天。」

VectorStore 和 ERP 库 **不出网**。这是大多数制造集团能批下来的形态。

### 10.6 常见立项问题（老师预答）

**问：多久能 demo？**  
答：HelloWorld 1 周；带 3 Tool + 只读视图 + 审计的 MVP，取决于 DBA 视图进度，通常 **视图就绪后 2～3 周** Java 侧可内测（不含安全灰度）。

**问：要不要买 GPU？**  
答：第一版 DeepSeek API，不买 GPU。本地模型是 extensions 扩展篇。

**问：能不能替代数据仓库？**  
答：不能。Agent 是查询与解释层，DW 仍是历史分析底座。

**问：模型换国产/换厂商怎么办？**  
答：换 ChatModel 配置，Tool 与视图不动——这就是 Spring 抽象的意义。

### 10.7 三场景 Tool 命名建议（第一版可照抄再改）

| 场景 | Tool 名（示意） | 只读视图（示意） |
|------|-----------------|------------------|
| 库存 | `queryAvailableStock` | `v_wms_available_stock` |
| 超期 PO | `queryOverduePoByLine` | `v_erp_po_overdue` |
| 停机 | `queryUnplannedDowntimeSummary` | `v_ems_downtime_event` |

命名用 **动词 + 业务含义**，避免 `doAiQuery1`。参数用 **公司主数据编码**（`warehouseCode` 不是 `wh` 黑话），方便审计日志被人读懂。

## 常见误解

| 误解 | 正解 |
|------|------|
| 「架构图里 DeepSeek 在中间，所以核心是模型」 | 核心是 **受控数据通路**；DeepSeek 是推理与表达引擎，不是事实中心。 |
| 「先做聊天 MVP，Tool 以后再加」 | 无 Tool 的 MVP 会养成错误预期且难审计；应 **最小 Tool 集与聊天同时上线**。 |
| 「宽表 = 大模型知识库」 | 宽表是 SQL 视图，给 Tool 查；不是 embedding 向量库。 |
| 「EMS 停机要靠 RAG 查日志」 | 停机时长是结构化事件，走 EMS 视图 + Tool；RAG 查 SOP。 |
| 「全景图看懂就能上线」 | 上线还要 Part 07～09 的安全、观测、灰度；Part 00 是 **对齐地图**，不是交付物。 |

## Part 00 结语

同学，走到这里，你手里的不应该只是「几个 AI 新词」，而应该是 **一张带边界的企业系统地图**：

- **ChatClient** 是你的门面；
- **Advisor** 是你的可循环 Filter 链；
- **Tool** 是受控的只读 Service；
- **RAG** 是文档的语义检索；
- **Memory** 是会话缓存，不是 ERP；
- **DeepSeek** 是驱动，不是数据库；
- **ERP/WMS/EMS 视图** 才是数字的法官。
