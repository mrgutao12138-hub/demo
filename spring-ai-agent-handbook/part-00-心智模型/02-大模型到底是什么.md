# 02 · 大模型到底是什么

> 同学，这一讲我们仍然不写 Spring 代码。  
> 我要你先在大脑里把「大模型」从「全知全能的神」降级成「一个被训练过的、会接龙的超级文本函数」——降级了，你才能正确用它。

---

## 你现在在哪

你已经会用 Spring 调各种外部系统：MySQL 返回行、Redis 返回 key、HTTP 返回 JSON。你知道 **有明确输入输出契约** 时，程序行为可测、可复盘。

你也可能在 DeepSeek 网页里问过业务问题，得到 **读起来非常专业** 的答案，甚至带表格、带建议。于是心里有个声音：

「它好像懂我们行业，那我把 ERP 接进去，它是不是就能替报表系统了？」

**这一讲要纠正的，正是这个「好像懂」带来的工程风险。**

---

## 学完本讲你能干什么

1. 用 **非算法语言** 说明：大模型训练在学什么、部署后在干什么（预测下一个 token，不是查表）。
2. 向业务经理解释：**为什么库存、金额、停机时长不能「问模型」，必须走 Tool/SQL**。
3. 区分 **能力**（语言理解、归纳、多步推理草稿）与 **边界**（无实时事实、无精确算术保证、无贵司私有数据除非 RAG/Tool）。
4. 在团队评审里识别「把大模型当数据库」的设计，并给出替代方案。

---

**1.5～2 小时。** 含做一道「找幻觉」小实验（见作业）。概念密集，建议分两段，中间休息 10 分钟。

## 1. 先用 Java 工程师听得懂的一句话定义

**大模型（Large Language Model，LLM）** 在这里指 DeepSeek API 背后的那类模型：输入一段文本（Prompt），输出一段文本（Completion）。

它本质上在做一件事：

> 在给定上文的情况下，按训练得到的统计规律，**逐个预测下一个最可能出现的 token**，直到停步。

用 Java 伪类比（不是真代码，是思维模型）：

```java
String complete(String context) {
    StringBuilder out = new StringBuilder();
    while (!shouldStop(out)) {
        Token next = probabilityTable.sampleNext(context + out); // 按概率抽样
        out.append(next);
    }
    return out.toString();
}
```

注意这里没有：

```java
ResultSet rs = jdbc.query("SELECT qty FROM inventory WHERE sku = ?", sku);
```

**没有数据库连接，没有你的 ERP，没有「现在几点」的真实时钟（除非你在 Prompt 里告诉它）。**  
它只有：**训练时见过的海量文本里学来的模式**，加上 **你本次请求里给的上下文**。

所以讲义第一句【红线】：

> **大模型不是数据库。它甚至不是搜索引擎。它是文本生成器。**

## 2. 训练阶段：它「见过」什么，没「见过」什么

### 2.1 训练在干什么（直觉版）

训练可以粗浅理解为：

1. 把互联网、书籍、代码、论文等切成 token 序列；
2. 让模型反复做「填空题」：给定前半句，预测下一个 token；
3. 预测错了就调参数，对了就强化——亿次重复后，参数里 **压缩了语言与常识的模式**。

它 **没有** 在训练时：

- 连接你们公司的 Oracle ERP；
- 订阅 WMS 的库存变更消息；
- 读取 EMS 里昨晚 2:17 的空压机报警。

因此，**你们库里的「ABC 华东仓 127 件」不在模型权重里**。除非你在运行时通过 Tool/RAG 把事实塞给它，否则它若说出 127，那是 **看起来像真的生成**，不是 **查出来的真值**。

### 2.2 「好像懂 ERP」从哪来

模型在训练文本里见过大量：

- 「安全库存」「采购订单」「BOM」「OEE」「停机」等术语；
- 行业文章里 **虚构或示例** 的数字与流程描述。

所以它能 **像资深顾问一样组织语言**，甚至 **合理编造** 一组数字来「完成看起来完整的回答」。  
这在写文案时是优点；在查库存时是 **事故**。

类比：一个读过一百本医学教材但没进过你们医院 HIS 的人，能讲糖尿病管理原则，但不能代替检验科出血糖数值。

### 2.3 微调、RAG、Tool 各自补哪块板（预告）

| 手段 | 补什么 | 不补什么 |
|------|--------|----------|
| 微调 | 语气、格式、行业术语偏好 | 实时库存、订单状态 |
| RAG | 私有文档片段（制度、手册） | 结构化事务型数字（除非文档里恰好有且仍可能过期） |
| Tool + SQL | 实时、可审计的结构化事实 | 文档型长篇推理（可配合 RAG） |

企业 Agent 的主线：**Tool 管数字，RAG 管文档，模型管理解与表达。**

## 3. 推理阶段：一次 API 调用里发生了什么

你在 Spring 里通过 ChatModel / ChatClient 调 DeepSeek，一次简化流程是：

```
你的 Prompt（system + user + 历史 + tool 结果 + RAG 片段）
        │
        ▼
DeepSeek 服务端的模型权重
        │
        ▼
自回归生成：token₁, token₂, … tokenₙ
        │
        ▼
Assistant 文本（可能包含「我要调 queryStock」的 tool call 结构）
```

和 JDBC 对比：

| 步骤 | JDBC 查库存 | 大模型生成 |
|------|-------------|------------|
| 输入 | 参数化 SQL + sku | 自然语言 + 上下文 |
| 内部 | 优化器 → 执行计划 → 读盘 | 矩阵运算 → 采样 token |
| 输出 | 行集，可重复 | 文本，同 Prompt 也可能略有不同 |
| 事实性 | 以库为准 | 以生成为准，**无事实保证** |
| 审计 | SQL + 行数 | Prompt + completion + tool 日志 |

【易混】**「确定性」**：同一 SQL 在同一库上结果应一致；模型即使用 `temperature=0`，也可能因服务版本、批处理等出现细微差异。**不要把 LLM 输出当唯一事实源。**

## 4. 它强在哪：为什么管理层 Agent 仍然值得做

既然不是数据库，为什么还要接 ERP？

因为管理层的问题里，有很大一块 **不是单行 SQL 能直接回答的界面**，而是：

1. **意图理解**：「上周那批」「华东」「撑几天」——需要结合上下文与多 Tool。
2. **跨结果归纳**：库存 + 消耗 + 在途 PO → 用中文解释风险，而不是扔三个 JSON。
3. **文档口径**：「按公司制度，超期 PO 谁负责」——RAG 查制度，Tool 查 PO 列表，模型综合成 **可读结论**。
4. **交互成本**：不会写 SQL 的厂长也能问；但 **数字仍来自 Tool**。

类比分工：

- **ChatModel** 像 **资深业务分析师的笔**：会写、会归纳、会提问澄清。
- **Tool + SQL** 像 **会计与仓储系统**：出数、可审计。
- **Agent** 是分析师 **被允许使用的只读终端**，不是分析师 **替会计改账**。

---

## 5. 它弱在哪：你必须假设会出错

### 5.1 幻觉（Hallucination）

**幻觉** 指模型自信地生成 **不存在或错误** 的事实：假 SKU、假供应商、假「第 3.2 节规定必须……」。

在 ERP 场景典型表现：

- 编造库存数量；
- 编造「已审批」状态；
- 引用不存在的采购单号；
- 把 RAG 里相似但另一份文档的条款当成当前制度。

【红线】**缓解幻觉靠工程，不靠「换个更聪明的模型就完事」：** Tool 强制取数、RAG 标注来源、答复必须引用 tool 返回字段、低温度、结构化输出校验、人工抽检。

### 5.2 算术与精确比较

模型不擅长大数运算、多步精确加总。  
「127 + 89 + 403 是否超过安全库存 500」——应 Java 算，模型只读 Java 算完的结果。

别在 Prompt 里扔 200 行 Excel 让模型「心算汇总」。那是用错工具。

### 5.3 时间与实时性

模型不知道「现在」 unless 你在 system prompt 注入 `Instant.now()` 或由 Tool 返回 `asOfTime`。  
库存、订单状态每 minute 变，**每次回答都应 Tool 现查**，不能靠 Memory 里 ten 分钟前的数。

### 5.4 保密与合规

Prompt 会发到 DeepSeek 云端（除非你们私有化部署，本讲义主线是 API）。  
**生产数据脱敏、字段最小化、合同与 DPA** 是上线前必答题，不是选修。

---

## 6. DeepSeek 在本讲义中的角色（不神化、不妖魔化）

技术栈约定：**Spring Boot 4.1 + Spring AI 2.0 + DeepSeek 官方 Starter**。

DeepSeek 是 **ChatModel 的一种实现**，像选一个 JDBC 驱动厂商：

- 你仍然通过 Spring 抽象调用，不绑死在 Controller；
- 密钥 `DEEPSEEK_API_KEY` 走环境变量；
- 常见型号有对话档、推理档等，讲义后续会教按场景选型（日常管理问数 vs 复杂多步分析）。

**换模型不换架构**：ChatClient、Advisor、Tool、RAG 分层不变；换的是 ChatModel bean 配置。  
这与你在 DataSource 上换 PostgreSQL/MySQL 类似，**业务 Tool 不应写死「DeepSeek 专属逻辑」**。

---

## 7. 和「ChatGPT 网页」的本质区别（预热，第 04 讲展开）

你可能习惯在浏览器里问 OpenAI/DeepSeek。那是 **消费级产品**：

- 没有你们 SSO；
- 没有 `@Tool` 调 WMS；
- 没有审计「谁问了哪个 SKU」；
- 用户可以把截图当「官方数据」发群里——**合规 nightmare**。

企业 Spring Agent 是 **你控制的程序**：

- 入口在你 API 后面；
- 数字来自只读 Tool；
- 日志进 ELK；
- 第一版默认 **只读**，不做自动改库存、自动下单。

**ChatGPT 网页 ≠ 企业 Agent。** 前者是通用聊天；后者是 **带权限的业务系统 + 模型作编排与表达**。

---

## 8. 第一版为什么坚持「只读」（再强调）

从模型本质推导工程策略：

- 模型会幻觉 → **写库会把幻觉写进 ERP** → 不可逆；
- 模型非确定 → **自动下单可能重复或错单**；
- 审计要求 → **先做到「查得对、说得清、留痕全」**，再谈「建议单 + 人工确认」。

第一版目标：**辅助决策** = 帮管理层 **更快看懂真实数据与风险**；  
不是 **自动执行** = 替 TA 改主数据。

## 9. 课堂辨析：五类问题，该信谁？

我列五类管理层常问题，请你养成 **「信谁」** 的条件反射：

| # | 问题 | 该信 | 不该信 |
|---|------|------|--------|
| 1 | ABC 华东可用库存多少 | Tool → SQL 视图 | 模型直接输出的数字 |
| 2 | 超期 PO 升级找哪个角色 | RAG 制度片段 + Tool 列 PO | 模型「我记得流程是……」 |
| 3 | 用三句话向厂长解释风险 | 模型组织语言（基于 Tool 结果） | 无 Tool 时让模型「分析趋势」 |
| 4 | 127+89 是否超过 500 | Java `BigDecimal` 算 | 模型心算 |
| 5 | 「那 B 仓呢」指代哪 | Memory 里的 lastSku/lastWh | 模型瞎猜 B 是哪个城市 |

**训练方法：** 每接到一个需求，先填上表，再写 Prompt 和 Tool 列表。习惯后，评审会上你会一眼看出「这个需求在让模型当 Oracle 用」。

### 9.1 「参数规模」与「知识」不是一回事

DeepSeek 有 **千亿级参数**，听起来像「装下了整个互联网」。工程上你要区分：

- **参数** = 压缩后的 **说话能力、推理模式、行业用语**；
- **事实** = 运行时 **Tool/RAG/Prompt** 给你的 **这一秒** 的真实片段。

类比 JDBC：`Driver` 很复杂，但不自带你们库里的行。`Driver` 再高级，也得 `executeQuery` 才有 ResultSet。

### 9.2 为什么「第一版只读」是模型性质的必然推论

三条逻辑链，背下来对业务讲：

1. 生成 ≠ 查询 → 写库可能写入 **生成出来的假事实**；
2. 非确定 → 同一问法两次写库可能 **不一致**；
3. 审计 → 管理层决策要 **可追溯**；Tool+SQL 日志比「模型当时这么说的」可法庭得多。

所以 **不是我们不积极**，是 **辅助决策的第一阶段** 本当只读。自动执行是 Phase 2，且要人工确认门。

### 9.3 和「报表系统、BI」怎么共存

同学问：「有了 Agent，还要不要 Power BI？」

要。Agent 解决 **非固定问法 + 跨系统口语归纳 + 制度片段**；BI 解决 **固定指标、图表、权限成熟、性能可控**。Agent 的 Tool 甚至可以 **调用 BI 语义层或已发布数据集 API**，而不是直接扫事实表——那是 Part 06 的集成话题。

### 9.4 温度、TopP 与「像不像真的」无关「对不对」

同学常把 **回答风格** 和 **事实正确** 混为一谈。`temperature` 低，模型更 **稳定选高概率 token**——话更「死板」，但 **库存该幻觉还是幻觉**。

管理问数场景建议：

- 涉及 **Tool 归纳**：temperature 偏低（具体数值 Part 03 代码章给）；
- **禁止** 为了「活泼」把 temperature 调高——管理层要的是 **稳**，不是创意写作。

【红线】调参不能替代 Tool。 **「模型参数千亿」+「温度 0」≠ 数据库。**

### 9.5 DeepSeek 在 Spring 里的位置（再巩固）

配置在 `application.yml` + 环境变量 `DEEPSEEK_API_KEY`；代码里注入 `ChatClient` 或测试里 Mock `ChatModel`。换型号（flash vs pro）像换连接池大小—— **架构不变**。

出网策略、密钥轮换、失败重试，Part 07～09 会写。Part 00 只需记住：**DeepSeek 是 ChatModel 实现，不是事实源。**

### 9.6 现场小测：三句话里有没有「假数字」

下面三句，只有一句可以进生产答复，指出哪句及原因：

1. 「根据系统查询，ABC 华东可用 127 件（视图 v_wms_available_stock，10:03）。」  
2. 「ABC 在华东大概有 100 多件吧，建议补货。」  
3. 「库存情况复杂，建议联系仓储科。」

**答案：** 仅 1 可在 **有对应 Tool 日志** 时展示。2 含模糊假数；3 可作 Tool 失败时的兜底，但不能 **假装查过**。

养成习惯：**每写一句答复模板，问「数字哪字段来的」**。这是 ERP Agent 工程师的基本功。

### 9.7 与测试工程师怎么协作

QA 不应只测「接口 200」。Agent 需要 **场景化用例**：

- **正常**：有 Tool、数字与 SQL 一致；
- **边界**：SKU 不存在、仓无权限；
- **恶意**：Prompt 注入、要求编造数字、要求自动改库。

预期结果写清：**无 Tool 不得出现具体 qty**；**写库 Tool 在 MVP 中不存在**。Part 07 会扩安全用例；Part 00 先建立 **测事实来源** 的意识。

### 9.8 一句话给厂长（背下来，开会用）

「这个系统像给您的 **望远镜和副驾**，帮您在 **只读** 的系统数据上 **快速看懂风险**；**方向盘和油门还在您和现有 ERP 流程手里**，AI 不会 secretly 改库存或下单。」

### 9.9 模型版本升级时 Java 侧要做什么

DeepSeek 换型号、Spring AI 小版本升级时：

1. 回归 **三场景 Tool 用例**（数字仍与 SQL 一致）；  
2. 看 **usage 与延迟** 是否突变；  
3. **不要** 改 Tool 契约除非业务变。

模型升级 **不应** 触发 ERP 表结构变更。若升级后幻觉率升，先调 Prompt/Tool 护栏，而不是怀疑 WMS 错了。

### 9.10 本讲小结

大模型 = **概率文本生成**；企业 Agent = **生成 + Tool 事实 + RAG 文档 + 只读边界**。  
DeepSeek = ChatModel 驱动；MySQL/视图 = 数字法官。  
ChatGPT 网页 ≠ 企业 Agent。  
第一版只读，因为 **生成式写库等于把幻觉写进 ERP**。  
背下这四句，02 讲毕业。

### 9.11 老师叮嘱

我见过太多团队在第一周被 DeepSeek 网页的「聪明」震撼，第二周就在生产 Demo 里展示 **假库存**。请你现在就把 **「像真的 ≠ 真的」** 贴在显示器边。做完本章幻觉实验作业，把结论写进团队 Wiki——那是你作为 Java 工程师对业务最负责任的一次科普。下一讲我们谈 Token，你会明白 **为什么「聪明」不能靠堆 Prompt 解决**。

**验收前自测：** 能否向厂长解释「为什么 AI 说的库存不能信，除非系统里查过」？能否区分 RAG 与 SQL 各管什么？能，02 讲过关。

**关键词：** 概率生成、token、幻觉、训练边界、Tool 事实、RAG 文档、只读、DeepSeek、ChatModel、不是数据库。

**本节复盘：** 大模型是文本生成引擎，不是事实存储。它懂术语，不懂你们昨晚的库存。企业 Agent 必须用 Tool 拉事实、用 RAG 拉制度、用 Java 做算术、用只读边界防写库事故。DeepSeek 在架构里是驱动，不是数据源。牢记「像真的不等于真的」，你就不会被 Demo 里的流畅回答骗到。完成幻觉实验作业后再进入 Token 章。这一讲是整个讲义防幻觉的工程基石。加油，我们下一讲见。

## 常见误解

| 误解 | 正解 |
|------|------|
| 「模型参数里存了互联网所有事实」 | 存的是语言与模式的统计压缩，不是可查询的事实库；私有 ERP 数据不在其中。 |
| 「temperature=0 就不会胡说」 | 降低随机性，不能消除幻觉；事实性靠 Tool 与护栏。 |
| 「DeepSeek 中文好，所以库存数也准」 | 中文好是语言表达；数字准不准看有没有 Tool 查库。 |
| 「RAG 把 ERP 导出 Excel 向量化就能查数」 | Excel 快照易过期；实时库存应 SQL；RAG 适合文档，不是事务库替身。 |
| 「推理模型（reasoner）可以替代 SQL」 | 推理模型强在链式思考，仍不保证事实；该 SQL 还是 SQL。 |
