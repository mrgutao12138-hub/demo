# 01 · 配置分层、密钥与多环境

> 配置乱，上线必乱。  
> 密钥进 Git，一次泄露够你写半年事故报告。  
> 本章教你用 Spring Boot 惯用手段，把 Decision Copilot 的「开发笔记本」和「5 人灰度 pilot」彻底隔开。

---

## 1. 为什么要分层

你可能已经有一个能跑的 `application.yml`。但灰度时至少需要三套心智：

| 环境 | 谁用 | 连什么数据 | 模型策略 |
|---|---|---|---|
| `dev` | 开发者本机 | 假数据 / 本地 Postgres | flash 为主，可开 debug 日志 |
| `pilot` | **5 位管理层灰度** | 只读宽表（真实或准真实） | pro + 严格限流 + 完整审计 |
| `prod` | 全量上线后（本章先铺路） | 同 pilot 或更强隔离 | 与 pilot 配置同源，规模不同 |

**不要**用「改几个注释」在同一份文件里切换环境。用 **Profile + 外部化配置**。

---

## 2. 目录结构建议

```
src/main/resources/
├── application.yml              # 全环境公共：应用名、Advisor 顺序、业务常量
├── application-dev.yml          # 本机：详细日志、假数据源
├── application-pilot.yml        # 灰度：真实只读库、审计全开、限流
└── application-prod.yml         # 预留：与 pilot 尽量 DRY，差异用环境变量注入
```

激活方式：

```bash
# 本机
export SPRING_PROFILES_ACTIVE=dev

# pilot 服务器（systemd / 容器环境变量）
export SPRING_PROFILES_ACTIVE=pilot
```

## 3. 公共配置写什么（`application.yml`）

只放**不敏感、各环境一致**的内容：

```yaml
spring:
  application:
    name: decision-copilot

  ai:
    deepseek:
      api-key: ${DEEPSEEK_API_KEY}   # 值永远来自环境，不写 sk- 真值
      chat:
        temperature: 0.2

# 业务常量：输出结构、工具轮次上限
decision-copilot:
  agent:
    max-tool-iterations: 8
    response-template: CONCLUSION,NUMBERS,SOURCES,RISKS,SUGGESTIONS
```

**【红线】** 文件中不得出现 `sk-` 开头的完整密钥。提交前执行：

```bash
git grep -E 'sk-[a-zA-Z0-9]{10,}' && echo "泄露风险！" || echo "未发现明文 Key"
```

## 4. 环境差异写什么

### 4.1 `application-dev.yml`

```yaml
spring:
  ai:
    deepseek:
      chat:
        model: deepseek-v4-flash

logging:
  level:
    org.springframework.ai: DEBUG
    com.yourcorp.decision: DEBUG

decision-copilot:
  pilot:
    enabled: false
    daily-question-limit-per-user: 999   # 开发不限
```

### 4.2 `application-pilot.yml`（灰度核心）

```yaml
spring:
  ai:
    deepseek:
      chat:
        model: deepseek-v4-pro
        thinking:
          type: enabled
        reasoning-effort: high

  datasource:
    url: ${PILOT_DB_URL}
    username: ${PILOT_DB_READONLY_USER}
    password: ${PILOT_DB_PASSWORD}
    hikari:
      maximum-pool-size: 10          # 灰度期压死连接数
      connection-timeout: 5000

management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics
  endpoint:
    health:
      show-details: when_authorized

decision-copilot:
  pilot:
    enabled: true
    allowed-user-ids: ${PILOT_USER_IDS}   # 逗号分隔的 5 个 SSO id
    daily-question-limit-per-user: 30
    audit:
      enabled: true
      retain-days: 90
```

### 4.3 用环境变量注入名单

```bash
export PILOT_USER_IDS="u_zhangsan,u_lisi,u_wangwu,u_zhaoliu,u_sunqi"
```

代码里在 Controller 或 Filter 校验：当前登录 `userId` 必须在白名单内，否则 **403 + 审计一条拒绝记录**。

## 5. 密钥管理：学习期 vs 灰度期

### 5.1 学习期（你一个人）

| 方式 | 是否够用 | 说明 |
|---|---|---|
| 本机 `export DEEPSEEK_API_KEY` | ✅ | 配合 `.gitignore` 不误提交 |
| IDE 运行配置里填环境变量 | ✅ | 不要写进共享的运行配置 XML |
| `application-local.yml` + gitignore | ✅ | 文件名加入 `.gitignore` |

### 5.2 灰度期（5 人 pilot 服务器）

| 方式 | 推荐度 | 说明 |
|---|---|---|
| 云厂商「密钥管理服务」注入容器 | ⭐⭐⭐ | 轮换方便，审计谁读过 |
| CI/CD 密文变量，部署时注入 | ⭐⭐⭐ | 与现有 Java 发布流程一致 |
| 服务器 `/etc/decision-copilot/env` 权限 600 | ⭐⭐ | 小团队可接受；要规定轮换 |
| 密钥写进 `application-pilot.yml` 提交 Git | ❌ | **禁止** |

**轮换流程（写进团队 Wiki）：**

1. 控制台新建 Key，命名带日期：`decision-copilot-pilot-202609`。
2. 部署环境变量指向新 Key，滚动重启 pilot 实例。
3. 观察 30 分钟无 401 后，作废旧 Key。
4. 审计日志确认无异常调用激增。

## 6. 配置优先级（口试必考）

Spring Boot 后加载的覆盖先加载的。常见顺序（后者赢）：

```
application.yml
  → application-{profile}.yml
    → 环境变量（SPRING_APPLICATION_JSON、DEEPSEEK_API_KEY 等）
      → 命令行参数
```

因此：**敏感项只放环境变量**；YAML 里只留 `${变量名}` 占位符。

## 7. 多环境「不要重复」的技巧

### 7.1 用 `@ConfigurationProperties` 收拢业务配置

```java
@ConfigurationProperties(prefix = "decision-copilot.pilot")
public record PilotProperties(
    boolean enabled,
    Set<String> allowedUserIds,
    int dailyQuestionLimitPerUser,
    AuditProperties audit
) {
    public record AuditProperties(boolean enabled, int retainDays) {}
}
```

灰度开关、名单、限额在一个 Java 类型里，单测可 mock，比满世界 `@Value` 强。

### 7.2 数据源与 VectorStore

| 组件 | dev | pilot |
|---|---|---|
| 业务宽表 | H2 / 本地 Postgres 假数据 | 只读账号连同步宽表 |
| VectorStore | 内存 `SimpleVectorStore` | pgvector 独立 schema |
| Embedding | 本地 Transformers | 与 dev 同模型即可，注意 CPU |

**【红线】** pilot 的 JDBC 账号在数据库侧确认：**只有 SELECT**。

## 8. 配置变更谁改、谁审

灰度期建议最小流程：

```
开发者提 MR → 另一位 Java 同事 Review → 运维/你在 pilot 改环境变量或发版
```

以下变更必须 **双人确认**：

- `allowed-user-ids` 增删
- `daily-question-limit-per-user` 放大 2 倍以上
- 数据源 URL 或账号变更
- `max-tool-iterations` 放大

---

## 9. 【必做】实验

1. 新建 `application-pilot.yml`，把上文 pilot 段落抄进去并改成你项目包名。
2. 本机 `SPRING_PROFILES_ACTIVE=pilot` 启动，故意不设 `DEEPSEEK_API_KEY`，确认错误信息是「缺少配置」而不是 NPE 堆栈。
3. 设一个假的 `PILOT_USER_IDS`，用两个不同 userId 调接口，一个 200 一个 403。
4. 运行 `git grep -i sk-`，确保仓库干净。

---

## 10. 小结

| 原则 | 做法 |
|---|---|
| 敏感外置 | Key、库密码、用户名单 → 环境变量或密钥管理服务 |
| 环境隔离 | Profile 分 dev / pilot / prod，禁止手改注释切换 |
| 灰度门禁 | pilot 白名单 + 每日问答上限 |
| 可审计 | 配置变更走 Review；密钥可轮换 |
