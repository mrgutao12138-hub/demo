# 07 · 下一季度演进路线

> 灰度不是为了「试完就归档」，是为了用真实反馈换一张路线图。  
> 本章给你一张 **下一季度（约 12 周）** 的演进草图：该做什么、不该做什么、和 Spring AI 2.0 哪条能力对齐。  
> 拿去和业务负责人开一次 30 分钟会就够。

---

## 1. 规划原则（先念三遍）

1. **灰度期只读不动账。** 写操作、自动下单、改主数据 —— 默认不在 Q1 路线图里，除非安全与流程评审单独立签字。
2. **先稳再广。** 先扩大可信域与评测，再扩大人数；不要先上 50 人再修幻觉。
3. **框架能力优先于换模型名。** MCP、Advisor 链、评测自动化，比追「又出了新模型」更值得排期。

---

## 2. 现状假设（灰度结束时）

你们大概率处于：

| 维度 | 状态 |
|---|---|
| 用户 | 5 人 pilot 完成 2～4 周 |
| 域 | 库存 + 采购 + 设备（三域中的 2～3 个） |
| 数据 | 只读宽表 + 制度 RAG |
| 工具 | `@Tool` 内嵌在 Spring 服务里 |
| 评测 | 20～50 条人工用例，改 prompt 后手工回归 |
| 观测 | 日志 + 部分 Micrometer 指标 |

路线图从这张「现状照片」往外长。

---

## 3. 下一季度目标（建议写进 OKR）

| 目标 | 可验收结果 |
|---|---|
| **G1 可信扩大** | 评测集 ≥ 100 条；P0 事故 0；幻觉类反馈环比下降 50% |
| **G2 域覆盖** | 在库存/采购/设备基础上 **+1 个业务域**（如质量、履约），或三域口径统一字典 |
| **G3 互操作** | 至少 **1 个外部能力** 通过 MCP 接入试点（只读） |
| **G4 工程化** | 评测回归 **半自动**（CI 或定时任务跑核心 30 条）；发布前有门禁 |
| **G5 产品闭环** | 反馈表 → 工单系统有状态；领导可见「已修复」 |

人数扩大建议：**5 → 15 → 30** 分两批，每批前跑一轮全量评测。

---

## 4. 四条主线详解

### 4.1 主线 A：MCP（工具互操作）

**为什么排进下一季度**

- 别的团队已有 HTTP 服务、遗留报表、算法容器；你不必每个都抄进 `@Tool`。
- Spring AI 2.0 官方支持 MCP Java SDK；MCP 是「插座」，不是替代 Advisor 主路。

**建议范围（克制）**

```
Q1 只做：
  - 1 个 MCP Server（只读），例如「设备 OEE 查询」或「外部质检 API」
  - ChatClient 侧 SyncMcpToolCallbackProvider 注入 .tools(...)
  - 权限仍在你 Java 网关层，不信 MCP 自带鉴权

Q1 不做：
  - 全面 MCP 化所有工具
  - MCP 写操作
```

**里程碑**

| 周 | 交付 |
|---|---|
| 1～2 | 选型：内嵌 Server vs 独立进程；网络与 SSO 策略 |
| 3～4 | 1 个只读 MCP 工具在 dev 跑通 |
| 5～6 | pilot 可选开关 `mcp.oee.enabled=true` |
| 7～8 | 文档 + 事故预案（MCP 进程挂了怎么降级） |

**与讲义对应：** part-04 `07-MCP是什么以及本周了解到哪.md` 复习；本章是生产级插座。

---

### 4.2 主线 B：工单流与「写操作」边界

**为什么谨慎**

- 管理层最想听的往往是：「能不能直接生成采购建议单并提交？」
- 工程上：**只读 Agent → 建议单草稿 → 人工审批 → 既有 ERP 接口写入**，才是企业可接受路径。

**建议分三期（Q1 只做第一期）**

```
第一期（Q1）：只读建议 + 导出
  - Agent 输出结构化「建议单」JSON / PDF
  - 用户一键「复制到工单系统」或生成草稿号
  - 写入仍由人在 ERP/工单里点确认

第二期（Q2+）：对接工单 API（仍要审批流）
  - 调用既有「创建工单」REST，状态=待审批
  - Agent 不持 ERP 写账号

第三期（更远）：有条件自动执行
  - 限额、双人复核、全量审计 —— 单独立项
```

**Q1 可交付**

- `SuggestionTicket` 结构化输出（`.entity()` + `validateSchema()`）
- 与企微/飞书「审批机器人」仅做通知，不做自动过账

**【红线】** Q1 不给 Agent 直连 ERP `INSERT/UPDATE`。

---

### 4.3 主线 C：更多业务域

**扩展顺序（按依赖从少到多）**

| 优先级 | 域 | 前提 |
|---|---|---|
| P0 已有 | 库存、采购、设备 | 灰度已验证 |
| P1 | 质量 / 客诉 | 有只读宽表或 API；制度 RAG 补口径 |
| P2 | 履约 / 物流时效 | 跨系统指标字典统一 |
| P3 | 财务毛利 | 敏感度高，需单独权限评审 |

**每个新域的标准包**

1. 指标字典（官方口径一段话 + 对应工具）
2. 5 条评测「金标准」问答
3. 2 条越权拒答用例
4. 宽表 `dataAsOf` 字段
5. 领导培训一页纸更新

**不要**一次加三个域；**一个季度加一个** 足够扎实。

---

### 4.4 主线 D：评测自动化

**为什么比换模型重要**

- 模型升级、prompt 微调、RAG 增量入库，都会悄悄掉点。
- 人工回归 100 条会偷懒；**自动化至少守住核心 30 条**。

**Q1 目标架构**

```
评测集 YAML/CSV（问题 + 期望包含/不包含 + 必调工具）
  → JUnit / Spring Boot Test  nightly 或 MR 触发
    → ChatClient 调用（mock 工具或连测试库）
      → 断言：结构化字段、关键词、工具名、拒答场景
        → 失败则 CI 红，禁止合入 pilot 分支
```

**分级**

| 层级 | 条数 | 自动化 | 耗时 |
|---|---|---|---|
| 冒烟 | 10 | 100% | < 5 min |
| 核心 | 30 | 100% | < 20 min |
| 全量 | 100+ | 50% 自动 + 50% 人工月审 | 半天/月 |

**指标看板（建议）**

- 冒烟通过率
- 工具调用命中率
- 拒答场景误答率
- 平均 token（成本漂移）

Spring AI 2.0 的 Advisor 链让「插入评测 Advisor」成为可能；Q1 不必做花哨，**JUnit + 黄金文件** 就够。

## 5. 季度节奏（12 周甘特示意）

```
周 1-2   灰度复盘 + OKR 签字 + 评测集扩到 50
周 3-4   新域需求评审 + 宽表/schema + 5 金标用例
周 5-6   MCP 只读试点 dev 通
周 7-8   建议单结构化输出 + 工单导出
周 9-10  评测 CI 门禁 + pilot 扩 15 人准备
周 11    全链路演练（06 章预案）
周 12    季度复盘 + 是否扩 30 人
```

并行不超过 **两条主线同时攻坚**（例如 MCP + 新域可以，再加工单 API 就满）。

---

## 6. 明确不排进 Q1 的（管理预期）

| 项 | 原因 |
|---|---|
| 微调公司专属大模型 | 不解决查数与权限 |
| 多 Agent 自主协作 | 复杂度高，ROI 低 |
| 全自动采购过账 | 合规与审批链未就绪 |
| 替换整个 BI 平台 | 定位是辅助临机决策 |
| 每天换一个最新模型名 | 无评测门禁等于赌博 |

这些话要提前和业务负责人说，避免会上被现场加需求。

## 7. 资源粗算（人力，不是日历）

| 角色 | Q1 投入（约） |
|---|---|
| Java / Agent 主程 | 0.5～0.7 人 |
| 数据 / DBA | 0.2 人（宽表、索引） |
| 业务专家 | 0.1 人（口径、金标） |
| 运维 | 0.1 人（pilot 稳定） |

5 人灰度不需要专职算法；需要**专职「把数弄对」的业务搭档**。

## 9. 【必做】作业

1. 与业务负责人过一遍 §3 目标，改写成你们公司 OKR 表述。
2. 在 backlog 里建 4 个 Epic：MCP、工单草稿、新域、评测 CI。
3. 选定 **一个** Q1 新域，写下 5 条金标问题。
4. 把 §6「不做清单」发给领导，避免预期膨胀。

## 10. 小结

下一季度不是「更聪明」，而是 **更广（域）、更稳（评测）、更通（MCP）、更闭环（工单草稿）**。  
路线图画在纸上，灰度才有下半场。
