# 03 · 熔断、降级：模型挂了怎么办

> 云模型不是你家机房里的 Oracle，它会超时、限流、维护、抽风。  
> 工具背后的宽表也不是无限扛并发。  
> 本章教你：**外部依赖失败时，用户看到一句体面中文，而不是白屏或堆栈。**

---

## 1. 先分清四种「挂」

| 类型 | 典型现象 | 用户该看到什么 |
|---|---|---|
| 模型 API 超时 / 5xx | 等很久后失败 | 「决策助手暂时繁忙，请稍后再试；数字类问题可先看 BI 看板 XXX」 |
| 模型限流 429 | 配额用尽或 QPS 超限 | 「今日助手调用已达上限，请联系管理员」+ 内部告警 |
| 工具 / SQL 超时 | 宽表慢查询 | 「数据查询超时，请缩小范围或稍后再试」；**不要**让模型编造数字 |
| 向量检索失败 | pgvector 连不上 | 「制度库暂不可用，仅能回答已缓存范围外请暂缓」或拒答 |

**【红线】** 任一环节失败，**禁止**让模型在无工具结果时编造库存、采购、设备数字。

---

## 2. 降级层次（从外到内）

```
用户请求
  → ① 网关 / Filter：鉴权、限流、熔断（按 userId）
    → ② ChatClient 调用：模型超时、重试策略
      → ③ ToolCallingAdvisor 循环：单工具超时、最大轮次
        → ④ 各 @Tool 内部：SQL 超时、结果行数上限
          → ⑤ RAG：检索超时、空结果策略（默认拒答）
```

每一层都要有**明确失败语义**，并写入审计日志。

---

## 3. 模型层：超时与重试

### 3.1 配置超时（示例）

Spring AI 底层走 HTTP 客户端，在 `application-pilot.yml` 中限制等待时间（具体属性名以你项目 BOM 为准，原则是不超过 60s）：

```yaml
spring:
  ai:
    deepseek:
      chat:
        options:
          # 示意：总等待不宜超过管理层耐心（30～45s）
          # 查阅当前 starter 文档中的 timeout 配置项
```

**老师建议：** pilot 期 **单次用户问答端到端上限 45s**；超过则中断并返回降级文案。

### 3.2 重试策略

| 错误 | 是否重试 | 次数 |
|---|---|---|
| 网络抖动、502、503 | 是 | 最多 2 次，指数退避 |
| 429 限流 | 否（立刻降级） | 0 |
| 401 密钥错误 | 否 | 0，告警运维 |
| 400 参数错误 | 否 | 0，记 bug |

重试**只对幂等的模型调用**；工具若带副作用（灰度期应无）才讨论幂等，只读工具重试一般安全。

### 3.3 用户可见降级文案（统一常量）

```java
public final class DegradationMessages {
    public static final String MODEL_UNAVAILABLE =
        "决策助手暂时无法连接分析服务，请稍后再试。"
        + "紧急数据请查看【供应链日报看板】或联系计划部。";
    public static final String RATE_LIMITED =
        "您今日的助手使用次数已达上限，如有特殊需要请联系系统管理员。";
    public static final String TOOL_TIMEOUT =
        "业务数据查询超时，请尝试缩小时间范围或仓库范围后重试。";
}
```

文案里**给一个线下替代路径**（看板名、联系人），管理层会感激你。

## 4. 熔断（Circuit Breaker）

### 4.1 什么时候需要

5 人灰度、QPS 很低，**不必**第一天就上 Resilience4j 全家桶。但若：

- 模型连续失败 ≥ 5 次 / 1 分钟；
- 或工具错误率 > 50%；

应**短暂拒绝新请求**（开路 30～60s），避免线程池被打满，把宽表拖死。

### 4.2 简易实现思路

**方案 A（灰度够用）：** 内存计数器 + `AtomicInteger` 失败窗口，失败达阈值则 Filter 直接返回 `MODEL_UNAVAILABLE`。

**方案 B（与 Spring 生态一致）：** 引入 Resilience4j，`@CircuitBreaker` 包住 `chatClient.prompt()...call()` 的入口 Service 方法。

示意（方案 B）：

```java
@CircuitBreaker(name = "deepseekChat", fallbackMethod = "chatFallback")
public ChatResponse askDecision(String userId, String question) {
    return chatClient.prompt().user(question).call().chatResponse();
}

private ChatResponse chatFallback(String userId, String question, Throwable t) {
    auditService.logDegraded(userId, question, t.getClass().getSimpleName());
    return ChatResponse.builder()
        .content(DegradationMessages.MODEL_UNAVAILABLE)
        .build();
}
```

`application-pilot.yml` 中配置：

```yaml
resilience4j.circuitbreaker:
  instances:
    deepseekChat:
      slidingWindowSize: 10
      failureRateThreshold: 50
      waitDurationInOpenState: 60s
      permittedNumberOfCallsInHalfOpenState: 3
```

### 4.3 熔断时管理员要知道

- 指标：`circuitbreaker.state` = OPEN 时钉钉/邮件告警。
- 面板：DeepSeek 控制台看是否平台故障。
- 决策：短期切换 flash（若 pro 独占故障）或暂停服务公告。

## 5. 工具层：别把库打爆

### 5.1 每个 @Tool 必须有

| 护栏 | 建议值（pilot） |
|---|---|
| 执行超时 | 5～10s |
| 返回行数上限 | ≤ 500 行（聚合类工具更小） |
| 连接池 | Hikari `maximum-pool-size` ≤ 10 |
| 并发 | 全实例同时活跃 SQL ≤ 20（可用 Semaphore） |

### 5.2 工具异常不要抛到用户脸上

```java
@Tool(description = "查询指定仓库 SKU 可用库存，只读")
public String queryInventory(
    @ToolParam(description = "仓库编码，如 WH-EAST") String warehouseId,
    @ToolParam(description = "SKU 编码") String skuId) {
    try {
        return inventoryService.querySummary(warehouseId, skuId);
    } catch (QueryTimeoutException e) {
        return "ERROR: " + DegradationMessages.TOOL_TIMEOUT;
    } catch (AccessDeniedException e) {
        return "ERROR: 您无权查看该仓库数据";
    }
}
```

模型收到 `ERROR:` 前缀时，system 提示里要求：**向用户转述错误，不要编造数字**。

### 5.3 限制工具循环轮次

```yaml
decision-copilot:
  agent:
    max-tool-iterations: 8
```

`ToolCallingAdvisor` 达到上限仍要调工具时，应停止并让用户换种问法。part-04 已讲，灰度期**务必开启**。

## 6. RAG 降级

| 场景 | 策略 |
|---|---|
| VectorStore 不可用 | 跳过 `RetrievalAugmentationAdvisor` 或整请求降级；**不要** `allowEmptyContext(true)` 硬答口径 |
| 检索结果为空 | 明确说「制度库未检索到相关条款」 |
| 检索慢 | 单独超时 3s，超时则当空结果处理 |

## 7. 按用户限流（与熔断配合）

灰度 5 人也要限流，防一位领导开心连问 200 次：

```java
// 伪代码：Redis 或 DB 计数
if (countToday(userId) >= pilotProperties.dailyQuestionLimitPerUser()) {
    throw new RateLimitException(DegradationMessages.RATE_LIMITED);
}
```

与 DeepSeek 账户配额是**两道闸**：一道防单人刷，一道防账户爆。

## 8. 降级时的产品行为

| 能力 | 模型挂了是否可用 |
|---|---|
| 历史会话查看 | ✅ 可读已落库记录 |
| 新问题 | ❌ 返回降级文案 |
| 审计写入 | ✅ 记一条 `degraded=true` |
| 来源卡片 | 无新回答则不展示 |

---

## 9. 【必做】故障演练

在 dev 或 pilot 低峰做四次演练（记录截图进周报）：

1. **错误 API Key** → 应快速失败 + 告警，不无限重试。
2. **工具 sleep 15s** → 应在工具超时后返回 TOOL_TIMEOUT 语义，不编数。
3. **断网模拟模型**（改 base-url 到无效地址）→ 熔断打开后新请求立即降级。
4. **连续 10 次快问** → 第 N 次触发 per-user 日限流（N 设为试点用的 3 便于测）。

## 10. 小结

| 原则 | 做法 |
|---|---|
| 失败可见 | 中文降级文案 + 审计 |
| 失败隔离 | 熔断保护线程池和数据库 |
| 失败诚实 | 无数据不编数 |
| 失败可恢 | 半开探测 + 控制台看配额 |
