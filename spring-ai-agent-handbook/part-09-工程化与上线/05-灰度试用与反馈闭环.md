# 05 · 灰度试用与反馈闭环

> 5 位管理层不是「内测用户」，他们是你的第一批评委。  
> 灰度成功的标志不是「他们登录了」，而是：**两周后你能说清楚值不值得扩大、哪里必须改。**

---

## 1. 灰度目标（SMART 版）

| 维度 | 灰度期约定 |
|---|---|
| **S**pecific | 验证库存 + 采购 + 设备（或你们选的三域）只读决策问答 |
| **M**easurable | 每人 ≥ 10 次有效提问；收集 ≥ 15 条结构化反馈 |
| **A**chievable | 5 人、4 周、只读、有值守 |
| **R**elevant | 问题来自真实周会，不是演示脚本 |
| **T**ime-bound | 第 1 周小流量，第 2～4 周全量 5 人 |

---

## 2. 邀请谁、怎么选 5 人

建议名单结构（和业务负责人一起定）：

| 角色 | 人数 | 作用 |
|---|---|---|
| 业务域负责人 | 1～2 | 敢问狠问题，能拍板是否扩大 |
| 一线管理（仓/采购/设备） | 2～3 | 问题接地气 |
| 「怀疑派」 | 1 | 故意挑刺，测护栏 |

**【红线】** 名单 = `PILOT_USER_IDS` 白名单，口头答应「给你试一下」不算数，SSO id 必须入库。

---

## 3. 邀请前交付包

发给每位领导前，确保其有：

1. **一页纸说明**（PDF 或企微图文）
2. **登录方式**（SSO 链接，不要单独发密码）
3. **能问 / 不能问** 清单
4. **反馈表**（见 §6）
5. **值班联系人**（工作日响应时间）

### 3.1 一页纸说明模板

```markdown
# Decision Copilot 灰度试用说明

## 这是什么
面向管理层的只读决策助手：可查库存/采购/设备相关数据与制度口径，并给出结构化建议。

## 这不是什么
- 不会自动改库存、不会下单、不会发邮件
- 不能替代财务关账与正式审批
- 不确定时会说明依据不足

## 请您怎么帮我们一起试
1. 用真实工作场景提问（周会准备、异常复盘）
2. 看到数字请点「来源」看工具与制度依据
3. 发现不对请截图 + 填反馈表（2 分钟）

## 试用期限
即日起至 ____月____日，共 ____ 周。

## 联系人
产品/业务：____  技术：____
```

### 3.2 能问 / 不能问

| ✅ 鼓励问 | ❌ 请勿依赖 |
|---|---|
| 「华东仓 A 品可用量及口径」 | 「帮我把库存改成 0」 |
| 「超期采购定义与当前清单」 | 「保证一定赚钱」 |
| 「对比两仓补货优先级及理由」 | 涉密未脱敏人员名单 |
| 「设备停机对产线影响」 | 未接入系统的域（如实说没有数据） |

## 4. 培训：30 分钟够用的场次

不必讲 Spring AI。讲三件事：

1. **怎么问：** 带仓库/时间/SKU；一次一事；复杂问题可拆两句。
2. **怎么看答案：** 结论 → 数字 → 依据 → 风险 → 建议；点来源卡片。
3. **怎么挑错：** 数字不对记反馈；口径不对记反馈；态度不好也记——但分清「产品」和「模型」。

建议：**业务负责人先讲 5 分钟「为什么做」**，你再讲 15 分钟，留 10 分钟现场一问一答。

---

## 5. 放量节奏

```
D0  部署 pilot，开发+业务自测
D1  业务负责人 1 人
D3  +2 人
D5  +2 人（满 5 人）
D7  第一次周报（见 §7）
D14 中期复盘会（30 分钟）
D28 灰度结论报告
```

每日你看后台：

- 活跃人数 / 提问数
- 降级次数
- Top 失败问题类型

## 8. 闭环：从反馈到改动

```
反馈/审计 → 分类 → 排期 → 发布 → 回归评测集 → 通知领导「已修」
```

| 问题类型 | 典型动作 | 响应 SLA（灰度期） |
|---|---|---|
| 数字错 | 查工具/SQL/宽表新鲜度 | 2 工作日 |
| 口径错 | 补 RAG 文档或改检索 | 3 工作日 |
| 越权 | 立即修权限 + 审计追溯 | 4 小时 |
| 幻觉 | 加强拒答 + 加评测用例 | 3 工作日 |
| 「太慢」 | 查 SQL/模型/熔断 | 2 工作日 |
| UI 难用 | 排产品迭代 | 可放到灰度后 |

**修完后**给提反馈的领导发一句：

> 「您 __ 日关于【__】的反馈已处理，版本 pilot__，欢迎再试。」

这比 silently deploy 更能攒信任。

## 9. 灰度结束：扩大还是叫停

### 9.1 建议「扩大」若

- 5 人中 ≥ 4 人周评「愿意推荐」或「观望偏正面」
- 结构化反馈 ≥ 15 条，且 **致命问题（越权、编数）= 0 未关闭**
- 月成本在预算区间内
- 运行手册与事故预案已验证至少一次演练

### 9.2 建议「暂停」若

- 出现未关闭的越权或 Key 泄露
- 同一类数字错误一周 ≥ 3 次
- 领导普遍不信任且不愿填反馈（说明产品形态不对）

### 9.3 结项报告提纲（1～2 页）

1. 灰度目标与范围
2. 使用数据与成本实算
3. 价值案例 3 则（匿名）
4. 问题与修复
5. 建议：扩大 / 续 pilot / 叫停
6. 下季度路线（指向 07 章）

---

## 10. 【必做】作业

1. 和业务负责人定 5 人名单，写入 `PILOT_USER_IDS`。
2. 把 §3.1 一页纸和 §6 反馈表发到企微/飞书。
3. 预约 30 分钟培训；准备现场演示「三问」。
4. 建好周报文档，D7 必填第一版。

---

## 11. 小结

灰度不是发链接，是 **节奏 + 反馈 + 周报 + 修复闭环**。  
5 位领导的时间很贵，你用结构化反馈尊重他们的时间，他们才会给你第二周。
