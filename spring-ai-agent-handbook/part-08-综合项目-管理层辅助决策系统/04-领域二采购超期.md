# 04 · 领域二：采购超期

> 管理层问采购，通常不是「PO 号是多少」，而是「谁又拖了、拖了什么、会不会断料」。

---

## 1. 本域问题

1. 当前超期未到货的采购单有哪些？按供应商谁最严重？
2. 某个 SKU 是否被超期采购拖累？
3. 某供应商近 30 天超期单数量。

超期定义写入假制度：

```text
超期 = 承诺到货日 promised_date < 今天，且收货状态不是 CLOSED/RECEIVED。
部分收货：received_qty < order_qty 仍算未关闭，若 promised_date 已过则算超期。
```

---

## 2. 视图

```sql
CREATE VIEW v_purchase_overdue AS
SELECT po.id AS po_id,
       po.supplier_id,
       po.supplier_name,
       pol.sku_id,
       pol.order_qty,
       pol.received_qty,
       (pol.order_qty - pol.received_qty) AS open_qty,
       po.promised_date,
       (current_date - po.promised_date) AS days_overdue,
       po.status,
       po.updated_at AS data_as_of
FROM purchase_order po
JOIN purchase_order_line pol ON pol.po_id = po.id
WHERE po.promised_date < current_date
  AND po.status NOT IN ('CLOSED', 'RECEIVED')
  AND pol.received_qty < pol.order_qty;
```

## 3. 工具

```java
@Tool(description = "查询超期未关闭采购行，可按供应商或 SKU 过滤。返回天数、未收数量、数据截止时间。只读。")
public String listOverduePurchase(
        @ToolParam(description = "可选，供应商编码") @Nullable String supplierId,
        @ToolParam(description = "可选，SKU") @Nullable String skuId,
        @ToolParam(description = "最多返回条数，默认 10，最大 50") @Nullable Integer limit,
        ToolContext ctx) {
    int n = limit == null ? 10 : Math.min(limit, 50);
    UserScope scope = support.scope(ctx);
    // 若采购按组织隔离，这里过滤 org
    return support.toJson(purchaseRepository.findOverdue(scope, supplierId, skuId, n));
}

@Tool(description = "按供应商汇总超期采购：单数、未收数量、最大超期天数。用于 Top 供应商。只读。")
public String summarizeOverdueBySupplier(ToolContext ctx) {
    UserScope scope = support.scope(ctx);
    return support.toJson(purchaseRepository.summarizeBySupplier(scope, 5));
}
```

【易混】不要让模型自己「今天减 promised_date」。视图算好 `days_overdue`。

## 4. 和库存域的联动（仍然是一个 ChatClient）

用户问：「SKU-1001 会不会断料？」理想轨迹：

1. `queryInventory` 看可用与安全库存。
2. `listOverduePurchase(skuId=SKU-1001)` 看在途是否还靠谱。
3. 归纳：可用低且采购超期 → 风险高；可用高即使采购超期 → 风险另说。

你不手写工作流引擎。靠工具描述 + 系统提示：

```text
当用户问断料、缺货风险时，应同时查看库存快照与该 SKU 的超期采购，不要只看一项。
```

若评测发现它经常漏第二步，把两个查询做成一个组合工具 `assessStockoutRisk(skuId, warehouseId)`，内部 Java 调两个仓储。这是企业里非常实用的手法：**用 Java 固化高频跨域问题，把模型从「编排家」降成「解释家」。**

第一期允许两种都存在。组合工具更稳，离散工具更灵活。评测集决定。
