# 02 · 信息架构与包结构

> 包结构一旦乱，工具、权限、审计会缠成一团。先定文件夹，再填类。

---

## 1. 逻辑分层

```
web        鉴权、会话 ID、SSE、DTO
application  ChatClient 编排、系统提示、审计、限流
agent      工具类、RAG 摄入与 Advisor 装配
domain     指标含义、UserScope（尽量薄）
infra      JDBC、VectorStore、ChatMemory、DeepSeek 配置
```

不要按「erp/wms/ems」切 Maven 多模块——第一期一个 jar 够。等三个域团队独立发版再拆。

## 3. ChatClient 怎么拆

两个 Bean 足够：

```java
@Bean
@Primary
ChatClient proClient(ChatClient.Builder builder, /* advisors, tools */) {
    return builder
            .defaultSystem(PromptCatalog.DECISION)
            .defaultAdvisors(memoryAdvisor, ragAdvisor)
            .defaultTools(inventoryTools, purchaseTools, equipmentTools)
            .build();
}

@Bean
ChatClient flashClient(ChatClient.Builder builder) {
    return builder
            .defaultSystem("你只做短改写与标题生成，不查数。")
            .build();
}
```

注意：若 flash 与 pro 要不同 `ChatModel`，按 part-03 用 `ChatClientBuilderConfigurer` 装配，避免丢观测。学习期可以共用 DeepSeek，只是 pro Bean 在 options 里指定 `deepseek-v4-pro`，flash 指定 `deepseek-v4-flash`——若当前 starter 一个 ChatModel 绑一个默认模型，则用运行时 `DeepSeekChatOptions` 覆盖。

编排层规则：

- 用户问题一律走 `proClient`（决策要稳）。
- flash 仅用于：查询改写（RAG 的 RewriteQueryTransformer 内部）、会话标题。

不要做复杂意图分类微服务。第一期让模型和工具自己选。评测集发现它乱选工具，再加一个极薄的关键字路由（例如「停机」只挂设备工具）——那是优化，不是第一天。

## 4. 一个请求的时序

```
Controller
  1. 解析 UserScope、conversationId
  2. GuardService.precheck
  3. RateLimitService.check
  4. ChatOrchestrator.ask
       - 填 toolContext(scope)
       - 调 proClient（记忆+RAG+工具循环）
       - 结构化成 DecisionReply
  5. AuditService.save
  6. SSE 或 JSON 返回
```

失败在哪一步都要审计。

## 5. API 设计

```text
POST /api/chat
  Header: X-User-Id, X-Conversation-Id
  Body: { "message": "..." }
  200: DecisionReply
  400: 缺会话 / 过长
  401: 无身份
  429: 限流

GET  /api/chat/stream  或 POST + text/event-stream
GET  /api/direct/inventory?sku=&warehouse=
GET  /api/audit?userId=&from=&to=     （管理员）
POST /api/rag/reload                  （管理员，演示用）
```

`DecisionReply` 建议：

```java
public record DecisionReply(
        String status,          // OK, REJECTED, ERROR, DEGRADED
        String conclusion,
        List<Metric> metrics,
        List<Source> sources,
        List<String> risks,
        List<String> suggestions,
        String rejectReason
) {
    public record Metric(String name, String value, String unit, Instant dataAsOf) {}
    public record Source(String type, String name, String detail) {} // TOOL / DOC
}
```

第一期若结构化抽取不稳，允许先返回 `markdown` 全文，同时另字段塞 sources。但系统提示必须按五段输出，方便你后期改 `.entity(DecisionReply.class)`。

## 6. 【必做】

1. 建空项目，包结构建好。
2. `GET /actuator/health` 能通。
3. `ChatController` 先返回写死的 `DecisionReply`，确认前端以后能接。然后再接线到真 ChatClient。

骨架先于智能。很多项目死在「ChatClient 都写了但 URL 和 DTO 每天改」。
