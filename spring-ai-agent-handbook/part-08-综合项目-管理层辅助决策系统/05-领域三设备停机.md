# 05 · 领域三：设备停机

> EMS 在本讲义里按设备/能源/运维系统理解。若你们实际是 MES，把「停机事件」换成「产线停线记录」，工具形状一样。

---

## 1. 本域问题

1. 昨天（或近 7 天）停机超过 30 分钟的产线有哪些？
2. 某条产线最近一次停机原因与时长。
3. 停机是否与某 SKU 产出缺口「时间上重叠」（只陈述重叠，不擅自说因果）。

制度假文案：

```text
停机时长 = ended_at - started_at（未结束则到 now）。
「严重停机」= 时长 ≥ 30 分钟。
计划停机（保养）与故障停机要区分 reason_type：PLANNED / FAULT。
管理层默认问的是 FAULT，除非他们说包含保养。
```

---

## 2. 工具

```java
@Tool(description = """
        查询设备故障停机。默认 reason_type=FAULT，时长不少于 30 分钟。
        可指定产线、起始时间。返回产线、设备、分钟数、原因、数据时间。只读。
        """)
public String listDowntime(
        @ToolParam(description = "可选产线编码") @Nullable String lineId,
        @ToolParam(description = "回溯天数，默认 1，最大 30") @Nullable Integer days,
        ToolContext ctx) {
    int d = days == null ? 1 : Math.min(days, 30);
    UserScope scope = support.scope(ctx);
    support.requireLineScope(scope, lineId);
    return support.toJson(equipmentRepository.findFaultDowntime(scope, lineId, d, 30));
}
```

组织/产线范围同样强制。仓经理未必能看全部产线。

---

## 3. 因果【红线】

模型很爱说「因为停机所以缺货」。没有产出表对账时，系统提示必须写：

```text
你可以指出停机时间窗口与库存下降是否邻近，但不要断言因果关系。
若没有产出数据，明确说「无法从当前数据验证产出缺口」。
```

第一期甚至不要做「停机影响产出」工具，除非你有 `output_gap` 表。演示靠停机清单已经够了。贪心会导致胡编。
