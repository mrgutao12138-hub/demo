# 经营决策逻辑架构（研发版）

> 面向研发落地：系统边界、数据契约、调度/插件接口、闭环执行、合规拦截、MVP 顺序。  
> 原文未钉死的字段/接口，文中标为 **【建议】**，实现前需与数据/业务确认。

---

## 0. 一句话与硬约束

**AI 只产出概率/趋势；规则引擎把概率换成可执行动作；合规在落库给业务之前物理丢弃违规方案；人审批后才打 ERP。**

研发必须守住的边界：

| ID | 约束 | 反例（禁止） |
|----|------|----------------|
| C1 | 模型不得直接调用 ERP/WMS/CRM | 在 `predict()` 里调采购创建接口 |
| C2 | 业务后端只消费 `dws_decision_advice` 中 `status='primary'` | 业务去读模型中间表或 shadow 行 |
| C3 | 硬红线命中发生在 **建议生成阶段**（`reject_at_generation`） | 先展示「违规能赚多少」再拦 |
| C4 | 硬红线剔除的方案 **不得写入违规收益** | audit 里记 excluded benefit |
| C5 | 用户执行/拒绝/改量必须回写 `dwd_human_feedback` | 只打 ERP 不记反馈 |
| C6 | 切模型走配置表 `logic_ref` + 影子升主，不改 DAG 硬编码 | Airflow DAG 里写死 `models.v2` |

## 1. 系统边界与职责矩阵

两张图是同一套系统的两个切面，不要做成两套代码。

| 切面 | 回答的问题 | 对应代码/服务 |
|------|------------|----------------|
| 落地四层 | 进程怎么拆、谁调谁、指令怎么进 ERP | 前端 / 业务中台 / Airflow+模型 / 数仓+SSO |
| 逻辑五层 | 一条建议在批处理内存里怎么算、合规在哪一刀切 | 特征 → 模型 → D1–D5 规则 → 合规 → 契约表 |

### 1.1 落地四层（部署视角）

```
[一线销售/采购] [管理层]
        │ SSO (Keycloak / 泛微 OA)
        ▼
┌─ L1 前端门户 ─────────────────────────────────────┐
│  智能任务中心 │ 数据驾驶舱(iframe/SDK→Superset) │ 规则配置台 │
└───────────┬──────────────────┬────────────────────┘
            │                  │
            ▼                  ▼
┌─ L2 业务闭环（新核心）────────────────────────────┐
│  Listener → Workflow → ComplianceInterceptor → API Gateway │
└───────────┬──────────────────────────────────────┘
            │ 仅 primary 建议
            ▼ 轮询/订阅
┌─ L3 AI/规则批处理 ────────────────────────────────┐
│  Airflow → Run_Decision_Engine.py → BaseDecisionModel* │
│  写出 dws_decision_advice                             │
└───────────┬──────────────────────────────────────┘
            │ 特征宽表
            ▼
┌─ L4 数仓 + 基础设施（复用）───────────────────────┐
│  ODS→DWD→DWS/ADS │ Superset │ Keycloak            │
└───────────┬──────────────────────────────────────┘
            │ T+1 ETL
            ▼
      ERP / WMS / CRM  （执行端，L2 反向下达指令）
```

### 1.2 模块所有权（建议）

| 模块 | Owner | 技术栈（原文） | 备注 |
|------|-------|----------------|------|
| 特征/ADS/DWS 表 | 数据平台 | 现有仓 | D1–D5 的输入质量归这一侧 |
| `Run_Decision_Engine` + 模型插件 | 算法 + 后端共同守契约 | Python, Airflow, importlib | 算法写 `predict`，后端守 `format_to_advice` Schema |
| Listener / Workflow / 合规拦截 / Gateway | 业务中台 | 【建议】独立服务 | 唯一允许调 ERP 的进程 |
| 任务中心 / 配置台 | 前端 + 中台 API | — | 驾驶舱不自研报表，嵌 Superset |
| SSO | 已有 | Keycloak / 泛微 | 门户与 Superset 都走 SSO |

### 1.3 逻辑五层（批处理管内视角）

```
业务数据 ──► AI 只算概率 ──► D1–D5 用公式算钱/算动作
                                    │
                                    ▼
                          硬红线（命中则 Drop，不记收益）
                                    │ 通过
                                    ▼
                          软边界（收益打折 + 高风险标红）
                                    │
                                    ▼
                          dws_decision_advice + log_audit_trail
```

**D3（额度/黑名单）、D5（近效期）** 原文图画了部分直出；实现时仍建议统一过合规拦截器，用空规则集跳过，避免两条写出路径。

## 2. 核心数据契约

所有跨层通讯收口到下面几张表。**L2 禁止依赖模型私有表。**

### 2.1 `dws_decision_advice`（AI ↔ 业务唯一协议）

建议粒度：**一条 = 一个可执行动作候选**（同一 `trace_id` 可多行）。

| 字段 | 类型【建议】 | 必填 | 说明 |
|------|----------------|------|------|
| `advice_id` | string/uuid | Y | 行主键 |
| `trace_id` | string | Y | 批次追踪号，对齐 `log_audit_trail` |
| `rule_id` | string | Y | 如 `R_D1_REPLENISH` / `D5_临期` |
| `decision` | string | Y | 场景码：`D1`…`D5` |
| `model_version` | string | Y | 如 `v2.1_XGBoost` |
| `status` | enum | Y | `primary` \| `shadow`；L2 **只拉 primary** |
| `action_code` | string | Y | 见 §2.2，Gateway 路由键 |
| `action_params` | json | Y | 执行参数，如 `{sku, qty, discount}` |
| `reason_chain` | json | Y | 前端直接渲染的理由链 |
| `risk_band` | json | Y | 最好 / 最坏 / 无作为成本 |
| `created_at` | timestamp | Y | 批次时间 |
| `effective_at` / `expire_at` | timestamp | N | 【建议】任务过期不执行 |

`reason_chain` 【建议】结构：

```json
{
  "summary": "SKU-A 建议补货 100",
  "steps": [
    {"step": "p90_demand", "value": 1000, "source": "dws_demand_forecast"},
    {"step": "on_hand_in_transit", "value": 900, "source": "dwd_inventory_batch"},
    {"step": "safety_stock_formula", "value": 100, "formula_ref": "D1"}
  ]
}
```

`risk_band` 【建议】结构：

```json
{
  "best":  {"metric": "gross_margin", "value": 12000},
  "worst": {"metric": "gross_margin", "value": -3000},
  "do_nothing": {"metric": "stockout_cost", "value": 8000}
}
```

### 2.2 `action_code` → Gateway 路由

原文已给示例，落地时做成枚举 + 适配器，**禁止**在工作流里 if-else 散落 URL。

| action_code | 含义 | 下游【建议】 |
|-------------|------|----------------|
| `CREATE_PO` | 创建采购单 | ERP 采购 |
| `MARK_DISCOUNT` | 打促销/折扣 | ERP 价格 或 CRM |
| 【待补】调拨 / 退厂 / 额度冻结 / 投放工单 | D5 / D3 / D4 | WMS / 信控 / 投放系统 |

`action_params` 必须能被对应适配器 JSON Schema 校验；校验失败 = 本条建议不可执行，进审计，不打 ERP。

### 2.3 `cfg_decision_rule`（调度路由，工厂配置）

原文示例（D1）：

```text
rule_id:        R_D1_REPLENISH
decision:       D1
scope:          {product_lines:[...], abc:[A,B], pattern:[high_freq]}
trigger:        {cron:"0 6 * * 1", or_event:["inv_cover_days<min","task_progress_gap>0.1"]}
inputs:         [dws_demand_forecast, dwd_inventory_batch, dim_vendor_policy, dws_payment_health]
logic_ref:      "logic.D1"          # importlib 路径，热更新只改这里
params:         {service_level:0.95, z_factor_method:"from_p90_p50"}
output_template:TPL_D1
owner:          supply_chain
effective:      {from:2026-08-01, to:null}
version:        3
```

影子模式需要在同一 `rule_id` 下挂多模型，【建议】拆行或加 role：

| 字段【建议】 | 说明 |
|--------------|------|
| `role` | `primary` \| `shadow` |
| `enabled` | bool |
| `logic_ref` | Python 模块路径，如 `models.replenishment.v3` |

**热更新**：改 `logic_ref` / `role`，次日（或下次 cron）批处理生效，DAG 不改。

`trigger.or_event` 是近实时探针；MVP 可只实现 `cron`，事件触发作为二期（见 §8）。

### 2.4 `cfg_compliance_rule`

原文硬红线示例 `C_HARD_KICKBACK_01`：

- `category`: `hard_redline`
- `detection.any`: 任一命中即拦（个人账户收款、现金礼品/未入账返利、会议无议程、单场金额 > 硬阈值、赞助挂钩采购）
- `action_on_hit`: **`reject_at_generation`**
- `soft_decay`: 硬红线为 null；软边界另配衰减系数
- `audit_log`: `log_exclusion_reason=true`，`log_excluded_benefit=false`

【建议】拦截器实现：

- `any` / `all` 组合求值
- `${cfg.threshold_hard}` 从配置中心解析，不要写死在规则 JSON
- 命中：候选从内存剔除，audit 只写 `rule_id + reason`，**收益字段置空或不落列**

### 2.5 `log_audit_trail`

原文字段包：

```text
trace_id, decision_id, input_snapshot_hash,
candidate_set_soft:[U, risk],
excluded_hard:[{rule_id, reason}],
chosen_option, chosen_by, forced_high_risk,
review_triggered, review_result, review_by,
executed, executed_params, timestamp
```

注意：`excluded_hard` 只有规则与原因，**没有金额**。`input_snapshot_hash` 用于复现，原始快照建议另存对象存储/审计表，本表只存 hash。

### 2.6 `dwd_human_feedback`（闭环 Label）

原文要求在用户「一键执行 / 拒绝 / 修改后执行」时由 **L2 写入**。

【建议】最小字段：

| 字段 | 说明 |
|------|------|
| `advice_id` / `trace_id` | 对齐建议 |
| `operator_id` | SSO 用户 |
| `action` | `accept` \| `reject` \| `modify_execute` |
| `original_params` / `final_params` | 改量时两边都留（建议 100 → 实采 50） |
| `operated_at` | — |

L3 定期读此表做监督学习样本，**不要**让模型在线连工作流库。

### 2.7 `dws_demand_forecast`（D1/D2/D5 主输入）

| 字段 | 说明 |
|------|------|
| `product_id` / `customer_id` / `region_id` / `period` | 粒度键 |
| `p10` / `p50` / `p90` | 需求分位数 |
| `overhang_h` | 透支池估计 |
| `supply_censor_flag` | 供给删失（断货导致销量被低估） |
| `demand_pattern` | `high_freq` \| `intermittent` \| `declining` |
| `prob_occur` / `cond_mean` | 间歇品 |
| `external_lift` | 外生信号贡献 |
| `model_version` / `fit_metric` | 版本 / WAPE / coverage |

D5 MVP 允许用「近 90 天平均月销」**临时代替 p50**，但列名/接口仍建议走同一张预测表或同一 View，避免 D5 代码分叉读销售明细。

### 2.8 其它输入（规则 `inputs` 已点名）

| 表 | 用途 |
|----|------|
| `dwd_inventory_batch` | 在途/在库、库龄、效期 → D1 净需求、D5 临期 |
| `dim_vendor_policy` | 供应商约束（MOQ、提前期等） |
| `dws_payment_health` | 回款健康 → D3 |
| 发货/纯销、财务台账、医保/中标指数 | 特征源，经 ADS 进模型，不让规则层直连 ODS |

**库存天数不准 → D1/D5 全错。** 特征 SLA 要单独监控，不要只监控 Airflow 成功。

## 3. L3：调度引擎与插件模型

### 3.1 目录【建议】

```text
decision_engine/
  airflow/dags/decision_engine_daily.py   # 只调入口，不 import 具体模型
  engine/run_decision_engine.py           # 读配置、动态加载、写契约表
  engine/base_model.py                    # ABC
  engine/compliance.py                    # 生成期硬/软规则
  models/replenishment/v3.py
  models/expiry/v1.py
  models/credit/xgboost_v1.py
  models/uplift/v1.py
```

DAG 伪代码：

```python
# 禁止：from models.replenishment.v3 import ReplenishmentV3
Run_Decision_Engine.py  # 内部读 cfg_decision_rule
```

### 3.2 基类（原文，落地时补合规与 status）

```python
from abc import ABC, abstractmethod

class BaseDecisionModel(ABC):

    @abstractmethod
    def fetch_features(self, config):
        """从 DWS 抽本规则 inputs 声明的特征，受 scope 过滤。"""

    @abstractmethod
    def predict(self, data):
        """只出概率/中间量。禁止副作用、禁止写 ERP。"""

    @abstractmethod
    def format_to_advice(self, raw_prediction):
        """转为 dws_decision_advice 行（含 action_code / reason_chain / risk_band）。"""

    def execute(self, config):
        data = self.fetch_features(config)
        res = self.predict(data)
        advices = self.format_to_advice(res)
        advices = apply_compliance(advices, config)  # 生成期拦截
        self.save_to_dws(advices, status=config.role)  # primary | shadow
```

新场景（如 D6 流失）：新建子类 → 实现三方法 → `cfg_decision_rule` 注册 `logic_ref`。不必改调度。

### 3.3 每日主路径

```text
Airflow cron
  → Run_Decision_Engine.py
  → 读 cfg_decision_rule（effective 窗口 + enabled）
  → for each rule_id:
        importlib.import_module(logic_ref)
        实例化 BaseDecisionModel 子类
        execute()
  → 写入 dws_decision_advice（带 status）
        primary → L2 Listener 拉取
        shadow  → 仅数分对比，L2 忽略
```

**幂等【建议】**：同一 `trace_id`（或 `rule_id + batch_date + model_version`）先删后写或 MERGE，避免重跑双倍任务。

### 3.4 影子升主

1. 同 `rule_id` 配 `role=primary`（v1）与 `role=shadow`（v2）  
2. 两套都跑、都落建议表，L2 只消费 primary  
3. 对比 WAPE / 覆盖 / 与 `dwd_human_feedback` 采纳率  
4. 配置把 v2 改 `primary`，v1 降级或 `enabled=false`

禁止「先停 v1 再上 v2」的空窗切流。

## 4. L2：监听、工作流、合规、执行

L2 是 **唯一执行面**。L3 的合规是生成期过滤；L2 拦截器是执行前二次校验（防配置被改、防人工改参绕过）。

```text
dws_decision_advice (status=primary)
        │ Listener：轮询或订阅（CDC / NOTIFY）
        ▼
  物化为待办任务（工作流）
        │ 用户：执行 / 拒绝 / 改参后执行
        ▼
  ComplianceInterceptor（硬红线再跑一遍，含改后的 action_params）
        │ pass
        ▼
  API Gateway 按 action_code 调 ERP
        │
        ├─ 成功 → 回写 executed + executed_params
        └─ 始终 → dwd_human_feedback + log_audit_trail
```

### 4.1 Listener

- 过滤：`status='primary'` 且未过期、未生成过任务  
- 【建议】按 `advice_id` 幂等建任务，重复拉取不建双单  
- shadow 行永不进工作流

### 4.2 工作流与前端

任务中心展示字段直接映射契约：

- 建议动作 ← `action_code` + `action_params`
- 理由 ← `reason_chain`
- 风险 ← `risk_band`
- 一键执行 = 工作流提交，不是前端直连 ERP

规则配置台写 `cfg_decision_rule` / `cfg_compliance_rule`（权限按 `owner` + SSO 角色）。

驾驶舱：iframe/SDK 嵌 Superset，数据集来自仓，不在门户里重做 BI。

### 4.3 Gateway

- 适配器注册表：`action_code → client.method`  
- 超时、重试、幂等键（【建议】`advice_id` 或 `trace_id + action_code`）  
- ERP 失败要可重放，且工作流状态可见

## 5. D1–D5：算法职责 vs 规则职责

实现时拆成 **Model.predict（概率）** 和 **DecisionRule（算钱/算量）**。原文强调：AI 不说「进 1000 盒」，只说 P90=1000；D1 再扣在途。

| 场景 | AI 层产出 | 规则层（解释性公式） | 合规敏感度 |
|------|-----------|----------------------|------------|
| **D1 日常备货** | 需求 P50/P90、透支池 | 安全库存 / 净补货量 | 中（过硬红线） |
| **D2 压货冲量** | 需求分位 | 净收益=0 求解压货量 | **高**，必须硬红线 |
| **D3 额度/黑名单** | 90 天逾期概率（XGBoost/生存分析） | 动态阈值 | 高（信控） |
| **D4 资源投放** | Uplift：投 1 元额外毛利 | 预算约束线性规划 | **高**，必须硬红线 |
| **D5 近效期** | 可用 P50（或 MVP 用 90 天均销） | `库存/P50 > 剩余效期月数` → 退厂/调拨 | 中 |

数据复用：

- 销售 → 时序模型、Uplift  
- 财务 + 外部指数 → 风控  
- **库存批次 → D1 且 D5**

### 5.1 D5 优先上线（确定性规则）

```text
cover_months = on_hand_qty / p50_monthly_velocity
if cover_months > remaining_shelf_life_months:
    告警 / MARK_DISCOUNT 或 调拨/退厂
```

- 无黑盒；P50 未就绪时用近 90 天平均月销经同一 View 注入  
- 状态空间模型只是把断货/压货水分从 P50 里挤掉，**替换输入即可，不要重写 D5 规则**

## 6. 合规防火墙（生成期 + 执行期）

```text
D1/D2/D4 候选
    │
    ▼
硬红线 ──命中──► Drop（内存剔除）
    │                └─ audit: rule_id + reason，不写收益
    │通过
    ▼
软边界 ──► 收益 × decay，前端高风险标红，可强制执行但记 forced_high_risk
    │
    ▼
契约表 + 审计台账（谁批了高风险）
```

硬红线检测器按 `cfg_compliance_rule.detection` 对 **候选动作字段** 求值（`payee_type`、`expense_type`、`meeting_has_agenda` 等）。D2/D4 的投放/压货对象必须带齐这些字段，否则视为不可执行（失败安全：缺字段 = 不通过）。

## 7. 观测、探针、反馈

### 7.1 下放探针

| 阶段 | 做法 | 落点 |
|------|------|------|
| 专家经验 | 线下或轻量看板 | 人脑，不进引擎 |
| 回写融合 | **必须进仓，一般 DWD** | 才能进特征、规则、审计 |

不要把探针只停在 Excel/看板。

### 7.2 批处理 SLO【建议】

- Airflow DAG 成功 ≠ 建议可用：监控「primary 行数、空结果、契约 Schema 失败率」  
- 特征新鲜度：`dwd_inventory_batch`、`dws_demand_forecast` 的 `period`  
- 闭环：建议数 / 任务数 / 执行数 / 改参率 / ERP 失败率  
- 影子：primary vs shadow 的量差、方向不一致率

### 7.3 追踪

全链路用 `trace_id`：特征快照 hash → 建议行 → 工作流任务 → ERP 幂等键 → feedback。排障只跟这一个 ID。

## 8. MVP 实施顺序（研发排期）

按依赖，而不是按模型炫技。

| 序 | 交付 | 目的 |
|----|------|------|
| 1 | 契约表 + `log_audit_trail` + 空 Listener | 钉死协议 |
| 2 | `cfg_decision_rule` + `Run_Decision_Engine` + ABC | 能热插拔 |

## 11. 研发 FAQ

**Q: 新算法要改后端吗？**  
A: 只要能 `format_to_advice` 进现有 Schema、`action_code` 已注册。新动作类型才需要加 Gateway 适配器。

**Q: 规则和模型写在一个类可以吗？**  
A: MVP 可以（D5 尤其如此）。D1 起建议 `predict()` 只返回分位，补货公式放独立函数，方便测「P90 不变、在途变了、建议怎么变」。

**Q: 合规只做在 L2 行不行？**  
A: 不行。原文要求生成期就 Drop，避免违规收益出现在任何业务可见数据集（含报表）。L2 是第二道，防改参。

**Q: 为什么业务不能读特征表自己算？**  
A: 破坏唯一契约和审计快照；影子对比、热更新、合规剔除都会失真。
